# Mounting and Unmounting Filesystems

## Mounting

Linux does not use drive letters such as `C:` or `D:` like Windows. Instead, Linux provides a single directory tree that starts at the root directory `/`.

To make a filesystem available, Linux **mounts** it onto a directory called a **mount point**.

A filesystem can be located on:

* A disk partition
* An LVM logical volume
* A USB drive
* A CD/DVD
* A network filesystem such as NFS or CIFS
* A loop-mounted image file
* Other block or virtual devices

Example:

```bash
sudo mount /dev/sdb1 /mnt/usb
```

After mounting:

```text
/dev/sdb1
    ↓
/mnt/usb
    ↓
Linux directory tree
```

The files stored on `/dev/sdb1` become accessible through `/mnt/usb`.

### Mount Point

A **mount point** is a directory in the existing Linux filesystem tree where another filesystem is attached.

For example:

```bash
sudo mkdir /data
sudo mount /dev/sdb1 /data
```

The filesystem on `/dev/sdb1` is now accessible through `/data`.

The mount point does not have to be empty from the kernel's point of view, but it is strongly recommended that it be an empty directory.

If a filesystem is mounted on a directory that already contains files, those files are **temporarily hidden** while the filesystem is mounted.

For example:

```text
Before mounting:

/mnt/data/
├── file1.txt
└── file2.txt
```

If another filesystem is mounted on `/mnt/data`:

```text
/mnt/data/
├── external-file1
└── external-file2
```

The original `file1.txt` and `file2.txt` have **not been deleted**. They are simply hidden by the mounted filesystem.

After:

```bash
sudo umount /mnt/data
```

the original files become visible again.

> Mounting a filesystem never moves or copies its data. It only determines where that filesystem is visible in the Linux directory tree.

---

## Temporary and Permanent Mounts

There are two common ways to mount a filesystem.

- ### Temporary Mount

    A manual mount normally remains active until it is explicitly unmounted or the system shuts down/reboots.

    Example:

    ```bash
    sudo mount /dev/sdb1 /mnt/usb
    ```

    After reboot, this manual mount is normally gone unless the filesystem is configured for automatic mounting.

    The data on `/dev/sdb1` is **not deleted**.

    You can mount the same filesystem somewhere else later:

    ```bash
    sudo mount /dev/sdb1 /home/user/data
    ```

    The filesystem's data does not depend on the mount point.

    For example:

    ```bash
    sudo mount /dev/sdb1 /mnt/usb
    sudo umount /mnt/usb

    sudo mount /dev/sdb1 /home/user/data
    ```

    The same filesystem is now accessible through a different directory.

- ### Permanent Mount

    To automatically mount a filesystem at boot, configure it in:

    ```text
    /etc/fstab
    ```

    Example:

    ```text
    UUID=7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab /data ext4 defaults 0 2
    ```

    The system reads `/etc/fstab` during boot and mounts the configured filesystem.

---

# The `/etc/fstab` File

`/etc/fstab` is the standard configuration file used to define filesystems that should be mounted automatically.

Each filesystem entry contains six fields:

```text
<device> <mount_point> <filesystem_type> <options> <dump> <fsck_order>
```

Example:

```text
UUID=7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab /data   ext4 defaults 0 2
/dev/sdb1                                  /backup xfs  noatime  0 2
/dev/sda2                                  none    swap sw       0 0
```

## The Six `/etc/fstab` Fields

- ### Device

    Specifies the filesystem to mount.
    
    It can be specified using:
    
    * Device path
    * UUID
    * Filesystem label
    
    Example:
    
    ```text
    /dev/sdb1
    ```
    
    or preferably:
    
    ```text
    UUID=7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab
    ```
    
    or:
    
    ```text
    LABEL=DATA
    ```
    
- ### Mount Point

    The directory where the filesystem will be attached.

    Example:

    ```text
    /data
    ```

    For swap, `none` is commonly used.

- ### Filesystem Type

    Specifies the filesystem type.

    Examples:

    ```text
    ext4
    xfs
    btrfs
    vfat
    exfat
    swap
    nfs
    ```

    The special value:

    ```text
    auto
    ```

    can be used to let the system detect the filesystem type.

- ### Mount Options

    Specifies how the filesystem should be mounted.

    Example:

    ```text
    defaults
    ```

    Multiple options are separated by commas:

    ```text
    rw,noatime
    ```

- ### Dump

    The fifth field is related to the legacy `dump` backup utility.

    Typical values are:

    ```text
    0
    1
    ```

    For modern Linux systems, this is usually set to:

    ```text
    0
    ```

    which disables dump-based filesystem backups.

- ### Filesystem Check Order

    The sixth field controls the order in which `fsck` checks filesystems during boot.

    Common values:

    ```text
    0
    1
    2
    ```

    * `0` → Do not automatically check this filesystem with `fsck`
    * `1` → Check first; normally used for the root filesystem
    * `2` → Check after the root filesystem

    Example:

    ```text
    UUID=... /     ext4 defaults 0 1
    UUID=... /home ext4 defaults 0 2
    ```

    For filesystems that should not be checked by `fsck`, use:

    ```text
    0
    ```

# Why UUID Is Usually Preferred

Device names such as:

```text
/dev/sda1
/dev/sdb1
```

are not guaranteed to remain the same when disks are added, removed, or detected in a different order.

For example, a disk that is currently:

```text
/dev/sdb
```

could become:

```text
/dev/sdc
```

after another disk is added.

A filesystem UUID is normally stable across device-name changes.

Find UUIDs with:

```bash
sudo blkid
```

or:

```bash
lsblk -f
```

Example:

```text
/dev/sdb1: UUID="7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab" TYPE="ext4"
```

Then use:

```text
UUID=7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab /data ext4 defaults 0 2
```

This is generally safer than:

```text
/dev/sdb1 /data ext4 defaults 0 2
```

---

# Filesystem Labels

A filesystem can also have a human-readable label.

For example:

```text
LABEL=DATA
```

You can view labels with:

```bash
lsblk -f
```

or:

```bash
blkid
```

Labels can be useful because they are easier to recognize than long UUIDs.

However, labels should be unique if they are used to identify filesystems.

# Mounting a Filesystem Manually

Suppose `/dev/sdb1` contains an ext4 filesystem.

Create a mount point:

```bash
sudo mkdir -p /mnt/data
```

Mount it:

```bash
sudo mount /dev/sdb1 /mnt/data
```

Verify:

```bash
findmnt /mnt/data
```

or:

```bash
lsblk -f
```

or:

```bash
df -h /mnt/data
```

You can also check all current mounts:

```bash
mount
```

or:

```bash
findmnt
```

`findmnt` is generally more convenient for inspecting the current mount hierarchy.

---

# Mounting by UUID

Instead of specifying the device name:

```bash
sudo mount /dev/sdb1 /mnt/data
```

you can use:

```bash
sudo mount UUID=7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab /mnt/data
```

This is useful when you want to explicitly identify the filesystem by UUID.

---

# Mounting by Filesystem Type

You can explicitly specify the filesystem type:

```bash
sudo mount -t ext4 /dev/sdb1 /mnt/data
```

Usually this is not necessary because `mount` can detect the filesystem type automatically.

# Common Mount Options

Mount options control how a filesystem behaves after being mounted.

- ## `defaults`

    The `defaults` option represents a standard set of options:

    ```text
    rw,suid,dev,exec,auto,nouser,async
    ```

    Meaning:

    * `rw` → read/write
    * `suid` → allow SUID/SGID bits
    * `dev` → interpret device files
    * `exec` → allow execution of programs
    * `auto` → allow automatic mounting
    * `nouser` → only root can mount
    * `async` → perform I/O asynchronously

    Example:

    ```text
    UUID=... /data ext4 defaults 0 2
    ```

- ## `ro`

    Mount read-only:

    ```text
    ro
    ```

    Example:

    ```bash
    sudo mount -o ro /dev/sdb1 /mnt/recovery
    ```

    Useful when you want to inspect a filesystem while minimizing writes.

- ## `rw`

    Mount read/write.

    This is normally the default for filesystems that support writing.

- ## `noexec`

    Prevents execution of binaries from the mounted filesystem.

    Example:

    ```text
    noexec
    ```

    Useful for certain removable or untrusted storage.

    It does not mean that absolutely every form of code execution from that filesystem is impossible; it specifically affects execution through the filesystem's execution permission mechanisms.

- ## `nosuid`

    Ignores SUID and SGID bits on files within the filesystem.

    Useful for reducing privilege-escalation opportunities on removable or untrusted filesystems.

- ## `nodev`

    Prevents device files on the mounted filesystem from being interpreted as device nodes.

    Useful for removable or untrusted storage.

- ## `noatime`

    Prevents normal access-time (`atime`) updates.

    This can reduce metadata writes and may improve performance for some workloads.

    Modern filesystems and distributions may already use `relatime`, which provides a compromise between accurate access times and excessive writes.

- ## `user`

    Allows a non-root user to mount the filesystem.

    Example:

    ```text
    user
    ```

    The user who mounts the filesystem can normally unmount it as well.

- ## `users`

    Allows users to mount and unmount the filesystem.

- ## `auto` / `noauto`

    `auto` allows the filesystem to be mounted when `mount -a` is executed and normally during boot.

    `noauto` prevents automatic mounting through `mount -a`.

    Example:

    ```text
    UUID=... /data ext4 noauto 0 2
    ```

    The filesystem can still be mounted manually.

# Testing `/etc/fstab`

After editing `/etc/fstab`, do **not** immediately reboot.

Test the configuration with:

```bash
sudo mount -a
```

`mount -a` attempts to mount all applicable filesystems configured in `/etc/fstab` that are not already mounted and are not marked with `noauto`.

If there is a syntax, UUID, mount-point, or filesystem problem, this command can expose it before rebooting.

> Always test `/etc/fstab` before rebooting. A bad entry can cause boot problems or leave the system waiting for a device that does not exist.

You can then verify:

```bash
findmnt
```

or:

```bash
lsblk -f
```

---

# `systemctl daemon-reload` and `/etc/fstab`

Modern Linux systems using `systemd` generate mount units from `/etc/fstab`.

After changing `/etc/fstab`, you may run:

```bash
sudo systemctl daemon-reload
```

This tells `systemd` to reload its unit configuration.

However, an important distinction is:

> `systemctl daemon-reload` is not normally required just to make `mount -a` read the newly edited `/etc/fstab`.

`mount -a` reads `/etc/fstab` itself.

`daemon-reload` becomes relevant when `systemd` needs to regenerate/reload its generated mount-unit configuration, especially when managing mounts through `systemd`.

A safe sequence on a modern system is:

```bash
sudo nano /etc/fstab
sudo systemctl daemon-reload
sudo mount -a
```

Then verify:

```bash
findmnt
```

---

# Safely Editing `/etc/fstab`

This command is problematic:

```bash
sudo echo "something" >> /etc/fstab
```

The reason is that `sudo` applies only to `echo`.

The shell handles:

```text
>>
```

before `echo` is executed, so the shell attempts to open `/etc/fstab` with the current user's permissions.

A correct method is:

```bash
echo "/dev/sdb1 /test_1 ext4 defaults 0 2" | sudo tee -a /etc/fstab
```

The:

```text
-a
```

option means append instead of replacing the file.

For normal administration, however, it is usually safer to edit the file with an editor:

```bash
sudo nano /etc/fstab
```

or:

```bash
sudo vim /etc/fstab
```

# Mounting the Same Filesystem on Different Mount Points

A filesystem can be mounted at different locations at different times.

Example:

```bash
sudo mount /dev/sdb1 /mnt/usb
sudo umount /mnt/usb
sudo mount /dev/sdb1 /home/user/data
```

The filesystem's data has not changed.

Only its location in the Linux directory tree has changed.

> The mount point controls **where the filesystem is visible**, not where its data is physically stored.

---

# Mounting Over an Existing Mount Point

Linux allows another filesystem to be mounted over an existing mount point.

For example:

```bash
sudo mount /dev/sdb1 /data
sudo mount /dev/sdc1 /data
```

The contents of `/dev/sdb1` are now hidden behind `/dev/sdc1`.

The first filesystem is still mounted, but its contents are no longer visible through `/data`.

After:

```bash
sudo umount /data
```

the underlying filesystem becomes visible again.

Therefore, avoid mounting multiple filesystems on the same directory unless this behavior is intentional.

---

# Mounting Without a Mount Point

Linux can also mount some filesystems without an ordinary directory mount point using special mechanisms, but for normal filesystem administration, the important model is:

```text
Device/filesystem
        ↓
   mount command
        ↓
    mount point
        ↓
Linux directory tree
```

---

# Unmounting

To safely unmount a filesystem:

```bash
sudo umount /mnt/usb
```

You can also unmount using the device:

```bash
sudo umount /dev/sdb1
```

Unmounting removes the filesystem from the directory tree.

It does **not** delete the data.

After unmounting:

```text
Filesystem → no longer visible at the mount point
```

The filesystem remains on the disk and can be mounted again.

---

# Why Unmounting Matters

Linux uses caching for filesystem I/O.

When a program writes data, some data may initially remain in memory rather than being immediately written to the physical storage device.

Unmounting ensures that pending filesystem operations are properly completed before the filesystem is detached.

This is especially important for removable storage.

Do not simply remove a USB device while it is mounted and actively being written to.

---

# Checking Whether a Filesystem Is Busy

If you attempt:

```bash
sudo umount /mnt/data
```

you may receive:

```text
target is busy
```

This means some process is still using the filesystem.

Common reasons include:

* A shell's current working directory is inside the mount
* A process has an open file
* A program has a file descriptor open
* A process is using a file or directory under the mount
* Another filesystem is mounted beneath it

Useful commands include:

```bash
sudo lsof +f -- /mnt/data
```

and:

```bash
sudo fuser -vm /mnt/data
```

`fuser` is particularly useful for identifying processes using a mount point.

After identifying the process, close the application or move the shell outside the mount:

```bash
cd /
```

Then retry:

```bash
sudo umount /mnt/data
```

## `umount` Options

- ### `-f` — Force Unmount

    ```bash
    sudo umount -f /mnt/data
    ```

    Force unmounting is mainly useful for situations such as inaccessible network filesystems.

    It should not be treated as the normal solution to a busy local filesystem.

    Forcing an unmount while data is actively being written can cause data loss or corruption.

    > Do not use `-f` simply because `umount` says the filesystem is busy.

- ### `-l` — Lazy Unmount

    ```bash
    sudo umount -l /mnt/data
    ```

    A lazy unmount immediately detaches the filesystem from the directory namespace but allows the kernel to clean up the filesystem once existing references disappear.

    This is useful when a filesystem cannot be cleanly detached immediately, particularly with stuck network filesystems.

    A subtle point:

    If a process already has the filesystem open, it may continue to access existing references for a while even though the mount is no longer visible through the normal mount tree.

    Therefore:

    > `umount -l` does not kill processes or immediately terminate every existing reference to the filesystem.

- ### `-r` — Remount Read-Only

    ```bash
    sudo umount -r /mnt/data
    ```

    If unmounting fails, `-r` attempts to remount the filesystem read-only.

    This can be useful when a filesystem is experiencing problems and you want to stop further writes while keeping it accessible.

    It is not a substitute for proper filesystem repair.

- ### `-d` — Detach Loop Device

    ```bash
    sudo umount -d /mnt/image
    ```

    If the mount uses a loop device, this option also attempts to detach the associated loop device.

    This is useful when mounting disk images such as:

    ```text
    .iso
    .img
    ```

# Mounting ISO and Image Files

Linux can mount an image file using a loop device.

For example:

```bash
sudo mount -o loop image.iso /mnt/iso
```

The `loop` option allows a regular file to be treated as a block device.

Modern versions of `mount` can often detect that an image file requires a loop device automatically:

```bash
sudo mount image.iso /mnt/iso
```

To unmount:

```bash
sudo umount /mnt/iso
```

The loop device can be inspected with:

```bash
losetup -a
```

---

# Read-Only Mounting

A filesystem can be mounted read-only:

```bash
sudo mount -o ro /dev/sdb1 /mnt/recovery
```

This is useful when you want to inspect data without intentionally allowing normal write operations.

You can also remount an already-mounted filesystem:

```bash
sudo mount -o remount,ro /mnt/data
```

To return it to read/write:

```bash
sudo mount -o remount,rw /mnt/data
```

Whether a remount is possible depends on the filesystem and current system state.

---

# Mounting Network Filesystems

Mounting is not limited to local disks.

For example, NFS can be mounted with:

```bash
sudo mount -t nfs server:/export/data /mnt/data
```

CIFS/SMB shares can be mounted with:

```bash
sudo mount -t cifs //server/share /mnt/share
```

The same fundamental concept applies:

```text
Remote filesystem
       ↓
    mount
       ↓
Local mount point
       ↓
Linux directory tree
```

Network filesystems have additional options related to networking, authentication, availability, and recovery.

---

# Automatic Mounting

Modern Linux systems can automatically mount filesystems using mechanisms such as:

* `systemd`
* `systemd.automount`
* `udisks`
* Desktop environments
* `udev`-based mechanisms
* `/etc/fstab`

For server administration, `/etc/fstab` is one of the most important mechanisms for persistent filesystem mounting.

Desktop environments commonly use `udisks` for removable media.

# `findmnt`

`findmnt` is a useful command for inspecting mounted filesystems and mount relationships.

- **`findmnt`** → List all mounts
- **`findmnt /data`** → Show the filesystem mounted at a specific path
- **`findmnt /dev/sdb1`** → Show the mount point for a device
- **`findmnt -t ext4`** → A particularly useful option which displays mounts of a specific filesystem type.

`findmnt` is often easier to read than the raw output of:

```bash
mount
```

---

# `mount` Without Arguments

Running:

```bash
mount
```

without arguments displays currently mounted filesystems.

On modern Linux systems, output may include entries such as:

```text
/dev/sda2 on / type ext4 (...)
```

and virtual filesystems such as:

```text
proc
sysfs
tmpfs
devtmpfs
```

Not every mounted filesystem represents a physical disk.

Linux also mounts many virtual and kernel-provided filesystems.

---

# Checking Mounted Filesystems

Several commands are useful for checking mounts.

- **`findmnt`** → Best for understanding the mount hierarchy.
- **`mount`** → Displays current mounts.
- **`df -h`** → Shows filesystem capacity and usage for mounted filesystems.
- **`lsblk -f`** → Shows block devices, filesystem types, UUIDs, labels, and mount points.

These commands answer slightly different questions:

```text
lsblk  → What block devices/filesystems exist?
findmnt → Where are filesystems mounted?
df     → How much space is available/used?
```

# Mounting and the Directory Tree

A useful mental model is:

```text
                         /
                         |
          +--------------+--------------+
          |              |              |
        /home           /var           /data
                                         |
                                   /dev/sdb1
                                   ext4 filesystem
```

Linux does not create:

```text
C:\
D:\
E:\
```

for each disk.

Instead, filesystems become branches of the single directory tree.

For example:

```text
/
├── boot
├── etc
├── home
├── var
├── usr
└── data
    └── files
```

If `/data` is a separate filesystem, `/data` is simply the point where that filesystem is attached to the tree.

---

# Important Mounting Concepts

### Mounting Does Not Format a Disk

This:

```bash
mount /dev/sdb1 /mnt/data
```

does not create a filesystem.

The filesystem must already exist.

Formatting is performed separately:

```bash
mkfs.ext4 /dev/sdb1
```

Then it can be mounted:

```bash
mount /dev/sdb1 /mnt/data
```

### Unmounting Does Not Delete Data

This:

```bash
umount /mnt/data
```

only removes the filesystem from the directory tree.

It does not erase the filesystem.

### Changing the Mount Point Does Not Move Data

This:

```bash
mount /dev/sdb1 /mnt/data
```

followed later by:

```bash
mount /dev/sdb1 /backup
```

does not move any data.

It only changes where the filesystem is accessible.

### Mounting Over a Directory Hides Existing Files

If `/data` already contains files and another filesystem is mounted there, those files become temporarily invisible.

They reappear after the filesystem is unmounted.

# Practical Permanent-Mount Procedure

Suppose you have a new filesystem on:

```text
/dev/sdb1
```

and want it permanently mounted at:

```text
/data
```

### Create the Mount Point

```bash
sudo mkdir -p /data
```

### Identify the Filesystem

```bash
lsblk -f
```

or:

```bash
sudo blkid /dev/sdb1
```

Example:

```text
/dev/sdb1: UUID="7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab" TYPE="ext4"
```

### Add the Entry to `/etc/fstab`

```bash
sudo nano /etc/fstab
```

Add:

```text
UUID=7f6c3a1a-89d0-4f3c-bf5a-4c3f1ab4d2ab /data ext4 defaults 0 2
```

### Reload systemd Configuration

On systemd-based systems:

```bash
sudo systemctl daemon-reload
```

### Test the Configuration

```bash
sudo mount -a
```

If there is no error, verify:

```bash
findmnt /data
```

or:

```bash
df -h /data
```

### Reboot Test

For critical systems, it is good practice to verify that the filesystem also mounts correctly after reboot.

Before rebooting, make sure:

```bash
sudo mount -a
```

completes successfully.

# Mounting a Filesystem Temporarily Without Modifying `/etc/fstab`

For a temporary mount, simply use:

```bash
sudo mount /dev/sdb1 /mnt/data
```

No `/etc/fstab` modification is required.

After reboot, the manual mount will normally disappear.

This is useful for:

* Temporary storage
* Troubleshooting
* Recovery
* Accessing another disk
* Inspecting filesystems
* Mounting removable media
