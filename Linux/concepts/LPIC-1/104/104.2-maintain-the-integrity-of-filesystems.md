# Maintain the Integrity of Filesystems

Filesystem maintenance is the process of monitoring filesystem usage, checking filesystem integrity, and repairing filesystem problems when necessary.

The main tasks are:

* Monitor filesystem disk usage and free space.
* Monitor inode usage.
* Identify whether a block device contains a filesystem.
* Check and repair filesystem inconsistencies.
* Understand filesystem metadata such as inodes and superblocks.
* Maintain ext2/ext3/ext4 filesystem parameters.
* Use filesystem-specific maintenance tools such as `e2fsck`, `tune2fs`, `xfs_repair`, `xfs_db`, and `xfs_fsr`.

---

## Checking Whether a Partition Is Formatted

Suppose `lsblk` shows a block device and several partitions, and you want to use one of the partitions but do not know whether it already contains a filesystem.

There are several ways to determine this.

### Using `lsblk -f`

```bash
lsblk -f
```

This displays filesystem information such as:

* `FSTYPE` → filesystem type
* `FSVER` → filesystem version, when available
* `LABEL` → filesystem label
* `UUID` → filesystem UUID
* `FSAVAIL` → available filesystem space
* `FSUSE%` → filesystem usage percentage
* `MOUNTPOINTS` → current mount points

Example:

```text
NAME       FSTYPE     LABEL      UUID                                       MOUNTPOINTS
sda
├─sda1     ext4                  1a2b3c4d-5678-90ef-ghij-1234567890ab       /
├─sda2     swap                  87654321-4321-5678-1234-abcd1234efgh       [SWAP]
└─sda3
```

If `FSTYPE` is empty, Linux did not detect a filesystem signature on that partition.

This normally means that the partition is unformatted, but it is not absolute proof. The partition could contain something that `lsblk` does not recognize as a normal filesystem, such as encrypted data, RAID metadata, LVM metadata, or corrupted filesystem metadata.

A more detailed version is:

```bash
lsblk -o NAME,SIZE,FSTYPE,FSVER,LABEL,UUID,FSAVAIL,FSUSE%,MOUNTPOINTS
```

### Using `blkid`

```bash
sudo blkid /dev/sdg2
```

Example:

```text
/dev/sdg2: UUID="3f2b4c5d-1a2b-4c3d-9e8f-123456789abc" TYPE="ext4"
```

If `TYPE="ext4"` or `TYPE="xfs"` is shown, Linux has detected a filesystem.

If `blkid` produces no output, there may be no recognizable filesystem signature.

Again, no output does not necessarily prove that the partition is completely empty. It only means `blkid` did not identify a known filesystem signature.

### Using `file`

```bash
sudo file -s /dev/sdg2
```

Example:

```text
/dev/sdg2: Linux rev 1.0 ext4 filesystem data
```

This indicates that filesystem metadata was detected.

If the result is:

```text
/dev/sdg2: data
```

`file` could not identify a known filesystem or other recognizable structure.

### Using `wipefs`

`wipefs` is particularly useful when investigating what signatures exist on a block device:

```bash
sudo wipefs /dev/sdg2
```

It reports recognizable filesystem, RAID, partition-table, and other signatures without mounting or modifying the device.

To display detailed information:

```bash
sudo wipefs -n /dev/sdg2
```

`-n` means do not perform any changes.

**Important:** `wipefs` can also erase signatures when used with destructive options. Do not use those options unless you intentionally want to remove the signatures.

### Trying to Mount

You can technically test a filesystem by attempting to mount it:

```bash
sudo mount /dev/sdg2 /mnt/test
```

However, mounting should **not** be the first method used to determine whether a partition is formatted.

A failure such as:

```text
unknown filesystem type
```

does not necessarily mean the partition is simply unformatted. It could indicate:

* An unsupported filesystem.
* Corrupted filesystem metadata.
* Encryption.
* RAID/LVM metadata.
* Missing filesystem support.
* A filesystem that Linux cannot identify correctly.

Use `lsblk -f`, `blkid`, `file`, and `wipefs` first.

## Kernel Partition Table Cache

When a partition table is modified, there are two separate things to consider:

1. The partition table stored on the disk.
2. The partition table currently known by the running kernel.

For example, suppose `/dev/sdg8` exists and you delete it using:

```bash
sudo fdisk /dev/sdg
```

and then:

```text
d
8
w
```

The partition table on disk has been changed, but the running kernel may still have the previous partition information cached.

As a result, the old partition can sometimes continue to appear temporarily in commands such as:

```bash
lsblk
```

### Refreshing the Partition Table

You can ask the kernel to reread the partition table:

```bash
sudo partprobe /dev/sdg
```

or:

```bash
sudo partx -u /dev/sdg
```

`partprobe` asks the kernel to reread the partition table.

`partx` can also manipulate the kernel's view of partition mappings.

To remove a specific partition from the kernel's partition mappings:

```bash
sudo partx -d /dev/sdg8
```

If the partition is currently in use, mounted, or otherwise held open, the kernel may refuse to remove or reread it.

In such cases, stopping the processes using the device, unmounting it, or rebooting may be necessary.

### Important Distinction

Deleting a partition does **not** erase the data that used to be inside it.

It primarily removes the partition's entry from the partition table.

The old filesystem metadata and data may still physically exist on the disk until the space is overwritten.

Therefore:

```text
Delete partition
      ↓
Remove partition-table entry
      ↓
Partition is no longer normally referenced
      ↓
Old filesystem/data may still physically exist
```

This is also why filesystem signatures can sometimes still be discovered during forensic or recovery operations.

# Inodes

An **inode** is a filesystem data structure that stores metadata about a file, directory, or other filesystem object.

In Linux filesystems such as ext2/ext3/ext4 and XFS, every filesystem object is associated with an inode.

An inode generally contains information such as:

* File type.
* File permissions.
* Owner UID.
* Group GID.
* File size.
* Number of hard links.
* Access time (`atime`).
* Modification time (`mtime`).
* Change time (`ctime`).
* Filesystem-specific timestamps or metadata where supported.
* Information needed to locate the file's data blocks.

The inode **does not normally contain the filename**.

Instead, directories contain directory entries that associate filenames with inode numbers:

```text
directory entry
      │
      ├── filename → inode number
      │
      └── inode
           │
           ├── permissions
           ├── owner
           ├── timestamps
           ├── size
           └── data block information
```

### Example

Suppose:

```bash
ls -i
```

produces:

```text
131082 notes.txt
131083 data.csv
```

The inode number of `notes.txt` is `131082`.

### Why File Names Are Not Stored in the Inode

A directory essentially maps:

```text
filename → inode number
```

The inode then describes the object.

This design allows multiple directory entries to refer to the same inode.

This is how **hard links** work.

For example:

```text
file1.txt ─┐
           ├──> inode 12345 ──> file data
file2.txt ─┘
```

Both names refer to the same inode and therefore the same underlying file data.

### Deleting a File

When you run:

```bash
rm file.txt
```

Linux removes the directory entry referring to the inode.

If no other hard links refer to that inode and no process still has the file open, the filesystem can reclaim the inode and its data blocks.

This explains why a deleted file can continue consuming disk space if a running process still has the file open.

---

## Inode Exhaustion

A filesystem can run out of **inodes before it runs out of disk space**.

This commonly happens when a filesystem contains a very large number of small files.

For example:

```text
Disk space:     80% used
Inodes:        100% used
```

The filesystem may still have free disk blocks, but it cannot create additional files because there are no free inodes.

Check inode usage with:

```bash
df -i
```

Example:

```text
Filesystem      Inodes   IUsed   IFree IUse% Mounted on
/dev/sda1      6553600  6000000 553600   92% /
```

Useful commands:

- **`ls -i file.txt`** → Display the inode number.
- **`stat file.txt`** → Display detailed inode and file metadata.
- **`df -i`** → Display inode usage for mounted filesystems.

# Monitoring Filesystem Space

Two commands are especially important:

```text
df → filesystem-level usage
du → file/directory-level usage
```

They answer different questions.

---

## `df` Command

`df` reports the amount of space used and available on filesystems.

Basic usage:

```bash
df
```

Example:

```text
Filesystem      1K-blocks     Used Available Use% Mounted on
/dev/sda1        20511356  5243180  14234520  27% /
tmpfs             1023456        0   1023456   0% /dev/shm
```

### Useful Options

- **`df -h`** → Human-readable output.
- **`df -T`** → Display the filesystem type.
- **`df -i`** → Display inode usage instead of block usage.
- **`df -t ext4`** → Show only filesystems of the specified type.
- **`df /home/user`** → Show information about the filesystem containing `/home/user`.

### What `df` Measures

`df` operates at the **filesystem level**.

It obtains usage information from the filesystem rather than walking through individual directories.

Therefore, it accounts for filesystem-level allocations such as:

* File data.
* Filesystem metadata.
* Journals.
* Reserved blocks.
* Some snapshot/CoW overhead.
* Space consumed by deleted-but-still-open files.

This makes `df` the right tool for answering:

> "How much free space does this filesystem actually have?"

---

# `du` Command

`du` reports disk usage associated with files and directories in a directory tree.

Basic syntax:

```bash
du [options] [path...]
```

Without a path:

```bash
du
```

uses the current directory.

Without options, it recursively reports usage for directories.

### Human-Readable Output

```bash
du -h /home/user
```

Example:

```text
4.0K    /home/user/docs/reports
20K     /home/user/docs
100M    /home/user/videos
200M    /home/user
```

### Summary

```bash
du -sh /home/user
```

`-s` means summarize.

Instead of showing every subdirectory, it displays only the total:

```text
200M    /home/user
```

### Limit Directory Depth

```bash
du -h --max-depth=1 /var
```

This displays `/var` and its immediate subdirectories.

### Specify Units

```bash
du -k /var
```

→ Kilobytes.

```bash
du -m /var
```

→ Megabytes.

### Find Large Directories

```bash
du -h --max-depth=1 /var | sort -h
```

This is useful for finding which directories consume the most space.

### Compare Apparent and Actual Usage

For a sparse file:

```bash
ls -lh big_sparse.img
du -h big_sparse.img
```

`ls -lh` shows the file's **logical size**.

`du` normally reports the amount of filesystem space actually allocated to the file.

To display the logical/apparent size with `du`:

```bash
du -h --apparent-size big_sparse.img
```

---

# `df` vs `du`

The distinction is extremely important.

| Feature                | `df`                                 | `du`                                |
| ---------------------- | ------------------------------------ | ----------------------------------- |
| Scope                  | Entire filesystem                    | Directory/file tree                 |
| Measures               | Filesystem allocation                | Space used by files it can traverse |
| Source                 | Filesystem metadata                  | Directory tree                      |
| Deleted open files     | Usually included                     | Not visible by pathname             |
| Filesystem metadata    | Included                             | Generally not included              |
| Reserved blocks        | Reflected in filesystem availability | Not treated as directory data       |
| Snapshots/CoW overhead | Can be reflected                     | Usually not represented directly    |
| Sparse files           | Filesystem allocation                | Allocated space by default          |
| Main use               | Check filesystem capacity            | Find what is consuming space        |

### Why `df` and `du` Can Disagree

A common troubleshooting situation is:

```text
df → filesystem is 90% full
du → visible files appear to use only 60%
```

Several things can cause this.

- ### Deleted but Open Files

  A process can keep a deleted file open.
  
  Example:
  
  ```text
  Application
      │
      └── opens /var/log/app.log
               │
               └── process keeps file open
  
  rm /var/log/app.log
      │
      └── directory entry disappears
  ```
  
  The file is no longer visible to `du`, but its blocks remain allocated until the process closes the file.
  
  Find such files with:
  
  ```bash
  sudo lsof +L1
  ```

  ---

- ### Reserved Blocks

  ext2/ext3/ext4 can reserve filesystem blocks for privileged processes, helping the system continue operating when the filesystem becomes nearly full.
  
  The default reserved percentage is commonly 5%, although this can be changed.

  ---
  
- ### Filesystem Metadata and Journals

  A filesystem consumes space for:
  
  * Inodes.
  * Allocation metadata.
  * Journals.
  * Superblocks.
  * Other filesystem structures.
  
  `du` is primarily concerned with files visible through the directory tree, whereas `df` sees filesystem-level allocation.

  ---

- ### Sparse Files

  A sparse file can have:
  
  ```text
  Logical size:     100 GB
  Actual allocated: 1 GB
  ```
  
  `du` normally reports allocated space, while `ls -lh` reports logical size.

- ### Different Scope

  Consider:
  
  ```bash
  du -sh /var
  df -h /var
  ```
  
  `du` examines the `/var` directory tree.
  
  `df` reports the entire filesystem containing `/var`.
  
  To make the comparison more meaningful:
  
  ```bash
  df -h /var
  sudo du -xsh /var
  ```
  
  `-x` prevents `du` from crossing into other mounted filesystems.

  ---

- ### Permissions

  If `du` cannot read some directories, it may undercount their usage.
  
  Use appropriate privileges when necessary:
  
  ```bash
  sudo du -xsh /var
  ```

# Checking and Repairing Filesystems

## `fsck` Command

`fsck` stands for **File System Consistency Check**.

It is used to check and, when requested, repair filesystem inconsistencies.

Typical causes of filesystem inconsistencies include:

* Unexpected shutdown.
* Power failure.
* Kernel crashes.
* Hardware problems.
* Storage errors.
* Filesystem bugs.

Basic syntax:

```bash
sudo fsck /dev/sda1
```

### Important Warning

Do **not** normally run a filesystem repair operation on a mounted, writable filesystem.

For example:

```bash
sudo fsck /dev/sda1
```

should not be used against `/dev/sda1` while `/dev/sda1` is actively mounted and writable.

For the root filesystem, maintenance is commonly performed from:

* Rescue mode.
* Emergency mode.
* A live environment.
* Another boot environment.

Some filesystem-specific tools have their own rules, so always check the filesystem-specific documentation.

### Common `fsck` Options

- **`-A`** → Check filesystems listed in `/etc/fstab`, subject to their filesystem-check configuration.
- **`-r`** → Interactive repair: ask before repairing problems.
- **`-y`** → Automatically answer yes to repair questions.
- **`-n`** → Do not make repairs; answer no to repair questions. Useful for performing a non-destructive check.
- **`-f`** →  Force a check even if the filesystem appears clean.
- **`-C`** → Display progress information when supported.

Examples:

- **`sudo fsck -n /dev/sdb1`** → Check without making repairs.
- **`sudo fsck -f /dev/sdb1`** → Force a check.
- **`sudo fsck -y /dev/sdb1`** → Automatically approve repairs.

### Checking All Configured Filesystems

```bash
sudo fsck -A
```

The exact behavior depends on the `/etc/fstab` configuration and filesystem check settings.

For example:

- **`sudo fsck -A -n`** → Check without performing repairs.
- **`sudo fsck -A -y`** → Automatically approve repairs.

### `fsck` Is a Front-End

`fsck` itself is a dispatcher/front-end.

It determines the appropriate filesystem-specific checker and invokes it.

For example:

```text
fsck
 │
 ├── ext2/ext3/ext4 → fsck.ext4 → e2fsck
 │
 ├── XFS            → filesystem-specific XFS handling
 │
 ├── FAT            → fsck.fat
 │
 └── other filesystems → corresponding checker
```

Therefore:

```bash
sudo fsck /dev/sdb1
```

may ultimately invoke something like:

```bash
fsck.ext4 /dev/sdb1
```

for an ext4 filesystem.

Filesystem-specific options should not be assumed to be identical across all `fsck` implementations.

---

# `e2fsck` Command

`e2fsck` is the filesystem checker for the ext2/ext3/ext4 family.

For example:

```bash
sudo e2fsck /dev/sdb1
```

The relationship is:

```text
fsck
  ↓
fsck.ext4
  ↓
e2fsck
```

`e2fsck` performs the actual consistency checking and repair of **`ext`** filesystems.

Common examples:

- **`sudo e2fsck -n /dev/sdb1`** → Check without making changes.
- **`sudo e2fsck -f /dev/sdb1`** → Force a full check.
- **`sudo e2fsck -y /dev/sdb1`** → Automatically answer yes to repair questions.

### Important

`e2fsck` should normally be run on an **unmounted** filesystem.

---

# `mke2fs` Command

`mke2fs` is the low-level utility used to create ext2/ext3/ext4 filesystems.

For example:

```bash
sudo mke2fs -t ext4 /dev/sdb1
```

This creates an ext4 filesystem.

Common wrappers include:

```bash
mkfs.ext2
mkfs.ext3
mkfs.ext4
```

These ultimately use the ext filesystem creation machinery provided by `mke2fs`.

For example:

```bash
sudo mkfs.ext4 /dev/sdb1
```

is the normal convenient way to create an ext4 filesystem.

### Important Distinction

```text
mke2fs → creates an ext filesystem
e2fsck → checks/repairs an ext filesystem
tune2fs → modifies parameters of an existing ext filesystem
```

Formatting a partition with `mkfs`/`mke2fs` destroys the filesystem structures previously stored there.

---

# `tune2fs` Command

`tune2fs` is used to view and modify tunable parameters of ext2/ext3/ext4 filesystems without recreating the filesystem.

Basic syntax:

```bash
sudo tune2fs [options] /dev/sdXN
```

### Display Filesystem Parameters

```bash
sudo tune2fs -l /dev/sdb1
```

This displays information such as:

* Filesystem UUID.
* Filesystem label.
* Filesystem features.
* Block size.
* Inode information.
* Mount count.
* Maximum mount count.
* Last checked time.
* Check interval.
* Reserved blocks.
* Filesystem state.

- ### Change Filesystem Label

  ```bash
  sudo tune2fs -L DATA /dev/sdb1
  ```
  
- ### Change UUID

  ```bash
  sudo tune2fs -U random /dev/sdb1
  ```
  
  Be careful when changing UUIDs because `/etc/fstab`, boot configuration, RAID/LVM configuration, or other applications may reference the old UUID.

- ### Reserved Blocks

  ```bash
  sudo tune2fs -m 2 /dev/sdb1
  ```
  
  This changes the percentage of blocks reserved for privileged processes to 2%.
  
  The commonly used default on ext filesystems is 5%, although the actual value may differ.

- ### Maximum Mount Count

  ```bash
  sudo tune2fs -c 20 /dev/sdb1
  ```
  
  This configures ext filesystem checking based on the number of mounts.

  The filesystem's mount count is tracked, and when the configured threshold is reached, the filesystem is scheduled for an `e2fsck` check at the next appropriate opportunity.
  
  Disable mount-count-based checking:
  
  ```bash
  sudo tune2fs -c 0 /dev/sdb1
  ```

- ### Time-Based Checking

  ```bash
  sudo tune2fs -i 6m /dev/sdb1
  ```
  
  This sets a maximum interval of six months between filesystem checks.
  
  Units include:
  
  ```text
  d → days
  w → weeks
  m → months
  ```
  
  Disable time-based checking:
  
  ```bash
  sudo tune2fs -i 0 /dev/sdb1
  ```

### Mount Count and Time Interval

The two mechanisms provide independent conditions for scheduling filesystem checks:

- **`-c`** → check based on number of mounts
- **`-i`** → check based on elapsed time

Whichever configured condition requires a check first can cause the filesystem to be checked.

Modern Linux systems may disable or alter periodic filesystem checking policies, so do not assume that every ext filesystem has the same default `-c` or `-i` behavior.

# Superblock

A **superblock** is filesystem metadata describing the filesystem as a whole.

It is not an inode.

For an ext filesystem, the superblock contains information such as:

* Filesystem size.
* Number of blocks.
* Number of inodes.
* Block size.
* Free block count.
* Free inode count.
* Filesystem state.
* Mount count.
* Maximum mount count.
* UUID.
* Filesystem features.
* Journal information.
* Other filesystem parameters.

Conceptually:

```text
Filesystem
│
├── Superblock
│     └── Information about the filesystem as a whole
│
├── Inode structures
│     └── Metadata about individual filesystem objects
│
└── Data blocks
      └── File contents
```

### Superblock vs Inode

| Feature                     | Superblock                              | Inode                                    |
| --------------------------- | --------------------------------------- | ---------------------------------------- |
| Describes                   | Entire filesystem                       | Individual filesystem object             |
| Contains filename           | No                                      | No                                       |
| Contains permissions        | No, not per-file                        | Yes                                      |
| Contains filesystem size    | Yes                                     | No                                       |
| Contains UUID               | Yes                                     | No                                       |
| Contains file size          | No                                      | Yes                                      |
| Contains file data location | No                                      | Yes                                      |
| Backup copies               | Ext filesystems have backup superblocks | Inode tables exist throughout filesystem |

The superblock is therefore a central piece of filesystem metadata.

# Journaling

A journaling filesystem keeps a record of certain filesystem changes in a **journal** before committing those changes to the main filesystem structures.

The journal helps the filesystem recover from interruptions such as:

* Power failure.
* System crash.
* Kernel panic.
* Unexpected reboot.

Conceptually:

```text
Application requests filesystem change
  ↓
Filesystem records required metadata changes
  ↓
Journal
  ↓
Filesystem applies the changes
```

If the system crashes during the operation, the filesystem can use the journal during recovery to bring its metadata back to a consistent state.

### Important Point

Journaling does **not** mean that your files are automatically protected from all corruption or hardware failure.

It primarily improves filesystem consistency and reduces the amount of filesystem metadata recovery required after an interrupted operation.

For example:

- **ext2**  → no journal
- **ext3**  → journaling
- **ext4**  → journaling
- **XFS**   → journaling

Other filesystems have their own consistency mechanisms.

# XFS Filesystem Maintenance

XFS is a high-performance journaling filesystem commonly used on servers and large filesystems.

The `xfsprogs` package provides many XFS administration utilities.

---

## `xfs_info`

Displays information about an XFS filesystem.

Example:

```bash
sudo xfs_info /dev/sda2
```

For a mounted filesystem, the mount point can also be used:

```bash
sudo xfs_info /data
```

It can display information such as:

* Block size.
* Allocation groups.
* Filesystem geometry.
* Inode configuration.
* Features.

---

## `xfs_growfs`

`xfs_growfs` increases the size of an existing XFS filesystem.

XFS can be **grown**, but it cannot be shrunk in place.

The underlying block device must first be expanded.

Example:

```text
20 GB LV
   ↓
lvextend
   ↓
30 GB LV
   ↓
xfs_growfs
   ↓
30 GB XFS filesystem
```

For example:

```bash
sudo lvextend -L +10G /dev/vg0/lv_data
sudo xfs_growfs /data
```

The XFS filesystem must be mounted when `xfs_growfs` is normally used.

### Important

Extending the underlying block device does **not automatically mean the filesystem has grown**.

You may need:

```text
Expand block device
       ↓
Expand filesystem
```

The exact filesystem command depends on the filesystem type.

---

## `xfs_admin`

Used to modify certain XFS filesystem parameters, such as the label and UUID.

Change the label:

```bash
sudo xfs_admin -L DATA /dev/sdb1
```

Generate a new UUID:

```bash
sudo xfs_admin -U generate /dev/sdb1
```

Changing filesystem identifiers can affect `/etc/fstab` and other configuration that references the old UUID or label.

---

## `xfs_repair`

`xfs_repair` is used to check and repair XFS filesystem metadata.

Example:

```bash
sudo xfs_repair /dev/sdb1
```

It is conceptually similar to `e2fsck` for ext filesystems:

```text
ext2/ext3/ext4 → e2fsck
XFS             → xfs_repair
```

The filesystem should normally be **unmounted** before repair.

For a mounted filesystem, first arrange for the filesystem to be unmounted or perform the repair from an appropriate rescue environment.

---

## `xfs_db`

`xfs_db` is a low-level XFS filesystem inspection and debugging utility.

It can be used to inspect internal structures such as:

* Superblocks.
* Inodes.
* Allocation groups.
* B-trees.
* Filesystem geometry.
* Block mappings.

Read-only mode:

```bash
sudo xfs_db -r /dev/sdb1
```

The `-r` option is important because it prevents modification of filesystem metadata.

Inside `xfs_db`, commands can be used to inspect filesystem structures.

For example:

```text
sb 0
```

loads superblock 0, and:

```text
print
```

displays information about the current structure.

### Important Warning

`xfs_db` is an advanced low-level tool.

Do not modify XFS metadata manually unless you fully understand the structure and have a recovery plan.

For normal corruption repair, use:

```bash
xfs_repair
```

rather than manually modifying filesystem metadata with `xfs_db`.

---

## `xfs_fsr`

`xfs_fsr` is the XFS filesystem reorganizer/defragmentation utility.

It reorganizes fragmented file data to improve storage layout.

Conceptually:

```text
Fragmented file
     ↓
xfs_fsr
     ↓
More contiguous file layout
```

It is a **performance/fragmentation** tool, not a filesystem corruption repair tool.

Do not confuse:

```text
xfs_repair → filesystem integrity
xfs_db     → low-level inspection/debugging
xfs_fsr    → defragmentation/reorganization
```

Defragmentation is generally less important on SSDs than on traditional HDDs because SSDs do not have mechanical seek latency.

---

# Useful ext Filesystem Tools

Several additional tools are useful when maintaining ext2/ext3/ext4 filesystems.

## `dumpe2fs`

Displays detailed ext filesystem information, including the superblock and block-group information.

Example:

```bash
sudo dumpe2fs /dev/sdb1
```

It is useful when you need more detailed filesystem metadata than `tune2fs -l` provides.

---

## `debugfs`

`debugfs` is an interactive low-level debugger for ext2/ext3/ext4 filesystems.

Example:

```bash
sudo debugfs /dev/sdb1
```

It can inspect filesystem structures and, depending on the operation, modify them.

Because it operates at a very low level, it should not be used casually on production filesystems.

---

## `resize2fs`

`resize2fs` is used to resize ext2/ext3/ext4 filesystems.

Example:

```bash
sudo resize2fs /dev/sdb1
```

It is commonly used after expanding an underlying partition or logical volume.

For example:

```text
Expand partition/LV
       ↓
resize2fs
       ↓
Expand ext filesystem
```

The exact procedure depends on whether the filesystem is mounted and whether the underlying device is a partition, LVM logical volume, or another block device.

Unlike XFS, ext4 supports shrinking, although shrinking requires the filesystem to be reduced carefully and normally while unmounted.

# Filesystem Integrity vs Disk Health

Filesystem integrity and physical disk health are related but different concepts.

### Filesystem Integrity

Questions such as:

> "Are the filesystem metadata and structures internally consistent?"

Tools include:

```text
fsck
e2fsck
xfs_repair
```

### Disk/Device Health

Questions such as:

> "Is the physical storage device reporting hardware problems?"

For physical disks, tools such as `smartctl` can be used to inspect SMART information.

Example:

```bash
sudo smartctl -a /dev/sda
```

This is especially useful when filesystem corruption repeatedly occurs.

A filesystem repair can fix filesystem metadata, but it **cannot repair a failing disk**.

For example:

```text
Hardware problem
      ↓
Bad/corrupt data
      ↓
Filesystem becomes inconsistent
      ↓
e2fsck repairs filesystem metadata
      ↓
Hardware problem still exists
      ↓
Corruption may happen again
```

Therefore, repeated filesystem corruption should also trigger investigation of:

* Disk health.
* SMART errors.
* Storage controller errors.
* Kernel logs.
* RAID status.
* Cables/backplane.
* Power problems.
* Virtual storage infrastructure.

# Common Filesystem Maintenance Workflow

When a filesystem appears to have a problem, a practical workflow is:

```text
Identify the filesystem
        ↓
lsblk -f
        ↓
Check filesystem usage
        ↓
df -h
df -i
        ↓
Investigate large directories/files
        ↓
du -xsh
        ↓
Check logs/kernel messages
        ↓
Determine filesystem type
        ↓
Choose filesystem-specific checker
        ↓
Unmount filesystem
        ↓
Run integrity check
        ↓
Repair if necessary
        ↓
Mount filesystem again
        ↓
Verify filesystem and application operation
```

For an ext4 filesystem:

```bash
lsblk -f
df -h
df -i
sudo umount /dev/sdb1
sudo e2fsck -f /dev/sdb1
```

For XFS:

```bash
lsblk -f
df -h
df -i
sudo umount /dev/sdb1
sudo xfs_repair /dev/sdb1
```

Do not blindly copy these commands into production. Always identify the correct device first.

# Important Distinctions

These concepts are easy to confuse.

### Partition vs Filesystem

A partition is a region of a disk defined by a partition table.

A filesystem is a data structure created inside a block device.

```text
Disk
 │
 ├── Partition 1
 │      └── ext4 filesystem
 │
 ├── Partition 2
 │      └── XFS filesystem
 │
 └── Partition 3
        └── LVM physical volume
```

A partition does not automatically contain a filesystem.

---

### Filesystem vs Mount Point

A filesystem is the storage structure.

A mount point is a directory where Linux makes that filesystem accessible.

For example:

```bash
sudo mount /dev/sdb1 /data
```

Here:

```text
/dev/sdb1 → filesystem
/data     → mount point
```

---

### Inode vs Superblock

```text
Superblock
→ describes the filesystem as a whole.

Inode
→ describes one filesystem object.
```

---

### `df` vs `du`

```text
df
→ "How much space is used/free on this filesystem?"

du
→ "Which files/directories are consuming space?"
```

---

### `fsck` vs `e2fsck`

```text
fsck
→ general filesystem-check dispatcher.

e2fsck
→ actual ext2/ext3/ext4 filesystem checker.
```

---

### `mke2fs` vs `e2fsck`

```text
mke2fs
→ create an ext filesystem.

e2fsck
→ check/repair an existing ext filesystem.
```

---

### `tune2fs` vs `mke2fs`

```text
mke2fs
→ create a new filesystem.

tune2fs
→ modify parameters of an existing ext filesystem.
```

---

### `xfs_repair` vs `xfs_db`

```text
xfs_repair
→ repair XFS filesystem problems.

xfs_db
→ inspect/debug internal XFS structures.
```

---

### `xfs_repair` vs `xfs_fsr`

```text
xfs_repair
→ integrity/corruption.

xfs_fsr
→ fragmentation/performance.
```

```bash
# Identify filesystems
```

# Practical Troubleshooting Examples

## Filesystem Is Full

Start with:

```bash
df -h
```

Then identify which filesystem is full.

If `/` is full:

```bash
sudo du -xhd1 / | sort -h
```

Then investigate the largest directory.

For example:

```bash
sudo du -xhd1 /var | sort -h
```

If `df` says the filesystem is nearly full but `du` cannot account for the space:

```bash
sudo lsof +L1
```

Look for deleted-but-open files.

---

## Filesystem Has No Free Inodes

Check:

```bash
df -i
```

If `IUse%` is 100%, find directories containing huge numbers of small files.

For example:

```bash
sudo find /var -xdev -type f | wc -l
```

Then investigate directories containing excessive numbers of files.

The problem is not necessarily insufficient disk capacity; it is **inode exhaustion**.

---

## Filesystem Will Not Mount

First identify what is actually on the device:

```bash
lsblk -f
sudo blkid /dev/sdb1
sudo file -s /dev/sdb1
sudo wipefs /dev/sdb1
```

Then check kernel messages:

```bash
dmesg | tail -50
```

or, on systems using systemd:

```bash
journalctl -k -n 50
```

Possible causes include:

* Wrong filesystem type.
* Filesystem corruption.
* Encryption.
* LVM.
* RAID.
* Missing filesystem support.
* Hardware/storage problems.

Do not immediately assume that the partition is simply unformatted.

---

## Filesystem Corruption

For an ext4 filesystem:

```bash
sudo umount /dev/sdb1
sudo e2fsck -f /dev/sdb1
```

For XFS:

```bash
sudo umount /dev/sdb1
sudo xfs_repair /dev/sdb1
```

Always verify the filesystem type before choosing the repair tool.

# Key Points to Remember

* A **partition** is not the same thing as a **filesystem**.
* `lsblk -f` is one of the quickest ways to identify filesystem types.
* `blkid` identifies filesystem signatures and UUIDs.
* `wipefs` is useful for investigating signatures on block devices.
* An **inode stores metadata about a filesystem object**, not its filename.
* Directory entries map filenames to inode numbers.
* A filesystem can run out of **inodes before disk space**.
* `df` reports filesystem-level space usage.
* `du` reports space associated with files/directories it can traverse.
* `df` and `du` can disagree, especially because of deleted-but-open files, filesystem metadata, reserved space, snapshots, sparse files, and different scopes.
* `fsck` is a front-end that dispatches to filesystem-specific checkers.
* `e2fsck` checks and repairs ext2/ext3/ext4.
* `mke2fs` creates ext filesystems.
* `tune2fs` modifies tunable parameters of existing ext2/ext3/ext4 filesystems.
* A **superblock describes the filesystem as a whole**.
* An **inode describes an individual filesystem object**.
* Journaling improves filesystem consistency and recovery after interrupted operations; it is not a replacement for backups.
* `xfs_repair` repairs XFS filesystem problems.
* `xfs_db` is a low-level XFS inspection/debugging tool.
* `xfs_fsr` is for XFS defragmentation/reorganization, not corruption repair.
* XFS can be grown but cannot be shrunk in place.
* Filesystem corruption can be caused by underlying hardware problems, so repeated corruption should also lead to hardware/storage investigation.
* **Never blindly run filesystem repair commands against a mounted production filesystem.**
