# Permissions

Linux permissions control who can access files and directories and what they are allowed to do with them.

Unlike Windows, Linux does not have one universal permission mechanism tied to a single filesystem. Traditional Linux permissions are implemented by the filesystem and exposed through the Linux VFS. Filesystems such as ext4 and XFS support the standard Unix permission model, while filesystems such as FAT/exFAT do not natively store Unix ownership and permission metadata in the same way.

When such filesystems are mounted on Linux, permissions can instead be assigned through mount options.

## Permissions vs Privileges

These two concepts are related but different.

**Permissions** control access to files and directories.

Examples:

- Read a file
- Modify a file
- Execute a file
- Enter a directory
- Create or delete files inside a directory

**Privileges** refer to the ability to perform system-level or administrative operations.

Examples:

- Installing software
- Managing users
- Changing system configuration
- Mounting filesystems
- Starting/stopping services
- Shutting down the system

The `root` user traditionally has broad administrative privileges, although modern Linux can also divide privileged operations using mechanisms such as Linux capabilities.

In short:

> **Permissions → control access to filesystem objects.**  
> **Privileges → control access to system-level operations.**

# Basic Linux Permissions

Linux has three basic permissions:

| Permission | File | Directory |
|---|---|---|
| `r` (read) | Read the file's contents | List directory entries |
| `w` (write) | Modify/truncate the file | Create, delete, or rename entries |
| `x` (execute) | Execute the file as a program | Traverse/enter the directory and access objects inside |

Directory permissions are particularly important.

### Read permission on a directory

`r` allows you to list the names of entries inside the directory.

```bash
ls directory/
```

However, **`r`** alone is not enough to access the files.

### Execute permission on a directory

**`x`** means traverse the directory.

It allows you to:

```bash
cd directory/
```

and access objects inside it when you know their names.

For example, a user may be unable to run:

```bash
ls directory/
```

without **`r`**, but may still be able to access:

```bash
cat directory/file.txt
```

if they have **`x`** permission on the directory and appropriate permissions on `file.txt`.

### Write permission on a directory

**`w`** allows modification of the directory's entries.

When combined with **`x`**, it allows users to:

- Create files
- Delete files
- Rename files
- Create directories

Therefore:

To create, delete, or rename entries in a directory, you normally need **`w + x`** on the directory.

**Important distinction when deleting a file**

Deleting a file depends primarily on the permissions of its parent directory, not the permissions of the file itself.

For example, a user may be unable to write to `file.txt`, but still be able to delete it if they have **`w+x`** on the containing directory.

This is why directories such as `/tmp` require special protection using the **sticky bit**.

## Permission Classes

Every Linux file has permissions for three classes of users:

- **Owner (user)**
- **Group**
- **Others**

For example:

```bash
rwxr-x--x
```

The permission string is divided into three groups:

```
rwx  |  r-x  |  --x
 ↓       ↓       ↓
user   group   others
```

Therefore:

- Owner → **`rwx`**
- Group → **`r-x`**
- Others → **`--x`**

## Numeric Permissions

Each basic permission has a numeric value:

- **`r`** = 4
- **`w`** = 2
- **`x`** = 1
- **`-`** = 0

These values are powers of two:

- **`r`** = 2² = 4
- **`w`** = 2¹ = 2
- **`x`** = 2⁰ = 1

For example:

```
rwxr-x--x
```

becomes:

- Owner:  **`rwx`** = 4 + 2 + 1 = 7
- Group:  **`r-x`** = 4 + 0 + 1 = 5
- Others: **`--x`** = 0 + 0 + 1 = 1

Therefore:

`rwxr-x--x` = 751

**Common examples:**

| Numeric | Symbolic | Meaning |
| --- | --- | --- |
| 777 | rwxrwxrwx | Everyone has full permissions |
| 755 | rwxr-xr-x | Owner full, others read/execute |
| 750 | rwxr-x--- | Owner full, group read/execute |
| 700 | rwx------ | Owner only |
| 644 | rw-r--r-- | Owner read/write, others read |
| 640 | rw-r----- | Owner read/write, group read |
| 600 | rw------- | Owner read/write |
| 400 | r-------- | Owner read-only |

## Viewing Permissions

The most common command is:

```bash
ls -l
```

Example:

```bash
-rwxr-x--- 1 amir developers 1234 Oct  5 10:00 script.sh
```

The first character represents the file type:

- **`-`** → regular file
- **`d`** → directory
- **`l`** → symbolic link
- **`c`** → character device
- **`b`** → block device
- **`p`** → named pipe
- **`s`** → socket

The next nine characters are the basic permissions:

```bash
rwx | r-x | ---
```

The output also shows:

- Number of hard links
- Owner
- Group
- Size
- Modification time
- Name

To inspect the directory itself rather than its contents:

```bash
ls -ld directory/
```

For example:

**`ls -ld /tmp`**

Whereas:

**`ls -l /tmp`** → lists the objects inside /tmp.

> Using **`ls -la directory/`**, shows hidden objects as well.

## stat command

The `stat` command displays detailed metadata about a file or directory.

```bash
stat file.txt
```

It can show:

- File type
- Permissions
- Owner
- Group
- Size
- Inode number
- Access time (**`atime`**)
- Modification time (**`mtime`**)
- Change time (**`ctime`**)

> The Access line contains the permission information and other metadata.

## chmod command

The `chmod` command changes file and directory permissions.

Basic syntax:

```bash
chmod [options] mode file
```

There are two major ways to specify permissions:

- Symbolic mode
- Numeric mode
- chmod: Symbolic Mode

Symbolic permissions use:

- **`u`** = user/owner
- **`g`** = group
- **`o`** = others
- **`a`** = all

Operators:

- `+` → add permission
- `-` → remove permission
- `=` → set exact permissions

Examples:

- `chmod u+r file` → Add read permission for the owner.
- `chmod g-rw file` → Remove read and write permissions from the group.
- `chmod o+x file` → Add execute permission for others.
- `chmod a+x file` → Add execute permission for everyone.
- `chmod u=rwx file` → Set the owner's permissions exactly to rwx.

Multiple changes can be specified together:

```bash
chmod u+rw,g+r,o-r file
```

### chmod: Numeric Mode

Numeric mode directly specifies the permission values.

Example:

- `chmod 755 script.sh` → produces `rwxr-xr-x`
- `chmod 640 file.txt` → produces `rw-r-----`

> Numeric permissions can also include special permissions such as **SUID**, **SGID**, and the sticky bit.

### Recursive chmod

The **`-R`** option applies permissions recursively.

```bash
chmod -R 755 directory/
```

This changes permissions on the directory and everything below it.

## Ownership

Every Linux filesystem object has an owner and a group.

Example:

```bash
-rw-r----- 1 user1 developers 1200 file.txt
```

Here:

- Owner = `user1`
- Group = `developers`

Ownership and permissions are separate concepts.

## chown command

`chown` changes the owner and optionally the group.

Basic syntax:

```bash
chown [options] owner[:group] file
```

Examples:

- `chown user1 file.txt` → Change the owner to user1.
- `chown user1:group1 file.txt` → Change both owner and group.
- `chown :group1 file.txt` → Change only the group.
- `chown -R user1:group1 directory/` → Recursively change owner and group.
- `chown --reference=<otherfile file>` → can copy the ownership information from another file.

## chgrp command

`chgrp` changes the group ownership of a file or directory.

```bash
chgrp group1 file.txt
```

For example:

- `chgrp developers project.txt` → changes the file's group to developers.
- `chgrp -R developers project/` → Recursive use

### Who Can Change Ownership?

A normal user cannot arbitrarily transfer ownership of a file to another user.

Typically, changing the owner requires **root privileges** or an appropriate administrative capability.

For example:

`chown user2 file.txt` will normally fail for an ordinary user who does not have the required privilege.

A user can generally change the group of a file only to a group they are allowed to use.

## Permission Matching

Linux does not combine permissions from the owner, group, and others categories.

A process is evaluated against exactly one of these classes:

- Owner
- Group
- Others

1. The owner class is checked first.
2. If the process is not the owner, Linux checks whether it belongs to the file's group.
3. If it matches the group class, the group permissions are used.
4. It does not then fall back to the others permissions.

Example:

```
-rwxr--rw- user2:dev file.txt
```

Suppose user1 belongs to both:

- `dev`
- `test`

The file is owned by `user2:dev` The permissions are:

- Owner  = `rwx`
- Group  = `r--`
- Others = `rw-`

`user1` is not the owner but is a member of `dev`, so the group permissions apply `r--`.

The user cannot write to the file, even though the others permissions contain `rw-`.

There is no permission merging such as:

group `r--` + others `rw-`

## Permission Checking on Paths

Linux checks permissions on every directory in a path.

For example:

```
/home/test/project/file.txt
```

To access `file.txt`, the process needs appropriate **execute (`x`)** permission on the directories it must traverse:

```
/
└── home/
    └── test/
        └── project/
            └── file.txt
```

The permissions of the file itself are not enough.

For example, even if:

```
file.txt = rw-------
```

you still need `x` permission on the parent directories to reach it.

This is why directory `x` permission is more accurately described as traverse/search permission rather than simply "enter permission."

## File Permissions vs Directory Permissions

The same permission has different meanings depending on the object.

| Permission | Regular File | Directory |
| --- | --- | --- |
| **`r`** | Read contents | List directory entries |
| **`w`** | Modify/truncate contents | Create/delete/rename entries |
| **`x`** | Execute program | Traverse/search directory |

For example:

```
Directory: rwx
```

means:

- **`r`** → list names
- **`w`** → modify directory entries
- **`x`** → traverse the directory

## Filesystem Metadata and Inodes

Linux filesystems such as ext4 and XFS use filesystem metadata structures to describe files.

An inode contains metadata such as:

- File type
- Owner UID
- Group GID
- Permissions
- File size
- Timestamps
- Link count
- References to the file's data blocks

The inode does not normally contain the filename.

Directory entries associate names with inode numbers.

Conceptually:

```
Directory entry
      |
      | filename → inode number
      v
   Inode
      |
      | metadata + data block references
      v
  File data
```

For example:

`/home/amir/test.txt` is resolved through the directory hierarchy.

> The filesystem does not normally store `/home/amir/test.txt` as one complete pathname inside the inode. Instead, it resolves the path step by step:
> ```
> /       → home
> home    → amir
> amir    → test.txt
> ```

Each directory contains mappings between names and inode numbers.

---

### Inodes and Hard Links

Multiple filenames can point to the same inode.

For example:

```
file1.txt ──┐
            ├──> inode 12345 ──> data blocks
file2.txt ──┘
```

These are hard links to the same file.

The inode contains a link count indicating how many directory entries reference it.

When a file is removed with:

```bash
rm file1.txt
```

the directory entry is removed.

The inode and data blocks are freed only when no directory entries (hard links) remain and no process still has the file open.

---

## File Allocation Table vs Inodes

Different filesystems use different methods to organize file metadata and data.

- ### FAT

    FAT filesystems such as FAT16 and FAT32 use a File Allocation Table.

    The FAT tracks the allocation chain of data clusters belonging to files.

    FAT filesystems are commonly used for removable media and compatibility with many operating systems.

    They do not natively provide the normal Unix ownership and permission model.

- ### Linux Filesystems

    Filesystems such as ext4 and XFS use structures such as:

    - Inodes
    - Directory entries
    - Allocation metadata
    - Filesystem metadata

    There is no single centralized FAT-style table containing all file allocation information.

    For ext4, for example, an inode references the file's data through filesystem-specific block mapping structures.

    Modern ext4 uses extents rather than relying primarily on the old direct/single/double/triple indirect block scheme.

## File Extensions

Linux does not normally use file extensions to determine whether a file can be executed.

For example:

```bash
script.sh
script
script.txt
```

can all potentially be executable if the file has **execute permission** and contains executable content appropriate for the system.

The `.sh` extension is primarily a naming convention.

For example:

```bash
chmod +x script.sh
./script.sh
```

> The execute permission is what allows the file to be executed; the `.sh` extension itself does not grant execution permission.
>
> This differs from Windows, where file extensions are heavily used to associate files with applications.

# Access Control Lists (ACLs)

Traditional Linux permissions provide only three classes:

- owner
- group
- others

Sometimes this is not enough.

For example, suppose:

```
file.txt
owner  = amir
group  = developers
```

You want:

```
amir       → rwx
developers → r--
bob        → rw-
alice      → r--
```

Standard permissions cannot directly express individual permissions for bob and alice.

This is where Access Control Lists (ACLs) are used.

**ACLs allow additional users and groups to receive specific permissions.**

- ### Viewing ACLs

    Use:

    ```bash
    getfacl file.txt
    ```

    Example:

    ```
    # file: file.txt
    # owner: amir
    # group: developers
    user::rw-
    user:bob:rw-
    group::r--
    mask::rw-
    other::---
    ```

    The ACL contains:

    - Owner entry
    - Named user entries
    - Group entry
    - Named group entries
    - ACL mask
    - Others entry

- ### Setting ACLs

    Use:

    ```bash
    setfacl
    ```

    - Give user bob read/write permission → `setfacl -m u:bob:rw file.txt`
    - Give group qa read permission → `setfacl -m g:qa:r file.txt`
    - Remove a user's ACL entry → `setfacl -x u:bob file.txt`
    - Remove all extended ACL entries → `setfacl -b file.txt`

- ### ACL Mask

    The ACL mask limits the effective permissions of:

    - Named users
    - Named groups
    - The owning group

    For example:

    ```
    user:bob:rwx
    mask::r--
    ```

    The ACL entry says that bob has `rwx`, but the mask limits the effective permissions to `r--`.

    This is why getfacl may display:

    ```
    user:bob:rwx        #effective:r--
    ```

    > The ACL mask does not restrict the file owner or others.

- ### Default ACLs

    A directory can have a default ACL.

    A default ACL is inherited by newly created files and directories inside that directory.

    Example:

    ```bash
    setfacl -m d:u:bob:rw /shared
    ```

    Now newly created objects inside `/shared` can inherit an ACL entry for bob.

    View it with:

    ```bash
    getfacl /shared
    ```

    > Default ACLs are useful for shared project directories where specific users or groups should automatically receive access to newly created files.

- ### ACLs and Inodes

ACLs are filesystem metadata, but it is not accurate to say that ACLs are always simply "stored inside the inode."

On filesystems such as ext4, extended ACL information is typically stored using extended attributes (**`xattrs`**) associated with the inode.

Conceptually:

```
inode
 ├── owner
 ├── group
 ├── basic permissions
 ├── timestamps
 └── references to extended attributes
                    |
                    └── ACL data
```

The exact implementation depends on the filesystem.

## Group Membership

A user's group memberships affect permission checking.

You can see the current user's groups with:

```bash
groups
```

or:

```bash
id
```

Example:

```bash
uid=1000(amir) gid=1000(amir) groups=1000(amir),1001(developers),1002(docker)
```

> When a user is added to a new group, an existing login session may not immediately have that new supplementary group membership.
> 
> For example:
>
> ```bash
> sudo usermod -aG docker amir
> ```
>
> After adding the user to the group, the user should normally start a new login session.

### newgrp

`newgrp` starts a new shell with a different effective group.

Example:

```bash
newgrp developers
```

The new shell uses developers as its effective group.

This affects the group ownership of newly created files in that shell when normal filesystem group-selection rules are applied.

It does not permanently change the user's primary group in `/etc/passwd`. To permanently change a user's primary group, an administrator can use tools such as:

```bash
usermod -g developers amir
```

## umask

`umask` controls which permission bits are removed from the default permissions when new files and directories are created.

Check the current umask:

```bash
umask
```

Example:

```bash
0022
```

The kernel/program starts from default creation permissions and applies the umask to remove permissions.

A common conceptual model is:

```bash
Files:       666 & ~umask
Directories: 777 & ~umask
```

For:

```bash
umask 022
```

new regular files typically become `666 - masked write permissions (022) = 644` and new directories typically become `777 - masked group/other write permissionsv = 755`

Therefore:

```
umask 022

new file       → 644
new directory  → 755
```

> **Important:**
> 
> A normal regular file is not created with execute permission merely because the umask allows it. Programs generally create regular files with a maximum mode of `666`, while directories use `777`. The exact final mode can also be influenced by the application creating the object and, when applicable, default ACLs.

# Special Permissions

Linux has three traditional special permission bits:

- **SUID**
- **SGID**
- **Sticky bit**

They are in addition to the normal rwx permissions.

- ## SUID

    **SUID (Set User ID)** is primarily used on executable files.

    When an executable has SUID set, the process normally runs with the effective user ID of the file owner, rather than the user who launched it.

    Example:

    ```
    -rwsr-xr-x 1 root root ... /usr/bin/passwd
    ```

    The **`s`** appears in the owner's execute position **`rws`** Instead of `rwx`.

    A classic example is `/usr/bin/passwd`. The program needs elevated privileges to modify password-related protected files such as `/etc/shadow`, so it traditionally uses SUID.

    ### Setting SUID

    Symbolically:

    ```bash
    chmod u+s file
    ```

    Numerically:
    ```bash
    chmod 4755 file
    ```

    ### Removing SUID

    ```bash
    chmod u-s file
    ```

    or:

    ```bash
    chmod 0755 file
    ```

    SUID programs must be treated carefully because vulnerabilities in privileged executables can have serious security consequences.

    ---

- ## SGID

    **SGID** has different behavior depending on whether it is applied to a file or directory.

    - ### SGID on a file

        For an executable, SGID causes the process to run with the effective group ID of the file's group.

        Example:

        ```bash
        -rwxr-sr-x
        ```

        The **`s`** appears in the group execute position.

        Set it with:

        ```bash
        chmod g+s file
        ```

        or:
        ```bash
        chmod 2755 file
        ```
    - ### SGID on a directory

        On a directory, SGID causes newly created files and directories to inherit the directory's group ownership.

        Example:

        ```bash
        drwxrwsr-x 2 root developers ... /shared
        ```

        The important part is `rws` in the group permission field.

        This is extremely useful for shared project directories.

        For example:

        `chmod g+s /shared` → Files created inside /shared will normally inherit the developers group rather than simply using the creator's primary group.

    ---

- ## Sticky Bit

    The sticky bit is primarily used on shared directories.
    
    When the sticky bit is set, users who have write permission on the directory cannot delete or rename files belonging to other users.
    
    Example:
    
    ```bash
    drwxrwxrwt
    ```
    
    The **`t`** at the end indicates the sticky bit.
    
    The classic example is **`/tmp`**, A typical `/tmp` directory is **`drwxrwxrwt`**. This means:
    
    - Everyone can create files.
    - Everyone can access the directory according to its permissions.
    - A user cannot normally delete or rename another user's files.
    - The file owner can delete their own file.
    - The directory owner can delete entries.
    - Root can delete entries.
    
    ### Set sticky bit

    ```bash
    chmod +t directory
    ```

    or:

    ```bash
    chmod 1777 directory
    ```
    
    ### Remove sticky bit
    
    ```bash
    chmod -t directory
    ```

    **Sticky Bit Example:**
    
    - Without the sticky bit: `drwxrwxrwx` → Users with write permission can potentially delete or rename other users' files.
    - With the sticky bit: `drwxrwxrwt`  → users cannot normally delete or rename other users' files.
    
    | User |Sticky bit set | Sticky bit not set |
    | --- | --- | --- |
    | File owner | Yes | Yes | 
    | Directory owner | Yes | Yes |
    | Other user with `w+x` on directory  | No | Yes |
    | Root | Yes | Yes |

---

## Special Permission Numeric Values

The special permission bits occupy an additional leading digit.

- **SUID**   = 4
- **SGID**   = 2
- **Sticky** = 1

**Examples:**

- `chmod 4755 file` → **SUID + 755**
- `chmod 2755 file` → **SGID + 755**
- `chmod 1777 /shared` → **Sticky bit + 777**

All three can be combined:

```bash
chmod 6755 file
```

which means:

- **`4`** = SUID
- **`2`** = SGID
- **`7`** = both
- **`755`** = normal permissions

## Special Permission Display

When execute permission is present, special permissions normally appear as lowercase:

- `-rwsr-xr-x` → SUID + execute
- `-rwxr-sr-x` → SGID + execute
- `drwxrwxrwt` → Sticky bit + execute

If the corresponding execute permission is not present, an uppercase letter is used:

- `-rwSr--r--` → SUID is set, but owner execute is not.
- `-rw-r-Sr--` → SGID is set, but group execute is not.
- `drwxrwxrwT` → Sticky bit is set, but others execute is not.

# Linux File Types

The first character of `ls -l` identifies the file type.

| Character | Type | Description |
| --- | --- | --- |
| - | Regular file | Normal data or executable file |
| d | Directory | Contains directory entries |
| l | Symbolic link | References another path |
| c | Character device | Device providing character-oriented I/O |
| b | Block device | Device providing block-oriented I/O |
| p | Named pipe | (FIFO)	Inter-process communication |
| s | Socket | Inter-process communication endpoint |

**Example:**

- `-rw-r--r--` → regular file
- `drwxr-xr-x` → directory
- `lrwxrwxrwx` → symbolic link
- `crw-rw-rw-` → character device
- `brw-rw----` → block device
- `prw-r--r--` → named pipe
- `srwxrwxrwx` → socket

### Character and Block Devices

A block device provides access to storage as addressable blocks.
Examples:

- `/dev/sda`
- `/dev/sda1`
- `/dev/nvme0n1`
- `/dev/nvme0n1p1`

A character device provides a character-oriented or stream-oriented interface. Examples include: 
- `/dev/tty`
- `/dev/console`
- `/dev/null`

It is important not to interpret "**character device**" as literally meaning that applications can only read one byte at a time. The distinction is about the device interface and I/O semantics, not a strict one-byte-at-a-time limitation.

## File Permissions and the Root User

The root user is not simply "unaffected by all permissions."

Root normally has the Linux capabilities needed to bypass ordinary discretionary access-control restrictions.
For example, root can normally read a file even when its mode is `----------`. However, Linux security mechanisms can still restrict root or privileged processes.

Examples include:
- **`Linux capabilities`**
- **`SELinux`**
- **`AppArmor`**
- **`Filesystem-specific restrictions`**
- **`Immutable file attributes`**
- **`Mount options`**
- **`Container isolation`**

Therefore, the better statement is:

> Root normally bypasses ordinary Unix discretionary permissions, but **root is not universally unrestricted by every Linux security mechanism.**

## Linux Capabilities

Traditional Unix privileges were heavily associated with the all-powerful root user.

Linux capabilities divide many root privileges into smaller units.

Examples include:

- **`CAP_NET_ADMIN`**
- **`CAP_NET_RAW`**
- **`CAP_SYS_ADMIN`**
- **`CAP_CHOWN`**
- **`CAP_DAC_OVERRIDE`**
- **`CAP_SETUID`**

For example:

- **`CAP_CHOWN`** allows changing file ownership.
- **`CAP_DAC_OVERRIDE`** allows bypassing many normal file permission checks.
- **`CAP_NET_ADMIN`** provides various network administration capabilities.

Capabilities are especially important in modern systems and containers because a process can be given only specific privileged operations instead of unrestricted root-level access.

You can inspect capabilities with:

```bash
getcap /path/to/program
```

and:

```bash
capsh --print
```

Capabilities are an extension of the Linux privilege model rather than a replacement for normal file permissions.

### File Allocation and Permissions Are Different

File allocation and access permissions solve different problems.

The filesystem must answer: "**Where is the file's data stored?**"

Structures such as:

- Inodes
- Extents
- Allocation groups
- Block allocation metadata

help answer this question.

The filesystem must also answer: **Who is allowed to access the file and what can they do?**

Metadata such as:

- UID
- GID
- Permission bits
- ACLs

help answer this question.

Therefore:

```
Filename
   ↓
Directory entry
   ↓
Inode
   ├── Owner
   ├── Group
   ├── Permissions
   ├── Timestamps
   ├── ACL metadata
   └── Data block references
          ↓
       File data
```

> ls /etc
> echo $?
> ```
> 
> - If ls succeeds: `0`
> - If the command fails, a non-zero value is returned.
> 
> > The values 1 through 255 do not have one universal meaning. Their meanings depend on the specific program.
> 
> Some common shell-related statuses include:
> 
> - `0` → Success
> - `1` → General error (commonly used)
> - `2` → Incorrect shell usage / syntax in some contexts
> - `126` → Command found but cannot be executed
> - `127` → Command not found
> - `128+n`  → Process terminated by signal n
> 
> Programs can define their own exit codes.
> 
> Exit statuses are especially important in shell scripting:
> 
> ```bash
> command
> 
> if [ $? -eq 0 ]; then
>     echo "Success"
> else
>     echo "Failed"
> fi
> ```
> 
> More commonly, the command can be tested directly:
> 
> ```bash
> if command; then
>     echo "Success"
> else
>     echo "Failed"
> fi
> ```

## Practical Permission Example

Consider:

```bash
drwxr-x---  root developers /shared
```

The permissions mean:

```bash
root       → rwx
developers → r-x
others     → ---
```

A member of developers can:

- Enter `/shared`
- List its contents

But cannot:

- Create files
- Delete files
- Rename files

because the group does not have `w`.

If we change it to:

```bash
chmod 2770 /shared
```

the resulting permissions are: `drwxrws---`

Now:
- Owner → full access
- Group → full access
- SGID → new files inherit the directory's group
- Others → no access

This is a common configuration for collaborative project directories.


## Permission Troubleshooting
When a user cannot access a file or directory, check the complete path rather than only the target file.

Useful commands include:

```bash
ls -l file
```

```bash
ls -ld directory
```

```bash
namei -l /path/to/file
```

> `namei -l` is particularly useful because it displays permissions and ownership for every component of a path.

You can also check the user's identity and groups:

```bash
id username
```

For ACLs:

```bash
getfacl file
```

For filesystem information:

```bash
ls -l
stat file
```

A systematic approach is:
1. Check the path
2. Check directory traversal permissions
3. Check file ownership
4. Check owner/group/others permissions
5. Check ACLs
6. Check special permissions
7. Check the user's group membership
8. Check filesystem/mount restrictions
9. Check security mechanisms such as SELinux/AppArmor if necessary

## Common Permission Mistakes

- **Giving everything 777**

    Avoid using: `chmod -R 777 /` or similar broad commands.

    `777` grants read, write, and execute permissions to everyone and can create serious security problems.

    Use the minimum permissions required.

- **Confusing file and directory permissions**

    For example:

    `x` on a directory ≠ execute a directory as a program

    It means the ability to **traverse/search** the directory.

- **Assuming group permissions are combined**

    If a user matches the file's group, Linux uses the group permission set. It does not combine it with others.

- **Assuming chmod changes ownership**

    It does not.
    - `chmod`  → permissions
    - `chown`  → owner/group ownership
    - `chgrp`  → group ownership

- **Assuming deleting a file depends on the file's write permission**

    Normally, deletion depends on the permissions of the parent directory.

- **Assuming the filename extension controls execution**

    Linux does not require `.sh`, `.exe`, or another extension for execution. The execute permission and the file's executable format/interpreter determine whether it can be executed.

## Permission Summary

Linux uses a layered access-control model.

```bash
File / Directory
       │
       ├── Owner
       ├── Group
       ├── Others
       │
       ├── rwx permissions
       │
       ├── SUID
       ├── SGID
       ├── Sticky bit
       │
       ├── ACLs
       │
       └── Security mechanisms
            ├── Capabilities
            ├── SELinux
            └── AppArmor
```

The most important commands are:

| Command | Purpose |
| --- | --- |
| `ls -l` | View permissions and ownership |
| `ls -ld` | View permissions of a directory itself |
| `stat` | View detailed metadata |
| `chmod` | Change permissions |
| `chown` | Change owner/group |
| `chgrp` | Change group |
| `id` | Display user and group information |
| `groups` | Display group membership |
| `newgrp` | Start a shell with a different effective group |
| `umask` | View/change default permission mask |
| `getfacl` | View ACLs |
| `setfacl` | Modify ACLs |
| `getcap` | View file capabilities |
| `namei -l` | Inspect permissions along a path |


The core concepts to remember are:

```
r → read
w → write
x → execute / traverse

u → owner
g → group
o → others

chmod  → permissions
chown  → ownership
chgrp  → group ownership

SUID   → executable uses file owner's effective UID
SGID   → executable uses file group's effective GID
SGID on directory → new objects inherit directory group
Sticky → users cannot delete/rename other users' files in shared directory

ACL → additional per-user/per-group permissions
umask → removes permissions from newly created objects

inode → file metadata and data references
directory entry → filename → inode mapping
```
