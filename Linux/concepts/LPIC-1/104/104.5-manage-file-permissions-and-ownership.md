# Permissions

Linux permissions control who can access files and directories and what they are allowed to do with them.

Unlike Windows, Linux does not have one universal permission mechanism tied to a single filesystem. Traditional Linux permissions are implemented by the filesystem and exposed through the Linux VFS. Filesystems such as ext4 and XFS support the standard Unix permission model, while filesystems such as FAT/exFAT do not natively store Unix ownership and permission metadata in the same way.

When such filesystems are mounted on Linux, permissions can instead be assigned through mount options.

## Permissions vs Privileges

These two concepts are related but different.

**Permissions** control access to files and directories.

Examples:

- Read a file
- Modify a file
- Execute a file
- Enter a directory
- Create or delete files inside a directory

**Privileges** refer to the ability to perform system-level or administrative operations.

Examples:

- Installing software
- Managing users
- Changing system configuration
- Mounting filesystems
- Starting/stopping services
- Shutting down the system

The `root` user traditionally has broad administrative privileges, although modern Linux can also divide privileged operations using mechanisms such as Linux capabilities.

In short:

> **Permissions → control access to filesystem objects.**  
> **Privileges → control access to system-level operations.**

# Basic Linux Permissions

Linux has three basic permissions:

| Permission | File | Directory |
|---|---|---|
| `r` (read) | Read the file's contents | List directory entries |
| `w` (write) | Modify/truncate the file | Create, delete, or rename entries |
| `x` (execute) | Execute the file as a program | Traverse/enter the directory and access objects inside |

Directory permissions are particularly important.

### Read permission on a directory

`r` allows you to list the names of entries inside the directory.

```bash
ls directory/
```

However, **`r`** alone is not enough to access the files.

### Execute permission on a directory

**`x`** means traverse the directory.

It allows you to:

```bash
cd directory/
```

and access objects inside it when you know their names.

For example, a user may be unable to run:

```bash
ls directory/
```

without **`r`**, but may still be able to access:

```bash
cat directory/file.txt
```

if they have **`x`** permission on the directory and appropriate permissions on `file.txt`.

### Write permission on a directory

**`w`** allows modification of the directory's entries.

When combined with **`x`**, it allows users to:

- Create files
- Delete files
- Rename files
- Create directories

Therefore:

To create, delete, or rename entries in a directory, you normally need **`w + x`** on the directory.

**Important distinction when deleting a file**

Deleting a file depends primarily on the permissions of its parent directory, not the permissions of the file itself.

For example, a user may be unable to write to `file.txt`, but still be able to delete it if they have **`w+x`** on the containing directory.

This is why directories such as `/tmp` require special protection using the **sticky bit**.

## Permission Classes

Every Linux file has permissions for three classes of users:

- **Owner (user)**
- **Group**
- **Others**

For example:

```bash
rwxr-x--x
```

The permission string is divided into three groups:

```
rwx  |  r-x  |  --x
 ↓       ↓       ↓
user   group   others
```

Therefore:

- Owner → **`rwx`**
- Group → **`r-x`**
- Others → **`--x`**

## Numeric Permissions

Each basic permission has a numeric value:

- **`r`** = 4
- **`w`** = 2
- **`x`** = 1
- **`-`** = 0

These values are powers of two:

- **`r`** = 2² = 4
- **`w`** = 2¹ = 2
- **`x`** = 2⁰ = 1

For example:

```
rwxr-x--x
```

becomes:

- Owner:  **`rwx`** = 4 + 2 + 1 = 7
- Group:  **`r-x`** = 4 + 0 + 1 = 5
- Others: **`--x`** = 0 + 0 + 1 = 1

Therefore:

`rwxr-x--x` = 751

**Common examples:**

| Numeric | Symbolic | Meaning |
| --- | --- | --- |
| 777 | rwxrwxrwx | Everyone has full permissions |
| 755 | rwxr-xr-x | Owner full, others read/execute |
| 750 | rwxr-x--- | Owner full, group read/execute |
| 700 | rwx------ | Owner only |
| 644 | rw-r--r-- | Owner read/write, others read |
| 640 | rw-r----- | Owner read/write, group read |
| 600 | rw------- | Owner read/write |
| 400 | r-------- | Owner read-only |

## Viewing Permissions

The most common command is:

```bash
ls -l
```

Example:

```bash
-rwxr-x--- 1 amir developers 1234 Oct  5 10:00 script.sh
```

The first character represents the file type:

- **`-`** → regular file
- **`d`** → directory
- **`l`** → symbolic link
- **`c`** → character device
- **`b`** → block device
- **`p`** → named pipe
- **`s`** → socket

The next nine characters are the basic permissions:

```bash
rwx | r-x | ---
```

The output also shows:

- Number of hard links
- Owner
- Group
- Size
- Modification time
- Name

To inspect the directory itself rather than its contents:

```bash
ls -ld directory/
```

For example:

**`ls -ld /tmp`**

Whereas:

**`ls -l /tmp`** → lists the objects inside /tmp.

> Using **`ls -la directory/`**, shows hidden objects as well.

## stat command

The `stat` command displays detailed metadata about a file or directory.

```bash
stat file.txt
```

It can show:

- File type
- Permissions
- Owner
- Group
- Size
- Inode number
- Access time (**`atime`**)
- Modification time (**`mtime`**)
- Change time (**`ctime`**)

> The Access line contains the permission information and other metadata.

## chmod command

The `chmod` command changes file and directory permissions.

Basic syntax:

```bash
chmod [options] mode file
```

There are two major ways to specify permissions:

- Symbolic mode
- Numeric mode
- chmod: Symbolic Mode

Symbolic permissions use:

- **`u`** = user/owner
- **`g`** = group
- **`o`** = others
- **`a`** = all

Operators:

- `+` → add permission
- `-` → remove permission
- `=` → set exact permissions

Examples:

- `chmod u+r file` → Add read permission for the owner.
- `chmod g-rw file` → Remove read and write permissions from the group.
- `chmod o+x file` → Add execute permission for others.
- `chmod a+x file` → Add execute permission for everyone.
- `chmod u=rwx file` → Set the owner's permissions exactly to rwx.

Multiple changes can be specified together:

```bash
chmod u+rw,g+r,o-r file
```

### chmod: Numeric Mode

Numeric mode directly specifies the permission values.

Example:

- `chmod 755 script.sh` → produces `rwxr-xr-x`
- `chmod 640 file.txt` → produces `rw-r-----`

> Numeric permissions can also include special permissions such as **SUID**, **SGID**, and the sticky bit.

### Recursive chmod

The **`-R`** option applies permissions recursively.

```bash
chmod -R 755 directory/
```

This changes permissions on the directory and everything below it.

## Ownership

Every Linux filesystem object has an owner and a group.

Example:

```bash
-rw-r----- 1 user1 developers 1200 file.txt
```

Here:

- Owner = `user1`
- Group = `developers`

Ownership and permissions are separate concepts.

## chown command

`chown` changes the owner and optionally the group.

Basic syntax:

```bash
chown [options] owner[:group] file
```

Examples:

- `chown user1 file.txt` → Change the owner to user1.
- `chown user1:group1 file.txt` → Change both owner and group.
- `chown :group1 file.txt` → Change only the group.
- `chown -R user1:group1 directory/` → Recursively change owner and group.
- `chown --reference=<otherfile file>` → can copy the ownership information from another file.

## chgrp command

`chgrp` changes the group ownership of a file or directory.

```bash
chgrp group1 file.txt
```

For example:

- `chgrp developers project.txt` → changes the file's group to developers.
- `chgrp -R developers project/` → Recursive use

### Who Can Change Ownership?

A normal user cannot arbitrarily transfer ownership of a file to another user.

Typically, changing the owner requires **root privileges** or an appropriate administrative capability.

For example:

`chown user2 file.txt` will normally fail for an ordinary user who does not have the required privilege.

A user can generally change the group of a file only to a group they are allowed to use.

## Permission Matching

Linux does not combine permissions from the owner, group, and others categories.

A process is evaluated against exactly one of these classes:

- Owner
- Group
- Others

1. The owner class is checked first.
2. If the process is not the owner, Linux checks whether it belongs to the file's group.
3. If it matches the group class, the group permissions are used.
4. It does not then fall back to the others permissions.

Example:

```
-rwxr--rw- user2:dev file.txt
```

Suppose user1 belongs to both:

- `dev`
- `test`

The file is owned by `user2:dev` The permissions are:

- Owner  = `rwx`
- Group  = `r--`
- Others = `rw-`

`user1` is not the owner but is a member of `dev`, so the group permissions apply `r--`.

The user cannot write to the file, even though the others permissions contain `rw-`.

There is no permission merging such as:

group `r--` + others `rw-`

## Permission Checking on Paths

Linux checks permissions on every directory in a path.

For example:

```
/home/test/project/file.txt
```

To access `file.txt`, the process needs appropriate **execute (`x`)** permission on the directories it must traverse:

```
/
└── home/
    └── test/
        └── project/
            └── file.txt
```

The permissions of the file itself are not enough.

For example, even if:

```
file.txt = rw-------
```

you still need `x` permission on the parent directories to reach it.

This is why directory `x` permission is more accurately described as traverse/search permission rather than simply "enter permission."

## File Permissions vs Directory Permissions

The same permission has different meanings depending on the object.

| Permission | Regular File | Directory |
| --- | --- | --- |
| **`r`** | Read contents | List directory entries |
| **`w`** | Modify/truncate contents | Create/delete/rename entries |
| **`x`** | Execute program | Traverse/search directory |

For example:

```
Directory: rwx
```

means:

- **`r`** → list names
- **`w`** → modify directory entries
- **`x`** → traverse the directory

## Filesystem Metadata and Inodes

Linux filesystems such as ext4 and XFS use filesystem metadata structures to describe files.

An inode contains metadata such as:

- File type
- Owner UID
- Group GID
- Permissions
- File size
- Timestamps
- Link count
- References to the file's data blocks

The inode does not normally contain the filename.

Directory entries associate names with inode numbers.

Conceptually:

```
Directory entry
      |
      | filename → inode number
      v
   Inode
      |
      | metadata + data block references
      v
  File data
```

For example:

`/home/amir/test.txt` is resolved through the directory hierarchy.

> The filesystem does not normally store `/home/amir/test.txt` as one complete pathname inside the inode. Instead, it resolves the path step by step:
> ```
> /       → home
> home    → amir
> amir    → test.txt
> ```

Each directory contains mappings between names and inode numbers.

---

### Inodes and Hard Links

Multiple filenames can point to the same inode.

For example:

```
file1.txt ──┐
            ├──> inode 12345 ──> data blocks
file2.txt ──┘
```

These are hard links to the same file.

The inode contains a link count indicating how many directory entries reference it.

When a file is removed with:

```bash
rm file1.txt
```

the directory entry is removed.

The inode and data blocks are freed only when no directory entries (hard links) remain and no process still has the file open.

---

## File Allocation Table vs Inodes

Different filesystems use different methods to organize file metadata and data.

- ### FAT

    FAT filesystems such as FAT16 and FAT32 use a File Allocation Table.

    The FAT tracks the allocation chain of data clusters belonging to files.

    FAT filesystems are commonly used for removable media and compatibility with many operating systems.

    They do not natively provide the normal Unix ownership and permission model.

- ### Linux Filesystems

    Filesystems such as ext4 and XFS use structures such as:

    - Inodes
    - Directory entries
    - Allocation metadata
    - Filesystem metadata

    There is no single centralized FAT-style table containing all file allocation information.

    For ext4, for example, an inode references the file's data through filesystem-specific block mapping structures.

    Modern ext4 uses extents rather than relying primarily on the old direct/single/double/triple indirect block scheme.

## File Extensions

Linux does not normally use file extensions to determine whether a file can be executed.

For example:

```bash
script.sh
script
script.txt
```

can all potentially be executable if the file has **execute permission** and contains executable content appropriate for the system.

The `.sh` extension is primarily a naming convention.

For example:

```bash
chmod +x script.sh
./script.sh
```

> The execute permission is what allows the file to be executed; the `.sh` extension itself does not grant execution permission.
>
> This differs from Windows, where file extensions are heavily used to associate files with applications.

# Access Control Lists (ACLs)

Traditional Linux permissions provide only three classes:

- owner
- group
- others

Sometimes this is not enough.

For example, suppose:

```
file.txt
owner  = amir
group  = developers
```

You want:

```
amir       → rwx
developers → r--
bob        → rw-
alice      → r--
```

Standard permissions cannot directly express individual permissions for bob and alice.

This is where Access Control Lists (ACLs) are used.

**ACLs allow additional users and groups to receive specific permissions.**

- ### Viewing ACLs

    Use:

    ```bash
    getfacl file.txt
    ```

    Example:

    ```
    # file: file.txt
    # owner: amir
    # group: developers
    user::rw-
    user:bob:rw-
    group::r--
    mask::rw-
    other::---
    ```

    The ACL contains:

    - Owner entry
    - Named user entries
    - Group entry
    - Named group entries
    - ACL mask
    - Others entry

- ### Setting ACLs

    Use:

    ```bash
    setfacl
    ```

    - Give user bob read/write permission → `setfacl -m u:bob:rw file.txt`
    - Give group qa read permission → `setfacl -m g:qa:r file.txt`
    - Remove a user's ACL entry → `setfacl -x u:bob file.txt`
    - Remove all extended ACL entries → `setfacl -b file.txt`

- ### ACL Mask

    The ACL mask limits the effective permissions of:

    - Named users
    - Named groups
    - The owning group

    For example:

    ```
    user:bob:rwx
    mask::r--
    ```

    The ACL entry says that bob has `rwx`, but the mask limits the effective permissions to `r--`.

    This is why getfacl may display:

    ```
    user:bob:rwx        #effective:r--
    ```

    > The ACL mask does not restrict the file owner or others.

- ### Default ACLs

    A directory can have a default ACL.

    A default ACL is inherited by newly created files and directories inside that directory.

    Example:

    ```bash
    setfacl -m d:u:bob:rw /shared
    ```

    Now newly created objects inside `/shared` can inherit an ACL entry for bob.

    View it with:

    ```bash
    getfacl /shared
    ```

    > Default ACLs are useful for shared project directories where specific users or groups should automatically receive access to newly created files.

- ### ACLs and Inodes

ACLs are filesystem metadata, but it is not accurate to say that ACLs are always simply "stored inside the inode."

On filesystems such as ext4, extended ACL information is typically stored using extended attributes (**`xattrs`**) associated with the inode.

Conceptually:

```
inode
 ├── owner
 ├── group
 ├── basic permissions
 ├── timestamps
 └── references to extended attributes
                    |
                    └── ACL data
```

The exact implementation depends on the filesystem.
