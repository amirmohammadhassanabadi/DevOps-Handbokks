# 102.4 Use Debian Package Management

Debian-based systems use the **Debian package management system** to install, upgrade, remove, query, and maintain software.

The main package format is:

```text
.deb
```

The two main layers are:

```text
APT
 │
 │ dependency resolution,
 │ repository access,
 │ package selection
 ▼
dpkg
 │
 │ installs/removes
 │ .deb packages
 ▼
Installed software
```

* **`dpkg`** is the low-level package management tool. It works directly with `.deb` packages and maintains the local package database.
* **APT** is the higher-level package management system. It works with repositories, resolves dependencies, downloads packages, and uses `dpkg` to perform the actual package installation and removal.

Common APT-related commands include:

```text
apt
apt-get
apt-cache
apt-mark
```

`aptitude` is another higher-level frontend available on Debian-based systems, although it is not the primary tool covered by this objective.

---

## Debian Package Management

A Debian package contains the files and metadata required to install a piece of software.

A package can contain:

* Program binaries
* Configuration files
* Documentation
* Libraries
* Maintainer scripts
* Dependency information
* Package metadata

The package manager uses this information to install and maintain software consistently.

### Package database

`dpkg` maintains a local database containing information about installed and known packages.

This allows commands such as:

```bash
dpkg -l
dpkg -s nginx
dpkg -L nginx
dpkg -S /usr/sbin/nginx
```

to determine package state, package information, installed files, and file ownership.

---

## APT

APT (**Advanced Package Tool**) is the higher-level package management system used on Debian and its derivatives.

APT can:

* Obtain package information from repositories
* Resolve dependencies
* Download packages
* Install packages
* Upgrade packages
* Remove packages
* Search available packages
* Display package information

For interactive administration, both `apt` and `apt-get` are commonly used.

`apt` is designed as a user-friendly command-line interface, while `apt-get` is the more traditional and script-oriented APT command.

---

## Updating Package Information

```bash
sudo apt update
```

This downloads the latest package indexes from the configured repositories.

It **does not install or upgrade packages**.

The downloaded repository metadata is stored under:

```text
/var/lib/apt/lists/
```

This metadata tells APT which packages and versions are available and where they can be obtained.

Typical workflow:

```bash
sudo apt update
sudo apt upgrade
```

The `update` operation should normally be performed before upgrading packages so APT has current repository information.

---

## Installing Packages

Install a package from a configured repository:

```bash
sudo apt install <package>
```

Example:

```bash
sudo apt install nginx
```

APT resolves and installs the required dependencies automatically.

Multiple packages can be installed at once:

```bash
sudo apt install nginx curl vim
```

### Useful options

- **`-y`** →  Automatically answer yes to prompts.
- **`--reinstall`** →  Reinstall an already installed package.
- **`--download-only`** → Download the required packages without installing them.
- **`--no-install-recommends`** → Avoid installing packages listed as `Recommends`.
- **`-f`** → Attempt to fix broken dependencies. This is particularly useful when repairing an incomplete package installation.

---

## Upgrading Packages

- ### `apt upgrade`

    ```bash
    sudo apt upgrade
    ```

    Upgrades installed packages when newer versions are available.

    > `apt upgrade` is **not** strictly limited to upgrading packages without installing any new packages.

    Modern APT can install new packages when they are required to satisfy dependencies, but it will **not remove existing installed packages**. If upgrading a package requires removing another installed package, that package's upgrade is normally held back.

    - ### `--with-new-pkgs`

        With `apt-get`, the following option allows `upgrade` to install newly required dependency packages while still preventing package removal:

        ```bash
        sudo apt-get upgrade --with-new-pkgs
        ```

        This is different from `full-upgrade` because packages are still not removed.

    ---

    - ## `apt full-upgrade`

        ```bash
        sudo apt full-upgrade
        ```

        `full-upgrade` performs an upgrade while allowing APT to remove installed packages when necessary to resolve dependency changes.

        For `apt-get`, the traditional equivalent is:

        ```bash
        sudo apt-get dist-upgrade
        ```

    The important distinction is:

    | Command                           | Install new packages when required | Remove installed packages |
    | --------------------------------- | ---------------------------------: | ------------------------: |
    | `apt upgrade`                     | Yes, when required by dependencies |                        No |
    | `apt-get upgrade --with-new-pkgs` |                                Yes |                        No |
    | `apt full-upgrade`                |                                Yes |                       Yes |
    | `apt-get dist-upgrade`            |                                Yes |                       Yes |

    `full-upgrade` is a **package-system upgrade operation**. It should not be described as the command used to perform a distribution release upgrade such as Ubuntu 22.04 → 24.04. Release upgrades use the distribution's release-upgrade mechanism.

---

## Removing Packages

- ### Remove

    ```bash
    sudo apt remove <package>
    ```

    Removes the package while normally retaining its package-managed configuration files.

    Example:

    ```bash
    sudo apt remove nginx
    ```

- ### Purge

    ```bash
    sudo apt purge <package>
    ```

    Removes the package and its package-managed configuration files.

    Example:

    ```bash
    sudo apt purge nginx
    ```

The distinction is:

```text
remove
    → package removed
    → configuration files normally remain

purge
    → package removed
    → package-managed configuration files removed
```

---

### Automatically Removing Unused Dependencies

```bash
sudo apt autoremove
```

Removes packages that were automatically installed as dependencies and are no longer required.

For example:

```text
Package A
   │
   └── depends on Package B
```

If Package A is removed and Package B is no longer required by anything else, APT may mark Package B as no longer needed.

`autoremove` can then remove it.

#### Important correction

Do not use:

```bash
apt autoremove <package>
```

as a general equivalent of:

```bash
apt remove <package>
```

The normal form is:

```bash
sudo apt autoremove
```

If you want to explicitly remove a package and then clean up unused dependencies:

```bash
sudo apt remove <package>
sudo apt autoremove
```

---

## Searching for Packages

```bash
apt search <keyword>
```

Example:

```bash
apt search web server
```

This searches package names and descriptions.

To search only package names:

```bash
apt search --names-only <keyword>
```

Example:

```bash
apt search --names-only nginx
```

`sudo` is not required for package searches.

---

## Listing Packages

```bash
apt list
```

Lists packages known to APT.

Show installed packages:

```bash
apt list --installed
```

Show packages that can be upgraded:

```bash
apt list --upgradable
```

Show all available versions:

```bash
apt list --all-versions
```

These commands do not normally require `sudo`.

---

## Package Information

- ### `apt show`

    ```bash
    apt show <package>
    ```

    Example:

    ```bash
    apt show nginx
    ```

    Displays information such as:

    * Package name
    * Version
    * Architecture
    * Dependencies
    * Description
    * Package size
    * Repository information

- ### `apt-cache show`

    ```bash
    apt-cache show <package>
    ```

    `apt-cache` provides lower-level access to APT's package metadata.

---

## Package Versions and Repository Selection

```bash
apt policy <package>
```

Example:

```bash
apt policy nginx
```

This can show:

* Installed version
* Candidate version
* Available versions
* Package sources
* Repository priorities

This is particularly useful when troubleshooting repository or version-selection problems.

Example:

```text
Installed: 1.24.0-1
Candidate: 1.26.0-1
Version table:
   1.26.0-1 ...
   1.24.0-1 ...
```

---

## Package Dependencies

- **`apt depends <package>`** → Show the dependencies of a package
- **`apt rdepends <package>`** → Reverse dependencies. This shows packages that depend on the specified package.

    The same functionality is available through `apt-cache`:

    ```bash
    apt-cache depends nginx
    apt-cache rdepends libc6
    ```

---

## Reinstalling a Package

A package can be reinstalled using:

```bash
sudo apt install --reinstall <package>
```

Example:

```bash
sudo apt install --reinstall nginx
```

This is useful when package-managed files have been deleted or damaged.

---

## Holding Packages

APT can mark a package as **held**, preventing normal package upgrades from changing it.

- **`sudo apt-mark hold <package>`** → Hold a package
- **`apt-mark showhold`** → Show held packages
- **`sudo apt-mark unhold <package>`** → Remove the hold

This is useful when a package must temporarily remain at its current version.

---

## Downloading Packages Without Installing

APT can download a `.deb` package without installing it:

```bash
apt download <package>
```

Example:

```bash
apt download nginx
```

The package is downloaded into the current directory.

`sudo` is normally unnecessary.

By default, this command downloads the requested binary package rather than installing it. Dependency packages are not automatically installed.

For more controlled downloads, `apt-get download` is also available.

---

# Debian Package Management with `dpkg`

`dpkg` is the low-level Debian package management tool.

It works directly with `.deb` packages and maintains the local package database.

APT uses `dpkg` to perform the low-level installation and removal operations.

---

## Installing a Local `.deb`

```bash
sudo dpkg -i <package.deb>
```

Example:

```bash
sudo dpkg -i nginx_1.24.0-1_amd64.deb
```

Unlike APT, `dpkg` does not automatically obtain missing dependencies from repositories.

If dependencies are missing, the installation may leave the package in an incomplete state.

A common recovery command is:

```bash
sudo apt -f install
```

or:

```bash
sudo apt-get -f install
```

APT then attempts to resolve and install the missing dependencies.

---

## Removing a Package with `dpkg`

```bash
sudo dpkg -r <package>
```

Example:

```bash
sudo dpkg -r nginx
```

This removes the package while normally leaving its configuration files.

---

## Purging a Package with `dpkg`

```bash
sudo dpkg -P <package>
```

Example:

```bash
sudo dpkg -P nginx
```

This removes the package and its package-managed configuration files.

---

## Listing Installed Packages

```bash
dpkg -l
```

Search for a particular package:

```bash
dpkg -l nginx
```

Or:

```bash
dpkg -l 'nginx*'
```

The output contains package selection, status, and error information.

Common status combinations include:

```text
ii    installed
rc    removed, configuration files remain
un    not-installed
```

---

## Package Status

```bash
dpkg -s <package>
```

Example:

```bash
dpkg -s nginx
```

This displays information about an installed package, including:

* Package name
* Version
* Architecture
* Status
* Dependencies
* Description

---

## Listing Files Installed by a Package

```bash
dpkg -L <package>
```

Example:

```bash
dpkg -L nginx
```

This lists files belonging to an installed package.

---

## Finding Which Package Owns an Installed File

```bash
dpkg -S <file>
```

Example:

```bash
dpkg -S /usr/sbin/nginx
```

This determines which installed package owns the specified file.

This is an important distinction:

> **`dpkg -L package`** → What files does this installed package provide?
> 
> **`dpkg -S /path/to/file`** → Which installed package owns this file?

---

## Inspecting a `.deb` Without Installing It

`dpkg-deb` can inspect package files directly.

Display package metadata:

```bash
dpkg-deb -I <package.deb>
```

List files contained inside the package:

```bash
dpkg-deb -c <package.deb>
```

Example:

```bash
dpkg-deb -c nginx_1.24.0-1_amd64.deb
```

This is useful when the package is not installed yet.

---

# Finding Packages That Contain a File

One of the explicit LPIC-1 102.4 requirements is being able to find packages containing specific files or libraries, whether the package is installed or not.

There are two different situations.

### Package is already installed

Use:

```bash
dpkg -S /path/to/file
```

Example:

```bash
dpkg -S /usr/bin/vim
```

### Package is not installed

`dpkg -S` cannot search packages that are not installed.

A repository package-content search tool such as `apt-file` can be used:

```bash
apt-file search <filename>
```

Example:

```bash
apt-file search bin/htpasswd
```

`apt-file` searches repository package-content indexes rather than the local installed-package database.

This distinction is important for the exam:

```text
Installed package
    → dpkg -S

Package not installed
    → apt-file search
```

---

# Finding Libraries

The same concept applies to libraries.

If a library file is already installed:

```bash
dpkg -S /path/to/library
```

For example:

```bash
dpkg -S /usr/lib/x86_64-linux-gnu/libssl.so.3
```

If the library is not installed, use a repository package-content search such as:

```bash
apt-file search libssl.so
```

This allows you to determine which package provides the required library.

---

# Package Integrity and Verification

Package management includes verifying that packages and repository data can be trusted.

APT verifies repository metadata and package authenticity through Debian's repository signing system.

For an individual `.deb`, package metadata can be inspected with:

```bash
dpkg-deb -I package.deb
```

However, inspection is not the same as cryptographic verification.

APT's repository trust mechanism is based on signed repository metadata and trusted keys/keyrings.

For manually downloaded packages, additional tools and mechanisms may be required to verify signatures or checksums depending on the source.

---

# Debian APT Repositories

An APT repository is a package source containing packages and repository metadata.

APT uses repository definitions to determine:

* Where packages are located
* Which distribution/release they belong to
* Which package components are available
* Which keys are trusted for that repository

The traditional main configuration file is:

```text
/etc/apt/sources.list
```

Additional repositories are commonly configured under:

```text
/etc/apt/sources.list.d/
```

After changing repository configuration:

```bash
sudo apt update
```

should be run to download the updated package indexes.

---

## Traditional Repository Format

A traditional repository entry looks like:

```text
deb http://archive.ubuntu.com/ubuntu/ noble main restricted universe multiverse
```

The general structure is:

```text
deb URI suite components
```

For example:

```text
deb http://archive.ubuntu.com/ubuntu/ noble main restricted universe multiverse
```

Where:

```text
deb
    Binary package repository

URI
    Repository location

suite
    Distribution/release name

components
    Sections of the repository
```

For source packages:

```text
deb-src URI suite components
```

For example:

```text
deb-src http://archive.ubuntu.com/ubuntu/ noble main restricted universe multiverse
```

---

## Repository Components

Components depend on the distribution.

Ubuntu commonly uses:

```text
main
restricted
universe
multiverse
```

Debian commonly uses components such as:

```text
main
contrib
non-free
non-free-firmware
```

Therefore, components should not be treated as universal across all Debian-based distributions.

---

## `/etc/apt/sources.list.d/`

This directory contains additional repository configuration.

For example:

```text
/etc/apt/sources.list.d/docker.list
/etc/apt/sources.list.d/google-chrome.list
```

Modern APT also supports the deb822 format using `.sources` files:

```text
/etc/apt/sources.list.d/docker.sources
```

A deb822 repository definition can look like:

```text
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc
```

Important fields include:

| Field        | Meaning                                  |
| ------------ | ---------------------------------------- |
| `Types`      | Package type, such as `deb` or `deb-src` |
| `URIs`       | Repository location                      |
| `Suites`     | Distribution/release or repository suite |
| `Components` | Repository sections                      |
| `Signed-By`  | Keyring used to verify the repository    |

The `.sources` format is the modern structured alternative to traditional one-line `.list` entries.

---

# APT Repository Trust and Keyrings

APT verifies repository authenticity using cryptographic signatures.

Modern repository configuration commonly uses a repository-specific keyring with:

```text
Signed-By:
```

For example:

```text
Signed-By: /etc/apt/keyrings/example.gpg
```

The older global trust mechanisms include:

```text
/etc/apt/trusted.gpg
/etc/apt/trusted.gpg.d/
```

However, these should not be presented as the preferred method for configuring new third-party repositories.

A repository-specific keyring referenced with `Signed-By` provides better isolation because the key is associated with a particular repository rather than being globally trusted for all APT repositories.

---

# APT Package Indexes and Cache

APT uses several different types of local data, and they should not be confused.

### Repository package indexes

```text
/var/lib/apt/lists/
```

Contains downloaded repository metadata describing available packages.

This is primarily what `apt update` refreshes.

### Downloaded `.deb` files

```text
/var/cache/apt/archives/
```

Contains downloaded Debian package files when they are retained in the local cache.

Therefore:

```text
/var/lib/apt/lists/
    → repository/package metadata

/var/cache/apt/archives/
    → downloaded .deb packages
```

---

# APT Package Cache

APT can retain downloaded `.deb` packages in:

```text
/var/cache/apt/archives/
```

Whether downloaded packages are retained after installation depends on the APT configuration and distribution defaults. Therefore, it is better not to state that APT universally "always deletes" or "always keeps" downloaded packages.

You can inspect the effective configuration with:

```bash
apt-config dump | grep -i Keep-Downloaded-Packages
```

Configuration can also be placed in:

```text
/etc/apt/apt.conf.d/
```

For example:

```text
APT::Keep-Downloaded-Packages "true";
```

This tells APT to retain downloaded package files after installation.

The exact default can vary by APT/distribution configuration, so the effective configuration is more reliable than assuming a universal default.

---

## `apt clean`

```bash
sudo apt clean
```

Removes downloaded package files from:

```text
/var/cache/apt/archives/
```

and its `partial/` directory, except for the lock file.

This is useful when the package cache is consuming significant disk space.

---

## `apt autoclean`

```bash
sudo apt autoclean
```

Removes downloaded package files that can no longer be downloaded from configured repositories.

This allows useful cache entries to remain while removing obsolete package files.

The distinction is:

```text
apt clean
    → remove cached package files

apt autoclean
    → remove obsolete cached package files
```

---

## APT Cache Information

```bash
apt-cache show <package>
```

Displays package metadata.

```bash
apt-cache policy <package>
```

Displays installed/candidate versions and repository priorities.

```bash
apt-cache stats
```

Displays statistics about the APT package cache/index data.

Note that `apt-cache` is primarily working with package metadata; it is not simply querying the `.deb` files stored under `/var/cache/apt/archives/`.

---

# APT Configuration

APT configuration is commonly stored in:

```text
/etc/apt/apt.conf
/etc/apt/apt.conf.d/
```

The `apt.conf.d` directory contains configuration fragments.

For example:

```text
/etc/apt/apt.conf.d/99local
```

An administrator can use such a file for local configuration.

Example:

```text
Acquire::Retries "3";
APT::Keep-Downloaded-Packages "true";
```

APT reads its configuration when the command starts, so changes normally take effect on the next APT invocation. No daemon restart is required.

Avoid relying on a fixed list of filenames such as `00aptitude`, `10periodic`, `50unattended-upgrades`, etc. across all Debian-based systems. Those files are distribution/version/application dependent and are not a stable part of the LPIC-1 package-management model.

# Package Source and Build Commands

APT also provides functionality for working with source packages.

These commands are useful real-world administration/development knowledge but are **not central to the LPIC-1 102.4 objective**.

### Download source package

```bash
apt source <package>
```

This downloads the source package.

Source repositories must be enabled.

### Install build dependencies

```bash
sudo apt build-dep <package>
```

This installs the packages required to build the specified source package.

The corresponding source repositories and package metadata must be available.

---

# Checking Package Dependency Problems

APT provides:

```bash
sudo apt check
```

This is a diagnostic operation that updates package cache information and checks for broken dependencies.

For a system left in an incomplete package state, another important command is:

```bash
sudo dpkg --configure -a
```

This attempts to configure packages that have been unpacked but not completely configured.

If dependencies are missing:

```bash
sudo apt -f install
```

can attempt to resolve them.

A common recovery sequence is:

```bash
sudo dpkg --configure -a
sudo apt -f install
```

Then verify:

```bash
sudo apt check
```

---

# `dpkg-reconfigure`

`dpkg-reconfigure` reruns the configuration process of an already installed Debian package.

Syntax:

```bash
sudo dpkg-reconfigure <package>
```

Example:

```bash
sudo dpkg-reconfigure tzdata
```

This can be useful for packages such as:

```text
tzdata
keyboard-configuration
locales
```

It does not reinstall the package. It reruns its package configuration process.

`dpkg-reconfigure` is explicitly listed by LPI for 102.4.

---

# Practical Local `.deb` Installation Workflow

A common real-world situation is receiving a `.deb` file manually.

For example:

```bash
wget https://example.com/package.deb
```

Then:

```bash
sudo dpkg -i package.deb
```

If dependencies are missing:

```bash
sudo apt -f install
```

Alternatively, modern APT can install a local `.deb` and resolve its dependencies directly:

```bash
sudo apt install ./package.deb
```

The `./` tells APT that the argument is a local package file rather than a repository package name.

For normal repository packages, use:

```bash
sudo apt install nginx
```

For a local package:

```bash
sudo apt install ./nginx_package.deb
```

# `apt` vs `apt-get` vs `apt-cache`

| Tool               | Main purpose                                       |
| ------------------ | -------------------------------------------------- |
| `apt`              | User-oriented APT command-line interface           |
| `apt-get`          | Traditional/general APT package-management command |
| `apt-cache`        | Query and inspect package metadata                 |
| `dpkg`             | Low-level `.deb` package management                |
| `dpkg-reconfigure` | Re-run package configuration                       |
| `apt-mark`         | Manage package selection states such as holds      |
| `apt-file`         | Search repository package contents                 |

A simplified relationship:

```text
                    APT
                     │
       ┌─────────────┼──────────────┐
       │             │              │
      apt         apt-get       apt-cache
       │             │              │
       └─────────────┴──────────────┘
                     │
                   dpkg
                     │
              Debian package DB
```

# LPIC-1 102.4 Key Points

* Debian packages use the `.deb` format.
* `dpkg` is the low-level Debian package management tool.
* APT is the higher-level package management system.
* APT uses `dpkg` for low-level package installation and removal.
* `dpkg` maintains a local package database.
* `dpkg` does not resolve missing dependencies from repositories.
* `apt update` refreshes repository package indexes.
* `apt update` does not install or upgrade packages.
* `apt install` installs packages and resolves dependencies.
* `apt remove` removes packages but normally keeps package-managed configuration files.
* `apt purge` removes packages and their package-managed configuration files.
* `apt autoremove` removes automatically installed dependencies that are no longer required.
* `apt upgrade` does not remove installed packages.
* `apt full-upgrade` can remove installed packages when required to resolve dependency changes.
* `apt-get dist-upgrade` is the traditional equivalent of `apt full-upgrade`.
* `dpkg -i` installs a local `.deb` package.
* `dpkg -r` removes a package.
* `dpkg -P` purges a package.
* `dpkg -L` lists files installed by a package.
* `dpkg -S` finds which installed package owns a file.
* `dpkg-deb` can inspect a `.deb` without installing it.
* `dpkg --configure -a` configures unpacked but unconfigured packages.
* `dpkg-reconfigure` reruns a package's configuration process.
* `apt-cache` can query package metadata and dependencies.
* `apt-file` can search package contents for packages that are not installed.
* `/etc/apt/sources.list` contains traditional APT repository definitions.
* `/etc/apt/sources.list.d/` contains additional repository definitions.
* `/var/lib/apt/lists/` contains downloaded repository indexes.
* `/var/cache/apt/archives/` contains cached `.deb` files when they are retained.
* `apt clean` removes cached package files.
* `apt autoclean` removes obsolete cached package files.
* Repository-specific keyrings referenced through `Signed-By` are the preferred modern approach for third-party repository trust.
