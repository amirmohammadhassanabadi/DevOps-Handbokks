# Cryptography

Cryptography is the science of protecting information by using mathematical algorithms and cryptographic keys. Its purpose is not limited to hiding data; it provides several distinct security services that address different security requirements. The four primary security services provided by cryptography are **confidentiality**, **integrity**, **authentication**, and **non-repudiation**.

- **Confidentiality** ensures that only authorized parties can read the data. It is achieved through encryption, where plaintext is transformed into ciphertext using an encryption algorithm and a key. Even if an attacker intercepts the ciphertext, it is computationally infeasible to recover the original data without the correct key.
- **Integrity** ensures that data has not been altered, whether accidentally or maliciously. This is typically achieved using cryptographic hash functions (e.g., SHA-256) or Message Authentication Codes (MACs). If even a single bit of the original data changes, the resulting hash changes, allowing tampering to be detected.
- **Authentication** verifies the identity of a user, device, or system, or confirms the origin of a message. Cryptography enables authentication through mechanisms such as digital signatures, MACs, certificates, and challenge-response protocols. Authentication answers the question, "Who sent this data?" or "Who is this entity?"
- **Non-repudiation** ensures that a sender cannot later deny performing a particular action, such as sending a message or signing a document. This property is provided by digital signatures, which use asymmetric cryptography. Since only the owner's private key could have created a valid signature, anyone with the corresponding public key can verify it, making the action provable.

These four services are independent. A system may provide one without the others. For example, encrypting a file provides confidentiality but does not guarantee integrity or authenticity. A digital signature provides integrity, authentication, and non-repudiation, but it does not keep the data secret. In practice, secure systems combine multiple cryptographic mechanisms to achieve the required security properties.

### Historically:

Cryptography has evolved significantly over time. one of the very first ways was The Scytale. 

The Scytale was an ancient Spartan transposition cipher consisting of a wooden cylinder and a narrow strip of leather or parchment. To encrypt a message, the sender wrapped the strip tightly around the cylinder, wrote the message lengthwise, and then unwrapped it, leaving the letters completely scrambled. The receiver, possessing an identical cylinder of the exact same diameter, would wrap the strip around it to align the letters and reveal the original plaintext, making the cylinder’s precise diameter the secret cryptographic key.

One of the earliest and simplest encryption algorithms is the **Caesar cipher**, named after Julius Caesar, who reportedly used it to protect military communications.

The Caesar cipher is a substitution cipher in which each plaintext letter is shifted by a fixed number of positions in the alphabet. For example, using a shift of **3**, `A → D`, `B → E`, `C → F`, and so on. Mathematically, the encryption can be expressed as:

**`Encrypted Letter = (Original Letter + n) mod 26`** → where `n` is the agreed-upon shift value (the encryption key).

The Caesar cipher is insecure because its key space is very small. With the English alphabet, there are only 25 meaningful shift values, allowing an attacker to try every possible key in a brute-force attack until the correct plaintext is found.

To overcome this limitation, **monoalphabetic (simple) substitution ciphers** were developed. Instead of shifting every letter by the same amount, each plaintext letter is replaced with a unique, **randomly** chosen ciphertext letter. For example: `A → Q`, `B → K`, `C → M`, ...

The sender and receiver must agree on the substitution table before communication. Because there are `26!` (approximately **`4 × 10²⁶`**) possible substitution tables, brute-force attacks are no longer practical.

Despite the much larger key space, monoalphabetic substitution ciphers remain vulnerable because they preserve the f**requency of letters**. Since each plaintext letter is always replaced by the same ciphertext letter, common letters such as `E`, `T`, and `A` remain the most frequent in the ciphertext. Attackers exploit these statistical patterns using frequency analysis, along with common letter combinations and words, to reconstruct the substitution table. Modern computers automate this process using statistical analysis and language models, making these ciphers unsuitable for secure communication.

> # Cryptography - Fundamental Concepts and Terminology
> 
> Cryptography is broader than encryption. It includes several techniques that solve different security problems:
> 
> - **Encryption:** Protects confidentiality by making data unreadable without the appropriate key.
> - **Hashing:** Produces a fixed-length digest used to detect changes and support other security mechanisms.
> - **Message authentication codes (MACs):** Help verify data integrity and authenticity using a shared secret key.
> - **Digital signatures:** Support integrity verification, authentication of the signing key, and evidence useful for non-repudiation.
> 
> Cryptography is one part of information security. It does not replace access control, secure configuration, patching, or other security measures.
> 
> ## Cryptography vs. Encryption
> 
> These terms are related, but they are not interchangeable.
> 
> | Term | Meaning |
> | --- | --- |
> | Cryptography | The broader field of securing information using cryptographic techniques. |
> | Encryption | A cryptographic process that transforms readable data into an unintelligible form to protect confidentiality. |
> | Decryption | The process of recovering the original data from encrypted data using the appropriate key. |
> 
> For example, **TLS** uses cryptography for more than encryption: it also uses mechanisms to authenticate peers and protect the integrity of communications.
> 
> ## Plaintext and Ciphertext
> 
> These terms describe data before and after encryption.
> 
> - **Plaintext:** Data in its original, readable or usable form before encryption. It does not have to be ordinary text; it can be a file, image, database record, or other binary data.
> 
> - **Ciphertext:** The output of encryption. It should not reveal the protected information to an unauthorized party when the cryptographic system is used correctly.
> 
> **Example:**
> 
> ```
> Plaintext
>     |
>     | Encryption + key
>     v
> Ciphertext
>     |
>     | Decryption + appropriate key
>     v
> Plaintext
> ```
> 
> A file encrypted with a strong, correctly implemented algorithm can still be compromised if its key is stolen or exposed.
> 
> ### Cipher and Cryptographic Algorithm
> 
> A cipher is an **algorithm used to perform encryption** and, where applicable, the corresponding decryption.
> 
> For example, AES (Advanced Encryption Standard) is a symmetric-key block cipher. It encrypts and decrypts data using the same secret key.
> 
> The term cryptographic algorithm is **broader**: it can refer to encryption algorithms, hash functions, signature algorithms, key-agreement algorithms, and other cryptographic operations.
> 
> A cipher is not the same as a key:
> 
> - **Algorithm/cipher:** Defines the mathematical operations.
> - **Key:** A value supplied to the algorithm that determines the particular cryptographic operation.
> 
> A fundamental principle of modern cryptography is that security should generally depend on keeping keys secret, not on keeping the algorithm secret. Standardized algorithms can be publicly studied and reviewed.
> 
> ## Cryptographic Key
> 
> A cryptographic key is a value used by a cryptographic algorithm to encrypt, decrypt, authenticate, or otherwise process data securely.
> 
> The security of a cryptographic system depends heavily on key strength, key protection, and correct key management.
> 
> Common key-related terms:
> 
> - **Secret key:** A key that must be protected from unauthorized access.
> - **Public key:** A key that can be shared publicly in an asymmetric cryptographic system.
> - **Private key:** The key in an asymmetric pair that must remain under the owner's control.
> - **Key length:** The number of bits in a key. For example, AES-256 uses a 256-bit key.
> 
> A longer key is not automatically more secure in every context; security also depends on the algorithm, implementation, and intended use.
> 
> ### Symmetric and Asymmetric Cryptography
> 
> Cryptographic algorithms are often categorized by how they use keys.
> 
> - **Symmetric-key cryptography**
> 
>     Symmetric cryptography uses the same secret key for encryption and decryption.
> 
>     ```
>     Plaintext + Secret Key
>               |
>            Encryption
>               |
>            Ciphertext
>               |
>            Decryption + Same Secret Key
>               |
>            Plaintext
>     ```
> 
> 
>     **Examples:**
> 
>     - **AES**
>     - **ChaCha20**
> 
>     Advantages include high performance and suitability for encrypting large amounts of data.
> 
>     The main challenge is securely sharing the secret key with the intended recipient.
> 
> - **Asymmetric-key cryptography**
> 
>     Asymmetric cryptography uses a mathematically related key pair: a **public key** and a **private key**.
> 
>     Depending on the algorithm and operation, the keys serve different roles:
> 
>     - **Encryption:** Data encrypted with the recipient's public key can generally be decrypted with the corresponding private key.
>     - **Digital signatures:** A private key creates a signature, and the corresponding public key verifies it.
>     - **Key agreement:** Algorithms such as Diffie–Hellman and elliptic-curve Diffie–Hellman allow parties to establish shared secret material.
> 
>     Examples:
>     - RSA
>     - Elliptic-curve cryptography (ECC)
>     - Diffie–Hellman (DH) and elliptic-curve Diffie–Hellman (ECDH)
> 
>     **Important:** Not every asymmetric algorithm supports every operation. For example, Diffie–Hellman is used for key agreement, not direct encryption or digital signatures.
> 
>     Asymmetric cryptography can help solve key-establishment and authentication problems, but it is generally more computationally expensive than symmetric encryption. Real-world protocols such as **TLS commonly combine both approaches**.
> 
> ---
> 
> ### Hashing and Hash Functions
> 
> A cryptographic hash function takes input data of arbitrary length and produces a fixed-length output called a hash or digest.
> 
> ```
> Input data
>     |
> Hash function
>     |
> Fixed-length digest
> ```
> 
> For example, SHA-256 produces a 256-bit digest regardless of the input size.
> 
> Important properties of a secure cryptographic hash function include:
> 
> - **Preimage resistance:** Given a digest, it should be computationally infeasible to find an input that produces it.
> - **Second-preimage resistance:** Given an input, it should be computationally infeasible to find a different input with the same digest.
> - **Collision resistance:** It should be computationally infeasible to find any two distinct inputs with the same digest.
> Unlike encryption, hashing is designed to be one-way: there is no decryption key that recovers the original input from the digest.
> 
> Examples include SHA-256 and SHA-3. MD5 and SHA-1 are no longer considered secure for collision-resistant applications.
> 
> **Important security distinction:** A plain hash alone does not authenticate who sent a message. An attacker who can modify both the data and its stored hash can calculate a new hash. Use a MAC or digital signature when authentication is required.
> 
> ### MAC and HMAC
> A **Message Authentication Code (MAC)** is a cryptographic value used to check the integrity and authenticity of data using a shared secret key.
> 
> A **Hash-based Message Authentication Code (HMAC)** is a type of MAC constructed using a cryptographic hash function and a secret key.
> 
> For example, if two parties share a secret key, the sender can generate an HMAC for a message. The recipient independently calculates the expected HMAC using the same key and compares the results.
> 
> A valid HMAC provides evidence that the message has not been modified and was generated by someone possessing the shared key, assuming the cryptographic system is secure.
> 
> > However, because both parties share the same key, HMAC does not independently prove which party created the message and does not provide public verifiability.
> 
> ### Digital Signatures
> 
> A digital signature is a cryptographic mechanism that allows a recipient to verify a signature using the corresponding public key.
> 
> **Conceptually:**
> 
> 1. The signer uses their private key to create a signature for the data.
> 2. The recipient uses the corresponding public key to verify the signature.
> 3. Successful verification supports the integrity of the signed data and establishes that the signature was produced using the corresponding private key, assuming the algorithm and implementation are secure.
> 
> Digital signatures are commonly used for software packages, certificates, documents, and secure communication protocols.
> 
> > A digital signature does not automatically prove a real-world identity. That association requires a trusted process, such as a properly validated digital certificate. Likewise, non-repudiation is not guaranteed by mathematics alone; key control, identity verification, system security, and applicable legal processes also matter.
> 
> ### Encoding Is Not Encryption
> 
> Encoding transforms data into a different representation, usually to support storage, transmission, or compatibility. It does not inherently provide confidentiality.
> 
> For example, `Base64` converts binary data into a text representation:
> 
> ```
> Hello → SGVsbG8=
> ```
> 
> Anyone can decode `Base64` without a secret key.
> 
> | Concept | Main purpose | Requires a secret key? |
> | --- | --- | --- |
> | Encryption | Confidentiality | Yes, in the cryptographic sense|
> | Encoding | Data representation or compatibility | No |
> | Hashing | Fixed-length digest for integrity-related uses | No |
> | Digital signature | Signature creation and verification | Private key to sign; public key to verify |
> | MAC/HMAC | Integrity and shared-key authenticity | Yes |
> 
> Encoding can be used alongside encryption, but it is not a substitute for it.
> 
> ### Salt, Nonce, and Initialization Vector (IV)
> 
> These terms refer to additional values used in particular cryptographic operations. They have different purposes and should not be treated as interchangeable.
> 
> - **Salt:** A value added to password hashing to make identical passwords produce different stored results when different salts are used. Salts are generally not secret.
> - **Nonce:** A value intended to be used only once within a defined cryptographic context. Correct uniqueness requirements depend on the algorithm.
> - **Initialization Vector (IV):** A value used by certain encryption modes to initialize the encryption process. Its requirements vary by mode; some require uniqueness, others require unpredictability.
> 
> For example, modern authenticated encryption such as AES-GCM requires that a nonce never be reused with the same key. Reusing a nonce in this context can seriously compromise security.
> 
> These values do not replace the cryptographic key and do not necessarily need to be secret.
> 
> ### Key Exchange and Key Management
> 
> Key exchange or key agreement establishes shared secret material between parties. Some mechanisms involve exchanging key-related values; others allow both parties to derive a shared secret without transmitting that secret directly.
> 
> For example, Diffie–Hellman allows two parties to derive a shared secret over a network. By itself, ordinary Diffie–Hellman does not authenticate the participants, so an attacker could perform a man-in-the-middle attack unless authentication is added.
> 
> Key management covers the key's lifecycle, including:
> - Secure generation
> - Distribution and establishment
> - Storage and access control
> - Rotation and expiration
> - Revocation, backup, and destruction
> 
> Poor key management can undermine even strong cryptographic algorithms.
> 
> ### Digital Certificates and PKI
> 
> A digital certificate binds an identity or subject to a public key through a digitally signed statement, commonly issued by a Certificate Authority (CA).
> 
> Public Key Infrastructure (PKI) is the collection of roles, policies, processes, and technologies used to issue, validate, manage, and revoke certificates and their associated trust relationships.
> 
> For example, when a browser validates a website's TLS certificate, it checks matters such as the certificate chain, validity period, hostname, and relevant trust and usage requirements.
> 
> A certificate does not make a system secure by itself. Its value depends on correct validation, trusted issuers, private-key protection, and proper configuration.
> 
> ### Brute-Force Attacks and Cryptanalysis
> 
> - **Brute-force attack:** Attempts many possible keys or passwords until the correct one is found. Resistance depends on factors such as key-space size, password quality, rate limits, and computational resources.
> - **Cryptanalysis:** The study and application of techniques to analyze or attack cryptographic systems, potentially recovering secret information or finding weaknesses without simply trying every possible key.
> These are different concepts: brute force is one possible attack approach, while cryptanalysis is a broader field that includes many techniques.
> 
> For password storage, a fast general-purpose hash such as SHA-256 is usually not suitable on its own. Passwords should be stored using a purpose-built password-hashing scheme such as Argon2id, scrypt, or appropriately configured bcrypt, with unique salts and suitable parameters.
> 
> ### Data at Rest and Data in Transit
> 
> Cryptography is frequently discussed in terms of when and where data needs protection.
> 
> - **Data at rest:** Data stored on disks, SSDs, backups, or other storage. Full-disk encryption and file-level encryption can help protect it.
> - **Data in transit:** Data moving between systems over a network. TLS and properly configured VPNs are common ways to protect it.
> 
> Encryption at rest does not necessarily protect data after a system has unlocked it, and encryption in transit does not protect compromised endpoints. Security depends on the threat model and implementation.
>

# Symmetric and Asymmetric Cryptography

Cryptographic algorithms can be classified according to how they use keys. Two fundamental categories are **symmetric-key cryptography** and **asymmetric-key cryptography**.

- **Symmetric cryptography:** Uses the same secret key for encryption and decryption.
- **Asymmetric cryptography:** Uses a mathematically related public/private key pair for operations such as encryption and decryption, digital signatures, or key agreement, depending on the algorithm.

These approaches solve different problems and are frequently combined in modern security protocols.

- # Symmetric Cryptography

    Symmetric cryptography, also called *secret-key cryptography*, uses a shared secret key. Both parties must possess the appropriate key and protect it from unauthorized access.

    ### How It Works

    ```text
    Plaintext
        |
        | Encrypt using Secret Key
        v
    Ciphertext
        |
        | Decrypt using the Same Secret Key
        v
    Plaintext
    ```

    The sender encrypts the data using the secret key, and the receiver uses the same key to decrypt it.

    ### Advantages

    - **High performance:** Symmetric algorithms are generally much faster than public-key operations.
    - **Efficiency:** Suitable for encrypting large amounts of data.
    - **Lower computational overhead:** Particularly useful for continuous data transfer and storage encryption.

    ### Disadvantages

    - **Secure key establishment:** Both parties must obtain the same secret key securely.
    - **Key management complexity:** Each communicating pair may need its own shared key.
    - **Limited attribution:** Sharing a key does not independently prove which party created a message, because either party can generate a valid result using that key.

    If every pair among \(n\) users needs a separate shared secret, the number of keys required is:

    ```
    n(n-1)/2
    ```

    For example, 10 users would require 45 pairwise keys. This illustrates the scaling challenge of managing individual shared secrets.

    ### Common Algorithms

    - **AES (Advanced Encryption Standard):** A widely used symmetric block cipher. AES supports 128-, 192-, and 256-bit keys.
    - **ChaCha20:** A widely used symmetric stream cipher. It is commonly paired with Poly1305 for authenticated encryption.
    - **3DES (Triple DES):** A legacy cipher that is no longer recommended for modern applications.
    - **DES (Data Encryption Standard):** Obsolete because its 56-bit effective key is too small to resist modern brute-force attacks.

    **Important:** Encryption alone does not necessarily provide integrity or authenticity. Modern applications commonly use authenticated encryption with associated data (AEAD), such as AES-GCM or ChaCha20-Poly1305, to provide confidentiality and detect unauthorized modifications.

    ### Typical Uses

    - Disk encryption, such as LUKS and BitLocker
    - VPN data encryption
    - TLS application-data encryption
    - Wi-Fi security protocols
    - Database and file encryption
    - Encrypted backups and storage

- # Asymmetric Cryptography

    Asymmetric cryptography, also called *public-key cryptography*, uses two mathematically related keys:

    - **Public key:** Can be distributed openly.
    - **Private key:** Must be protected by its owner.

    The keys have different roles depending on the algorithm and operation. Not every asymmetric algorithm supports both encryption and digital signatures.

    - ## Public-Key Encryption

        In a public-key encryption scheme, a sender can encrypt data using the recipient's public key. The corresponding private key is required to decrypt it.

        ```text
        Sender:
        Plaintext
            |
            | Encrypt using Recipient's Public Key
            v
        Ciphertext
            |
            | Send
            v
        Recipient:
        Decrypt using Recipient's Private Key
            |
            v
        Plaintext
        ```

        This can provide confidentiality because someone who possesses only the public key should not be able to recover the plaintext.

        However, **public-key encryption does not automatically authenticate the sender**. Anyone who knows the recipient's public key can generally encrypt a message to that recipient.

    - ## Digital Signatures

        Digital signatures provide a different capability. The signer uses their private key to generate a signature, and other parties use the corresponding public key to verify it.
        
        ```text
        Sender:
        Message + Private Signing Key
                      |
                   Sign
                      |
                      v
                   Signature
                      |
               Send Message + Signature
                      |
                      v
        Recipient:
        Message + Signature + Public Key
                      |
                   Verify
                      |
                      v
               Valid or Invalid
        ```
        
        In practice, signature algorithms typically operate on a cryptographic digest of the message or use a defined signature construction that processes the message.
        
        A successful verification supports the following conclusions:
        
        - **Integrity:** The signed data has not been changed since it was signed, subject to the security of the algorithm and implementation.
        - **Signing-key authentication:** The signature was produced using the private key corresponding to the verification key, assuming the scheme is secure.
        
        To associate that public key with a real-world identity, the recipient needs a trustworthy way to establish whose key it is — for example, a properly validated digital certificate.
        
        Digital signatures can support non-repudiation, but they do not guarantee it by themselves. Private-key control, identity verification, system security, and legal context also matter.
        
### Advantages

- **Easier public-key distribution:** Public keys can be shared openly without revealing private keys.
- **Digital signatures:** Enables public verification of signatures.
- **Key agreement:** Certain asymmetric algorithms allow parties to establish shared secret material over an insecure network.
- **Scalability:** Public-key systems can reduce the need to maintain a separate pre-shared secret for every communicating pair.

### Disadvantages

- **Higher computational cost:** Public-key operations are generally more expensive than symmetric encryption.
- **Algorithm-specific capabilities:** Some algorithms support signatures, others support key agreement or encryption; these functions are not interchangeable.
- **Authentication and trust requirements:** Public keys must be reliably associated with the intended identities.
- **Private-key protection:** Compromising a private key can undermine the security properties that depend on it.

Asymmetric cryptography helps address key-establishment and authentication challenges, but it does not eliminate key management or the need to establish trust.

### Common Algorithms and Families

- **RSA:** Can support public-key encryption and digital signatures when used with appropriate schemes. RSA key transport is not supported in TLS 1.3.
- **ECC (Elliptic Curve Cryptography):** A family of cryptographic techniques based on elliptic curves.
- **ECDSA:** An elliptic-curve digital signature algorithm.
- **Ed25519:** A digital signature scheme.
- **Diffie–Hellman (DH):** A key-agreement method.
- **ECDH / ECDHE:** Elliptic-curve Diffie–Hellman key agreement; ECDHE uses ephemeral key pairs to support forward secrecy when properly implemented.

**Terminology note:** RSA is an algorithm; ECC is a family; ECDSA and Ed25519 are signature schemes; DH and ECDH are key-agreement methods. These should not be treated as interchangeable algorithms with identical capabilities.

### Typical Uses

- HTTPS/TLS authentication and key establishment
- SSH public-key authentication
- GPG/PGP email encryption and digital signatures
- Digital certificates and Public Key Infrastructure (PKI)
- Software-package and software-release signatures
- Digital document signatures

## Why Modern Systems Use Both

Modern secure protocols combine symmetric and asymmetric cryptographic techniques because each is suited to a different task.

- **Asymmetric cryptography:** Can authenticate identities, verify signatures, and establish shared secret material.
- **Symmetric cryptography:** Efficiently encrypts and authenticates large amounts of data.

For example, TLS uses public-key cryptography and key agreement during connection establishment, then symmetric authenticated encryption for application data.

This combination is often called a *hybrid cryptographic system*.

## Signing and Encryption: Does the Order Matter?

Suppose Node 1 wants to send a confidential message to Node 2 while also providing evidence that the message was signed using Node 1's private key.

Two separate security goals are involved:

- **Confidentiality:** Encrypt the message for Node 2.
- **Integrity and signing-key authentication:** Sign the appropriate data using Node 1's private key.

There are two conceptual constructions.

- ### Approach A: Encrypt, Then Sign

   ```text
   Message
      |
   Encrypt using Node 2's Public Key
      |
   Ciphertext
      |
   Sign the Ciphertext using Node 1's Private Key
      |
   Send Ciphertext + Signature
   ```

   Node 2 can first verify the signature using Node 1's trusted public key. If verification succeeds, Node 2 can decrypt the ciphertext using its private key.

   This construction can allow signature verification before decryption. However, the signature may be visible to observers, and the ciphertext is publicly verifiable by anyone who has Node 1's public key.

- ### Approach B: Sign, Then Encrypt

   ```text
   Message
      |
   Sign using Node 1's Private Key
      |
   Message + Signature
      |
   Encrypt for Node 2
      |
   Send Ciphertext
   ```

   Node 2 first decrypts the received ciphertext using its private key, then verifies the signature using Node 1's public key.

   This construction conceals the signature inside the encrypted message, so an observer without the decryption key cannot directly inspect or verify it.

### Which Approach Is Better?

**There is no universal rule that one ordering is always more secure.** The correct choice depends on the protocol's security requirements, including confidentiality, sender privacy, replay protection, identity binding, and error handling.

Neither construction should be designed casually. For real systems, use established protocols and reviewed cryptographic libraries rather than inventing a custom combination of encryption and signatures.

Also, the signature must be checked against a public key that is reliably associated with Node 1. Otherwise, successful verification does not establish Node 1's identity.

# How HTTPS/TLS Uses Both Types

When a client connects to a server using HTTPS, TLS protects the communication between them. For the usual HTTPS-over-TCP connection, the sequence is as follows.

## The big picture

```text
┌─────────────────────────────────────────────────────────────────┐
│                       Browser (client)                          │
│            Wants to connect securely to example.com             │
└─────────────────────────────────────────────────────────────────┘
                               ↓↑
                TCP connection, then TLS handshake
┌─────────────────────────────────────────────────────────────────┐
│                         Web server                              │
│         Has a certificate and corresponding private key         │
└─────────────────────────────────────────────────────────────────┘
 ───────────────────────────────────────────────────────────────── 
┌─────────────────────────────────────────────────────────────────┐
│ Certificate Authority (CA)                                      │
│ Previously issued and signed the server's certificate.          │
│                                                                 │
│ The browser trusts certain root CAs through its trust store.    │
│ During the connection, it validates the certificate chain       │
│ using those trusted roots. The CA normally does not need        │
│ to be contacted.                                                │
└─────────────────────────────────────────────────────────────────┘
```

There are two distinct stages to understand:
- **Before the connection:** the CA verifies the domain-control requirements under its issuance process and issues a certificate that binds a domain name to a public key.
- **During the connection:** the server presents that certificate, and the browser checks whether it can trust it. The browser and server then establish keys for encrypted communication.

The CA does not usually generate the TLS session keys, see the HTTPS data, or decrypt the session.

Suppose you enter: `https://example.com`

- ## **Step 1** — DNS resolution

   The browser needs the IP address associated with `example.com`.
   1. The browser may first check its own DNS cache.
   2. If the answer is not cached, the operating system may check its DNS cache and configuration.
   3. A DNS resolver is queried to obtain the IP address. Depending on the environment, this may involve a recursive DNS resolver and several DNS servers.
   4. The browser receives an address, for example `93.184.216.34` (illustrative only).

   The browser now knows which IP address to connect to.

   **Important:** DNS resolution does not, by itself, establish a secure HTTPS connection or prove that the server is trustworthy. DNS can be protected by technologies such as DNSSEC or encrypted DNS, but TLS still performs its own server authentication.

   ---

- ## **Step 2** — The browser prepares to connect

   For conventional HTTPS over TCP, the browser normally connects to the server's TCP port 443.

   It has two main jobs:
   - Establish a reliable TCP connection.
   - Establish a secure TLS session over that connection.

   TCP and TLS solve different problems:

   | Protocol | Main responsibility |
   | --- | --- |
   | DNS | Finds an IP address for the domain |
   | TCP | Provides a reliable, ordered byte stream |
   | TLS | Authenticates the server and protects communication cryptographically |
   | HTTP | Defines the web requests and responses |

   ---

- ## **Step 3** — TCP three-way handshake

   TCP establishes the transport connection before the TLS handshake begins.

   Assume the browser is the client and the web server is listening on TCP port 443.
   Browser

   ```
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │         │ 1. SYN →                                                                   │
   │ Browser │          The client sends a TCP segment with the SYN flag set.             │
   │         │          It requests a connection and proposes an initial sequence number. │
   │   ───────────────────────────────────────────────────────────────────────────────    │
   │         │ 2. ← SYN-ACK                                                               │
   │ Server  │          The server acknowledges the client's SYN and sends                │
   │         │          its own SYN with its own initial sequence number.                 │
   │   ───────────────────────────────────────────────────────────────────────────────    │
   │         │ 3. ACK →                                                                   │
   │ Browser │         The client acknowledges the server's SYN.                          │
   │         │         The TCP connection is now established.                             │
   └──────────────────────────────────────────────────────────────────────────────────────┘
   ```

   **What do the flags mean?**

   - **SYN (synchronize):** starts connection establishment and synchronizes sequence numbers.
   - **ACK (acknowledgment):** acknowledges received TCP sequence space.
   - **Sequence numbers:** help TCP keep track of byte positions and deliver data in order.
   - **Acknowledgment numbers:** indicate the next sequence number expected from the other side.

   For example, if a client sends a `SYN` with initial sequence number `1000`, the server normally acknowledges it with `ACK` number `1001`, because the `SYN` consumes one sequence number. The exact values are chosen by the endpoints.

   TCP also handles retransmission of lost data, flow control, and congestion control. It does not encrypt the data or authenticate the website's identity.

   At this point, the TCP connection exists, but it is not yet protected by TLS. The browser and server have not yet established the TLS encryption keys.

- ## Before the handshake: how the CA issued the certificate

   This is where the CA fits into the bigger story.

   A web server administrator needs a TLS certificate for `example.com`. A simplified certificate-issuance process looks like this:

   ```
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ 1. The server operator creates a key pair                                            │             
   │    The operator generates a private key and its corresponding public key.            │
   │    The private key must be kept secret.                                              │
   │   ───────────────────────────────────────────────────────────────────────────────    │
   │ 2. The operator creates a CSR                                                        │
   │    A Certificate Signing Request (CSR) contains the public key and requested         │
   │    certificate information, such as the domain name. It is submitted to a CA.        │
   │   ───────────────────────────────────────────────────────────────────────────────    │
   │ 3. The CA validates domain control                                                   │
   │    The CA follows its issuance procedures to verify that the requester is authorized │ 
   │    to obtain a certificate for the domain. For a typical domain-validated            │
   │    certificate, this is domain-control validation, not a full investigation of the   │ 
   │    website's business identity.                                                      │
   │   ───────────────────────────────────────────────────────────────────────────────    │     
   │ 4. The CA issues and signs the certificate                                           │
   │    The CA creates a certificate binding the domain name to the server's public key   │ 
   │    and signs the certificate using the CA's private signing key.                     │
   │   ───────────────────────────────────────────────────────────────────────────────    │  
   │ 5. The server installs its certificate and private key                               │
   │    The server is configured with its certificate, typically the required intermediate│
   │    certificates, and its corresponding private key. The CA's signing private key is  │
   │    not installed on the web server.                                                  │
   └──────────────────────────────────────────────────────────────────────────────────────┘
   ```

   **What is inside a certificate?**

   A typical TLS server certificate includes:
   - **Subject Alternative Name (SAN):** the DNS names or IP addresses for which the certificate is valid.
   - **Subject and issuer:** information identifying the certificate's subject and the CA that issued it.
   - **Public key:** the server's certificate public key.
   - **Validity period:** the certificate's not-before and not-after timestamps.
   - **Key usage and extended key usage:** constraints on how the key and certificate may be used.
   - **Signature:** the CA's digital signature over the certificate's signed data.

   The CA uses its private signing key to create the signature. The browser can verify that signature using the corresponding CA public key, which it obtains through the certificate chain and its trust store.

   ### The certificate chain

   A common chain has three levels:

   ```
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │                               Root CA certificate                                │ │
   │ │ Its public key is trusted through the browser or operating system's trust store. │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │                                         ↓                                            │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │                          Intermediate CA certificate                             │ │
   │ │             Signed by the root CA or another trusted intermediate.               │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │                                         ↓                                            │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │                           Server (leaf) certificate                              │ │
   │ │        Names example.com and contains the server's certificate public key.       │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   └──────────────────────────────────────────────────────────────────────────────────────┘
   ```

   The browser or operating system already has a set of trusted root CA certificates. The server commonly sends its leaf certificate and necessary intermediate certificates during the handshake. It normally does not need to send the root certificate, because the client should already have an appropriate trust anchor.

   A root certificate is often self-signed, but a self-signature alone does not make it trusted. Trust comes from the client trusting that root certificate through its configured trust store or another applicable trust mechanism.

   Now let's see how the browser uses this chain during the actual connection.

- ## **Step 4** - TLS 1.3 handshake
   The TCP connection is established. Now the browser and server need to agree on cryptographic parameters, authenticate the server, and derive the keys used to protect their communication.

   A full TLS 1.3 handshake usually follows this sequence:

   ```
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │ Browser → ClientHello                                                            │ │
   │ │ Proposes TLS settings and sends a key share.                                     │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │  ↓                                                                                   │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │ Server → ServerHello                                                             │ │
   │ │ Selects settings and sends its key share.                                        │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │  ↓                                                                                   │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │ Both sides derive handshake keys                                                 │ │
   │ │ They use the key-agreement result and handshake information to derive keys.      │ │
   │ │ The server's remaining handshake messages are now encrypted.                     │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │  ↓                                                                                   │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │ Server → EncryptedExtensions, Certificate, CertificateVerify, Finished           │ │
   │ │ Sends negotiated settings, proves its certificate-based identity,                │ │
   │ │ and confirms the handshake.                                                      │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │  ↓                                                                                   │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │ Browser → Finished                                                               │ │
   │ │ Confirms its side of the handshake.                                              │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   │  ↓                                                                                   │
   │ ┌──────────────────────────────────────────────────────────────────────────────────┐ │
   │ │ Protected HTTP communication                                                     │ │
   │ │ The browser and server exchange application data using symmetric authenticated   │ │
   │ │ encryption.                                                                      │ │
   │ └──────────────────────────────────────────────────────────────────────────────────┘ │
   └──────────────────────────────────────────────────────────────────────────────────────┘
   ```

   The exact messages can vary depending on the TLS configuration and features in use. The sequence above describes the common full TLS 1.3 handshake, without session resumption or optional client-certificate authentication.

   - ### **Step 4.1** — ClientHello

      The browser sends a TLS message called ClientHello.

      It includes information such as:

      | Field | Purpose |
      | --- | --- |
      | `supported_versions` | Lists the TLS versions the client supports, such as TLS 1.3. |
      | `cipher_suites` | Lists supported TLS cipher suites, which specify the symmetric protection and hash algorithms used by TLS. |
      | `supported_groups` | Lists supported key-agreement groups, such as X25519. |
      | `key_share` | Contains a public key-agreement value for a supported group. |
      | `signature_algorithms` | Lists supported digital-signature algorithms. |
      | `server_name` (SNI) | Normally identifies the requested hostname, `example.com`. |
      | `ALPN` | May advertise application protocols such as HTTP/2 and HTTP/1.1. |
      | Random and other fields | Provide handshake-specific values and additional protocol information. |

      SNI helps a server hosting multiple websites on one IP address identify which hostname the client wants. Without additional protection such as Encrypted ClientHello (ECH), the hostname in ordinary SNI is generally visible to observers of the connection.

      **What is a key share?**

      For a common key-agreement method such as ECDHE, the browser creates an ephemeral key pair:

      - An ephemeral private value, kept secret by the browser.
      - A corresponding public value, which it sends in ClientHello.

      The server will generate its own ephemeral key pair and return its public value.

      These ephemeral keys are separate from the server's certificate key. The browser is not yet sending its HTTP request; it is negotiating the secure connection.

      > The point of sharing ephemeral keys is to let the browser and server create the same secret key without ever sending that secret over the network.
      > 
      > Let's build it up step by step.
      >
      > ### The problem they need to solve
      >
      > The browser and server want to encrypt their communication using symmetric encryption, such as AES-GCM.
      > 
      > Symmetric encryption requires both sides to have the same secret key (Both sides need the key, but an attacker listening to the network must not learn it.)
      >
      > But how can they agree on a secret key when they have never communicated before?
      >
      > If the browser simply generated an AES key and sent it to the server, an attacker could intercept it and decrypt the communication.
      >
      > They need a way to establish a shared secret without transmitting the secret itself. This is what ephemeral Diffie–Hellman key exchange helps them do.
      >
      > ### How ephemeral key exchange works
      >
      > Imagine the browser and server each create a temporary key pair.
      >
      > ```
      > ┌──────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
      > │ Step 1 — Each side creates a temporary key pair                                                              │
      > │                                                                                                              │
      > │ Browser                         │ Server                                                                     │
      > │ Private value: A (secret)       │ Private value: B (secret)                                                  │
      > │ Public value: Pₐ                │ Public value: Pᵦ                                                           │
      > │                                                                                                              │
      > │ The private values never leave their respective sides.                                                       │
      > │ ──────────────────────────────────────────────────────────────────────────────────────────────────────────── │
      > │ Step 2 — They exchange only public values                                                                    │
      > │                                                                                                              │
      > │ ┌──────────────────┐  →  ┌──────────────────┐                                                                │
      > │ │   Browser's Pₐ   │  ←  │   Server's Pᵦ    │                                                                │
      > │ └──────────────────┘     └──────────────────┘                                                                │
      > │ The browser sends Pₐ to the server, and the server sends Pᵦ to the browser.                                  │
      > │ ──────────────────────────────────────────────────────────────────────────────────────────────────────────── │
      > │ Step 3 — Each independently calculates the same secret                                                       │
      > │                                                                                                              │
      > │ ┌─────────────────────────────────────────────┐ ┌─────────────────────────────────────────────┐              │
      > │ │ Browser calculates                          │ │ Server calculates                           │              │
      > │ │  Uses its private A and server's public Pᵦ. │ │ Uses its private B and browser's public Pₐ. │              │
      > │ └─────────────────────────────────────────────┘ └─────────────────────────────────────────────┘              │ 
      > │ Both calculations produce the same shared secret, but the secret itself is never sent over the network.      │
      > └──────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
      > ```
      >
      > The mathematics behind Diffie–Hellman allows both sides to calculate the same result using their own private value and the other side's public value. Someone who merely observes the exchanged public values should not be able to feasibly calculate the shared secret.
      >
      > The actual TLS algorithms use carefully defined cryptographic mathematics; the letters above are just a simplified representation.
      >
      > **Why are the keys called ephemeral?**
      >
      > Ephemeral means **temporary**.
      > 
      > The browser and server generate fresh key-agreement material for the connection rather than relying on a permanent key pair for every session.
      > 
      > This provides an important security property called **forward secrecy**.
      > 
      > Suppose an attacker records today's encrypted HTTPS traffic and, months later, steals the server's certificate private key.
      > 
      > If the connection used ephemeral Diffie–Hellman correctly and the ephemeral secrets were erased, stealing the certificate private key alone should not let the attacker decrypt those previously recorded sessions.
      > 
      > The certificate private key authenticates the server; the ephemeral key agreement establishes the shared secret material used to derive the session's encryption keys. These are separate jobs.
      >
      > **Remember:** ephemeral public keys help the browser and server agree on secret key material; the server's certificate and signature help the browser verify who it is establishing that secret with.
      > 
      > ### why using ephemeral keys and not using the permanent keys?
      >
      > The main benefit is that stealing the server's permanent certificate private key later does not normally allow an attacker to decrypt previously recorded sessions. This property is called forward secrecy.
      >
      >Let's compare the two approaches.
      > - **If TLS relied on a permanent key to establish session secrets**
      >
      >   Imagine an older TLS connection using RSA key transport:
      >
      >   1. The attacker records the encrypted HTTPS traffic.
      >   2. Later, the attacker steals the server's permanent RSA private key.
      >   3. If the recorded session used that RSA key to encrypt the premaster secret, the attacker may recover that secret and derive the session keys.
      >   4. The attacker can then decrypt the recorded traffic.
      >
      > - **With ephemeral Diffie–Hellman (ECDHE)**
      >   1. The browser and server generate temporary key-agreement key pairs.
      >   2. They exchange public values and independently derive shared secret material.
      >   3. After the session, the temporary private values are erased when no longer needed.
      >   4. Later, an attacker steals the server's permanent certificate private key.
      >   5. That key alone is not enough to recover the shared secrets from previously recorded sessions, assuming the ephemeral secrets were erased and the cryptographic algorithms remain secure.
      >
      > **One nuance:** ephemeral keys aren't necessarily valid for a specific number of seconds. Their security benefit comes from using temporary private values and discarding them, not simply from having an expiration time.
      >
      > | Key type | Purpose | Typical lifetime |
      > | --- | --- | --- |
      > | Server certificate private key | Authenticates the server during TLS handshakes | Often months or years, depending on certificate/key policy |
      > | Ephemeral key-agreement private value | Helps establish shared secret material for a session | Temporary; discarded after its use |
      > | TLS traffic keys | Encrypt and authenticate data for a connection | Used during the relevant connection, with possible key updates |
      >
      > > ephemeral key pairs limit the impact of a later compromise of the server's permanent certificate key. They don't make a session immune to an attacker who compromises the server or its session secrets while the session is active.
      >
      > > ### When are ephemeral public keys transferred?
      > >
      > > The ephemeral public keys are transmitted in **steps 1 and 2 of the TLS handshake** — specifically, in the **ClientHello** and **ServerHello** messages.
      > >
      > > Let's map this to our previous flow.
      > >
      > > ### Where are the keys transmitted?
      > > ```
      > > ┌──────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
      > > │ Step 1 — ClientHello                                                                                         │
      > > │ Browser → Server                                                                                             │
      > > │                                                                                                              │
      > > │ The browser sends its ephemeral public key share in the key_share extension of ClientHello.                  │
      > > │                                                                                                              │
      > > │ Transmitted: public value                                                                                    │
      > > │                                                                                                              │
      > > │ Never transmitted: ephemeral private value                                                                   │
      > > │  ──────────────────────────────────────────────────────────────────────────────────────────────────────────  │
      > > │ Step 2 — ServerHello                                                                                         │
      > > │ Server → Browser                                                                                             │
      > > │                                                                                                              │
      > > │ The server sends its own ephemeral public key share in the key_share extension of ServerHello.               │
      > > │                                                                                                              │
      > > │ Transmitted: public value                                                                                    │
      > > │                                                                                                              │
      > > │ Never transmitted: ephemeral private value                                                                   │
      > > │  ──────────────────────────────────────────────────────────────────────────────────────────────────────────  │
      > > │ After ServerHello                                                                                            │
      > > │ Both sides calculate locally                                                                                 │
      > > │                                                                                                              │ 
      > > │ The browser and server use their own private values and the other side's public value to independently       │ 
      > > │ derive the same shared secret.                                                                               │
      > > │                                                                                                              │
      > > │ The shared secret itself is never transmitted.                                                               │
      > > └──────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
      > > ```
      > > 
      > > **What about the other keys?**
      > >
      > > | Key or value | Transmitted? | Where? |
      > > | --- | --- | --- |
      > > | Browser's ephemeral public key share | Yes | ClientHello |
      > > | Server's ephemeral public key share | Yes | ServerHello |
      > > | Ephemeral private values | No | Remain secret on each side |
      > > | Derived shared secret | No | Calculated independently by both sides |
      > > | Server's certificate public key | Yes, as part of the certificate | Certificate message |
      > > | Server's certificate private key | No | Used locally to sign CertificateVerify |
      > > | TLS traffic keys | No | Derived independently by both sides |
      > > 
      > > **The key distinction:** 
      > >
      > > TLS transmits public key-agreement values, not the private values or the resulting shared secret. Both sides use those public values to calculate the secret locally, then derive the symmetric keys that encrypt the HTTPS traffic.

      ---
   - ### **Step 4.2** — ServerHello

      The server responds with `ServerHello`.

      It selects compatible parameters and includes its own key share for the chosen key-agreement group.

      For example:
      - The client offers `TLS 1.3`.
      - The server selects `TLS 1.3`.
      - The client and server agree on a supported cipher suite.
      - Both sides have exchanged the public values needed for the selected key-agreement method.

      **How do they create the same secret without sending it?**

      Consider an illustrative **ECDHE** exchange:

      1. The browser has its ephemeral private value and the server's public value.
      2. The server has its ephemeral private value and the browser's public value.
      3. Each side performs the agreed key-agreement calculation locally.
      4. Both sides derive the same shared secret, assuming the protocol's mathematical requirements are met.

      **The shared secret itself is not sent across the network.**

      > An observer can see the exchanged public values, but should not be able to calculate the shared secret from them under the security assumptions of the selected algorithm.

      The ECDHE result is not used directly as the final HTTP encryption key. TLS uses a key-derivation function, HKDF, along with handshake context and transcript information to derive the relevant handshake and application traffic secrets and keys.

      Why is the server certificate key not doing this job?

      The server's certificate key is generally used to authenticate the handshake, while the ephemeral ECDHE keys are used to establish shared secret material.

      This separation is important. It is a central feature of modern TLS 1.3, and it enables forward secrecy when ephemeral key material is handled correctly.

      ---

   - ### **Step 4.3** — Both sides derive handshake keys

      After `ServerHello`, the browser and server have enough information to derive the TLS handshake traffic keys.

      They use these keys to protect subsequent handshake messages. In TLS 1.3, messages such as the server's certificate and Finished message are normally encrypted after `ServerHello`.

      The browser can therefore decrypt and process the server's protected handshake messages, but it has not yet accepted the server's identity as valid. That decision requires certificate and handshake verification.

      ---

   - ### **Step 4.4** — Server sends EncryptedExtensions

      The server sends `EncryptedExtensions`, which carries additional negotiated parameters that are not part of `ServerHello`.

      For example, this can include the application protocol selected through ALPN, such as HTTP/2.

      This message is protected using the handshake encryption keys.

      ---
   - ### **Step 4.5** — Server sends its Certificate

      The server sends a Certificate message containing its certificate chain, typically:

      - The leaf certificate for `example.com`.
      - Intermediate CA certificates needed to build a chain to a trusted root.

      This is the moment when the browser gets the certificate information it needs to authenticate the server.

      The CA usually does not join the connection at this point. The browser uses the certificates supplied by the server and the trust anchors already available locally.

      **How does the browser verify the certificate?**

      The browser performs a series of checks. The exact validation and revocation policies depend on the browser, operating system, and certificate ecosystem.

      1. **Build a certificate chain**. It attempts to link the server certificate through appropriate intermediate certificates to a trusted root or another permitted trust anchor.
      2. **Verify certificate signatures**. It checks that each certificate's signed contents are valid under the public key of the issuer certificate in the chain.
      3. **Check the hostname**. It checks that the certificate's Subject Alternative Name (SAN) covers `example.com`.
      4. **Check validity**. It checks the certificate's validity period against the relevant time.
      5. **Check usage and constraints**. It verifies relevant key-usage, extended-key-usage, and CA constraints.
      6. **Apply trust and policy checks**. Depending on the ecosystem and policy, this can include revocation information, certificate-transparency requirements, and other checks.

      If the chain cannot be trusted, the hostname does not match, the certificate is expired, or another mandatory validation fails, the browser should reject the connection or show a certificate error.

      **Where exactly does the CA's signature matter?**

      Imagine the server certificate says:

      > This public key is associated with `example.com`.

      The certificate also has a CA's digital signature. The browser checks that signature using the issuer CA's public key, following the chain to a trusted root.

      This helps establish that the certificate's signed contents have not been altered and that the certificate was signed by the corresponding issuer key.

      But the CA's signature on the certificate alone does not prove that the current network peer possesses the corresponding server private key. That is why TLS needs the next message.

   - ### **Step 4.6** — Server sends CertificateVerify

      The server sends `CertificateVerify`, which contains a digital signature made using the private key corresponding to the public key in its leaf certificate.
      
      This signature covers the TLS handshake transcript according to TLS 1.3's rules.
      
      The browser verifies the signature using the public key in the server certificate.
      
      This proves that the peer possesses the private key associated with that certificate and binds the proof to this particular handshake.
      
      These are two different cryptographic checks:

      - **Certificate signature verification:** checks the CA's signature on the certificate chain.
      - **CertificateVerify verification:** checks the server's proof of possession of its private key for this handshake.

      A valid certificate chain without a valid CertificateVerify is not sufficient to authenticate the server in this handshake.

      > **Certificate signature verification**
      >
      > This phrase:
      > 
      > ```
      > A valid CA has signed the server's public key, meaning the server administrator went through the certificate issuance process and proved ownership of the domain.
      > ```
      >
      > is Almost correct. More precisely:
      >
      > - The CA followed its issuance procedure and validated the required domain control or identity information.
      > - The CA issued a certificate containing the server's public key and the domain name, such as `example.com`.
      > - The CA signed the certificate's contents using its private signing key.
      > - The browser verifies that signature through a certificate chain leading to a trusted CA.
      >
      > This establishes that the certificate's signed information has not been altered and was signed by the corresponding CA key.
      > 
      > **One nuance:** for a typical domain-validated certificate, the CA verifies control of the domain, not necessarily legal ownership of the domain or the identity of the server administrator.
      >
      > **CertificateVerify verification**
      >
      > This phrase:
      >
      > ```
      > The server proves that it possesses the private key corresponding to the permanent public key in its certificate. It signs something with the private key, and the browser verifies it with the server's public key.
      > ``` 
      >
      > is Exactly right! There's one extra detail: 
      >
      > > The server signs data tied to the current TLS handshake, not just an arbitrary message.
      >
      > 1. The server uses its certificate's private key to create a digital signature over the handshake transcript, following TLS 1.3's **`CertificateVerify`** rules.
      > 2. The browser takes the signature and the relevant handshake data.
      > 3. It uses the public key in the server's certificate to verify the signature.
      > 4. If verification succeeds, the browser has evidence that the server possesses the corresponding private key and that the signature is tied to this handshake.
      >
      > This prevents an attacker from simply copying a legitimate server's public certificate and pretending to be that server without possessing its private key.
      >
      > **Compare the two checks**
      > | Check | What does it establish? |
      > | --- | --- |
      > | **Certificate signature verification** | The certificate was signed by the corresponding CA key, and its signed contents are intact. |
      > | **Certificate validation as a whole** | The browser can trust the certificate for the requested hostname under its applicable trust and validation rules. |
      > | **CertificateVerify verification** | The current server proves possession of the private key corresponding to the certificate's public key, tied to this handshake. |
      >
      > The distinction is that the CA vouches for the certificate, while the server proves possession of the corresponding private key during the handshake.
      >
      > **Both checks are necessary:** a trusted certificate alone does not prove that the current peer possesses its private key, and possession of a private key alone does not establish that the browser should trust that key for example.com.

      ---

   - ### **Step 4.7** — Server sends Finished

      The server sends a TLS Finished message.

      It contains a verification value calculated using a key derived from the TLS handshake secrets and a hash of the handshake transcript.

      The browser verifies it.

      This confirms that the server derived the expected handshake key material and that the handshake transcript matches what the server is confirming. It protects against undetected modification of the handshake messages.

      At this point, the browser has checked the certificate and hostname, verified the server's proof of private-key possession, and verified the server's handshake confirmation.

      ---

   - ### **Step 4.8** — Client sends Finished

      The browser sends its own Finished message, which the server verifies.

      For a typical HTTPS website that does not require client-certificate authentication, the browser usually does not send a certificate of its own. The server authenticates the website; it does not automatically authenticate the human user.

      The browser and server now have the information needed to use their derived application traffic keys for protected HTTP communication.

      The handshake is complete for this common flow.

   ---

- ## **Step 5** - The browser sends the HTTP request

   Now the browser can send its HTTP request, for example:

   ```
   GET / HTTP/1.1
   Host: example.com
   ```

   The exact HTTP version and request format depend on the negotiated application protocol. The example above is `HTTP/1.1`.

   Before transmission over TCP, TLS protects the HTTP data using its application traffic keys.

   ### How is the actual data encrypted?

   TLS uses symmetric authenticated encryption, commonly an **AEAD** algorithm such as:

   - AES-GCM
   - ChaCha20-Poly1305

   Symmetric cryptography uses secret keys to protect data efficiently. The browser and server have derived corresponding traffic keys, with separate protection for each direction.

   For each protected TLS record, TLS uses the selected **AEAD** algorithm to provide:

   - **Confidentiality:** outsiders cannot ordinarily read the HTTP content.
   - **Integrity:** modifications to the protected record are detected.
   - **Authenticity:** the record must have been produced by someone with the appropriate traffic key.

   The HTTP request is protected by TLS and carried over TCP. TCP divides the byte stream into segments as needed, retransmits lost data, and delivers bytes in order. The receiver's TLS implementation reconstructs and decrypts the protected records before passing the HTTP request to the web server.

   The server then processes the request and generates an HTTP response.

   ### Why not encrypt every HTTP message with the certificate's public key?

   Public-key cryptography is useful for authentication and key establishment, but it is generally much more computationally expensive than symmetric encryption for bulk data.

   In the modern TLS 1.3 flow:

   1. The server's certificate key authenticates the handshake.
   2. Ephemeral key agreement establishes shared secret material.
   3. **HKDF** derives the TLS traffic keys.
   4. Symmetric authenticated encryption protects the actual application data.

   This combines the strengths of different cryptographic techniques rather than using one algorithm for everything.

   > The symmetric keys used to encrypt application data are derived from the shared secret that the browser and server calculate using their own ephemeral private values and the other side's ephemeral public key share.
   >
   > But there's one important distinction: **the shared secret itself is not the final symmetric encryption key.**
   >
   > Here's the sequence in TLS 1.3:
   >
   > ```
   > ┌──────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
   > | Step 1 — ClientHello                                                                                         |
   > | The browser sends its ephemeral public key share to the server.                                              |
   > | ──────────────────────────────────────────────────────────────────────────────────────────────────────────── |
   > | Step 2 — ServerHello                                                                                         |
   > | The server sends its ephemeral public key share to the browser.                                              |
   > | ──────────────────────────────────────────────────────────────────────────────────────────────────────────── |
   > | Step 3 — Both calculate the shared secret                                                                    |
   > | Each side combines its own ephemeral private value with the other side's public key share to independently   |
   > | calculate the same shared secret.                                                                            |
   > |                                                       ↓                                                      |
   > | Step 4 — TLS derives traffic keys                                                                            |
   > | TLS uses HKDF (a key-derivation function), together with the handshake information, to derive cryptographic  |
   > | secrets and keys.                                                                                            |
   > |                                                       ↓                                                      |
   > |┌────────────────────────────────────────────────────────────────────────────────────────────────────────────┐|
   > || Step 5 — Application data encryption                                                                       ||
   > || TLS uses the derived client-to-server and server-to-client application traffic keys with an algorithm      ||
   > || such as AES-GCM or ChaCha20-Poly1305.                                                                      ||
   > |└────────────────────────────────────────────────────────────────────────────────────────────────────────────┘|
   > └──────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
   > ```
   > **Why not use the shared secret directly?**
   >
   > TLS needs a carefully defined process to derive separate keys for different purposes and directions. HKDF derives those keys from the shared secret and the TLS handshake context.
   > 
   > For example, TLS derives distinct application traffic keys for:
   >
   > - Browser → Server
   > - Server → Browser
   >
   > These are not necessarily identical keys.
   > 
   > Remember the distinction:
   >
   > - Ephemeral key agreement: establishes shared secret material.
   > - HKDF: derives the actual traffic keys from TLS secrets and handshake context.
   > - Symmetric authenticated encryption: uses those traffic keys to protect the HTTP requests and responses.
   >
   > So your idea is correct, with one refinement: the application encryption key is derived from the shared secret, not simply the shared secret itself.
   
   ---

- ## **Step 6** - The server sends the HTTP response

   The server might respond with:

   ```
   HTTP/1.1 200 OK
   Content-Type: text/html
   ```

   The response body follows the headers.

   The server's TLS implementation protects the response with the appropriate server-to-client application traffic key. The response travels over TCP to the browser, which:

   1. Receives and reassembles the TCP byte stream.
   2. Processes the TLS records.
   3. Verifies their authentication tags and decrypts their contents.
   4. Passes the recovered HTTP response to the browser's HTTP implementation.
   5. Renders the returned content.

   The same TCP connection can carry many requests and responses. With HTTP/2, multiple streams can share one connection; with HTTP/1.1, persistent connections can also be reused.

   ---

- ## **Step 7** - What happens when the connection closes?

   TLS and TCP have separate shutdown mechanisms.

   - **TLS shutdown:** a peer can send a `close_notify` alert to signal that it has finished sending protected data.
   - **TCP shutdown:** the endpoints close their transport connection, commonly through `FIN` and `ACK` exchanges.

   A real browser may reuse the connection instead of closing it immediately. A network interruption can also prevent a clean shutdown.

## Put everything together

Here is the complete sequence in one compact reference.

| Stage | What happens | Main purpose |
| --- | --- | --- |
| 1. DNS	Browser | resolves `example.com` to an IP address. | Find the server |
| 2. TCP SYN | Client sends SYN. | Request a TCP connection |
| 3. TCP SYN-ACK | Server acknowledges and sends SYN. | Accept and synchronize |
| 4. TCP ACK | Client acknowledges the server's SYN. | Establish TCP |
| 5. ClientHello | Browser offers TLS parameters and a key share. | Start TLS negotiation |
| 6. ServerHello | Server selects parameters and sends its key share. | Agree on TLS settings and key agreement |
| 7. Key derivation | Both sides derive handshake secrets and keys. | Protect the rest of the handshake |
| 8. EncryptedExtensions | Server sends additional negotiated settings. | Complete negotiation |
| 9. Certificate | Server sends its certificate chain. | Provide identity and public-key information |
| 10. Certificate validation | Browser checks the chain, hostname, validity, and applicable policies. | Decide whether the certificate is trusted |
| 11. CertificateVerify | Server signs the handshake transcript with its certificate private key. | Prove possession of the private key |
| 12. Server Finished | Server confirms the handshake transcript. | Verify server-side handshake integrity |
| 13. Client Finished | Browser confirms the handshake transcript. | Complete the client's handshake confirmation |
| 14. HTTP request | Browser sends protected application data. | Request the website |
| 15. HTTP response | Server sends protected application data. | Return the website content |

**One final distinction:** this flow describes HTTPS over TCP. HTTP/3 uses QUIC over UDP, with TLS 1.3 integrated into QUIC's connection establishment rather than a separate TCP three-way handshake followed by TLS.

> The core idea is that the CA helps the browser establish trust in the server's certificate; TLS then proves possession of the associated private key and establishes protected session keys; finally, symmetric authenticated encryption protects the actual communication.

---

### Why Use This Combination?

- **Certificate-based authentication and signatures** help authenticate the server and protect the handshake.
- **Key agreement** establishes shared secret material without sending that secret directly over the network.
- **Symmetric authenticated encryption** protects ongoing application traffic efficiently.
- **Ephemeral key agreement** can provide forward secrecy: a later compromise of the server's long-term private key does not, by itself, reveal previously recorded sessions' traffic keys, assuming the ephemeral secrets were securely erased and the protocol was correctly implemented.

## Important Security Concepts

### Forward Secrecy

Forward secrecy means that compromise of a long-term authentication key does not automatically expose previously established session keys.

Ephemeral key agreement, such as ECDHE, is commonly used to achieve this property in TLS. Static RSA key transport does not provide the same property.

### Public-Key Distribution vs. Public-Key Authentication

A public key can be distributed openly, but a receiver still needs to establish that it belongs to the intended party.

For example, an attacker might provide their own public key while claiming it belongs to a legitimate server. Certificate validation, trusted fingerprints, or another authenticated key-distribution mechanism helps prevent this type of substitution attack.

### Encryption vs. Authenticated Encryption

Encryption alone does not necessarily detect modifications. Authenticated encryption, such as AES-GCM and ChaCha20-Poly1305, combines confidentiality with integrity and authenticity checks for the encrypted record.

### Post-Quantum Cryptography

RSA, traditional Diffie–Hellman, and common elliptic-curve schemes are vulnerable to sufficiently capable quantum computers running Shor's algorithm. Post-quantum cryptographic algorithms are designed to resist known attacks from both classical and quantum computers. Modern cryptographic standards and protocols are evolving to incorporate these algorithms.

## 7. Quick Comparison

| Feature | Symmetric Cryptography | Asymmetric Cryptography |
|---|---|---|
| Keys | Shared secret key | Public/private key pair |
| Main uses | Data encryption and authenticated encryption | Signatures, public-key encryption, key agreement |
| Performance | Generally very fast | Generally more computationally expensive |
| Key distribution | Shared secret must be established securely | Public keys can be shared openly, but authenticity must be established |
| Digital signatures | Not provided by ordinary symmetric encryption alone | Supported by signature algorithms |
| Large data encryption | Well suited | Usually not used directly |
| Examples | AES, ChaCha20 | RSA, ECDSA, Ed25519, ECDH |

**Core takeaway:** Symmetric cryptography efficiently protects data using shared secret keys. Asymmetric cryptography provides mechanisms for public-key signatures, certain forms of encryption, and key agreement. Modern systems combine these techniques and rely on sound authentication, key management, and protocol design to achieve secure communication.
