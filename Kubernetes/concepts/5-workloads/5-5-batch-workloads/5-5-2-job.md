# Job

A **Job** is a Kubernetes workload resource that runs one or more Pods until a specified number of successful completions is achieved. a Job is designed for **run-to-completion tasks**.

### Typical Use Cases

* Database migrations
* Data processing
* Report generation
* Cleanup tasks
* One-time administrative operations
* Batch computations

---

## How a Job Works

A Job defines a Pod template under `spec.template`. The Job controller creates and manages Pods according to the Job's completion and parallelism settings.

The basic lifecycle is:

```text
Job created
    ↓
Job controller creates Pod(s)
    ↓
Pod runs the task
    ↓
Successful completion
    ↓
Required completions reached
    ↓
Job → Complete
```

If Pods fail, Kubernetes retries the work according to the Job's configuration until the required completions are achieved or the Job is marked Failed.

---

# Key Fields

- ## completions

    Defines how many **successful Pod executions** are required for the Job to complete.

    Default:

    ```yaml
    completions: 1
    ```

    For example:

    ```yaml
    completions: 3
    ```

    means the Job must achieve three successful completions.

    Failed Pods do not count toward the completion total.

    ---

- ## parallelism

    Defines the maximum number of Pods that can run concurrently.

    For example:

    ```yaml
    completions: 5
    parallelism: 2
    ```

    The Job needs five successful completions but can run at most two Pods at the same time.

    If `parallelism` is omitted, its default is `1`.

    Therefore:

    ```text
    completions → How many successful executions are required
    parallelism → How many Pods may run concurrently
    ```

    ---

- ## backoffLimit

    Defines how many Pod failures are tolerated before the Job is considered failed.

    Default:

    ```yaml
    backoffLimit: 6
    ```

    For example:

    ```yaml
    backoffLimit: 4
    ```

    allows the Job to retry failed work before eventually being marked `Failed`.

    The exact retry behavior also depends on the Pod's `restartPolicy`, because a failure may involve restarting a container within the same Pod or creating a replacement Pod.

    ---

- ## activeDeadlineSeconds

    Defines a maximum amount of **wall-clock time** that the Job may remain active.

    ```yaml
    activeDeadlineSeconds: 600
    ```

    If the deadline is exceeded, Kubernetes terminates active Pods and marks the Job as failed.

    Unlike `backoffLimit`, which limits failure/retry behavior, `activeDeadlineSeconds` limits **execution time**.

    It is useful for preventing a batch task from running indefinitely.

---

- ## ttlSecondsAfterFinished

    Controls automatic cleanup of a completed Job.

    ```yaml
    ttlSecondsAfterFinished: 3600
    ```

    After the Job reaches a terminal state (`Complete` or `Failed`), Kubernetes can automatically delete the Job after the specified number of seconds.

    This is a **cleanup mechanism**. It does not affect:

    * Job execution
    * Retries
    * Completion criteria
    * Runtime behavior

    When the Job is deleted by the TTL controller, its dependent Pods are also deleted according to Kubernetes garbage-collection behavior.

---

# Job Lifecycle

A simplified Job lifecycle is:

```text
1. YAML submitted
           ↓
2. Job created
           ↓
3. Job controller creates Pod(s)
           ↓
4. Pod runs the task
           ↓
5. Pod succeeds or fails
           ↓
   ┌───────────────┐
   │               │
Success          Failure
   │               │
   ↓               ↓
Count completion  Retry
   │               │
   ↓               ↓
Required count?   Retry limit?
   │               │
  Yes             Yes
   ↓               ↓
Complete          Failed
```

A successful container normally exits with exit code `0`.

# Restart Policy

For Job Pods, `restartPolicy` can only be:

```yaml
restartPolicy: Never
```

or:

```yaml
restartPolicy: OnFailure
```

`Always` is not permitted for Job Pods because Jobs are designed for tasks that eventually terminate.

- ### OnFailure

    With `OnFailure`, kubelet restarts the failed container within the same Pod.

    ```text
    Pod
    └── Container
        ├── fails
        ├── restarts
        ├── fails
        └── restarts
    ```

    The Pod itself remains the same.

- ### Never

    With `Never`, a failed container causes the Pod to become `Failed`.

    The Job controller can then create a new Pod to retry the work.

    ```text
    Pod 1 → Failed
              ↓
           Job retry
              ↓
    Pod 2 → Running
    ```

Therefore:

| `restartPolicy` | Failure handling                            |
| --------------- | ------------------------------------------- |
| `OnFailure`     | Restart container in the same Pod           |
| `Never`         | Pod fails; Job can create a replacement Pod |

> `restartPolicy` controls container restart behavior inside a Pod. `backoffLimit` controls how much Job-level failure/retry behavior is tolerated.

> **`backoffLimit`** controls when a Job is considered failed. What Kubernetes counts toward that limit depends on the Pod's **`restartPolicy`**:
>
> | **`restartPolicy`** | When a container fails | What contributes to **`backoffLimit`** |
> | ------------- | ---------------------- | -------------------------------- |
> | **`OnFailure`** | Kubelet restarts the container in the same Pod  |  **Container restart** counts in active Pods |
> | **`Never`** | Container is not restarted; the Pod becomes **Failed** | **Failed Pods** |
>
> For example, with:
>
> ```yaml 
> spec:
>   backoffLimit: 4
>   template:
>     spec:
>       restartPolicy: OnFailure
> ```
>
> if the container repeatedly fails:
>
> ```
> Same Pod
>   failure → restart
>   failure → restart
>   failure → restart
>   failure → restart
>   → backoff limit reached → Job fails
> ```
>
> With **`Never`**:
>
> ```
> Pod-1 → fails
> Pod-2 → fails
> Pod-3 → fails
> Pod-4 → fails
> → backoff limit reached → Job fails
> ```
>
> **Important:** **`backoffLimit`** is not simply "the number of times Kubernetes restarts a container." With **`OnFailure`**, the Job controller considers **container restart** counts when calculating failures; with **`Never`**, it considers **failed Pods**. The exact controller calculation can also include failed Pods already recorded.
> 
> Also, kubelet's container restart backoff (the delay between container restarts) is separate from the Job's backoffLimit.

# Example Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  completions: 3
  parallelism: 2
  backoffLimit: 4

  template:
    spec:
      restartPolicy: OnFailure

      containers:
        - name: migrate
          image: mytool:1.0
          command: ["./migrate.sh"]
```

### Configuration


> **`completions: 3`** → Three successful executions are required.
> 
> **`parallelism: 2`** → At most two Pods run simultaneously.
> 
> **`backoffLimit: 4`** → Failed work is retried according to the Job's failure policy.
> 
> **`restartPolicy: OnFailure`** → Failed containers can be restarted within the same Pod.

---

# `completions` vs `parallelism`

These two fields are commonly confused.

Suppose:

```yaml
completions: 5
parallelism: 3
```

The Job needs **5 successful completions**, but no more than **3 Pods can run simultaneously**.

```text
Time →

Pod 1 ────────── Success
Pod 2 ─────── Success
Pod 3 ─────────────── Success
                    ↓
Pod 4 ───────── Success
Pod 5 ───────────── Success
                    ↓
              Job Complete
```

The important distinction is:

```text
completions → total successful executions required
parallelism → maximum concurrent executions
```

This makes Jobs useful for parallel batch processing and distributed workloads.

# Job vs Init Container

Both Jobs and init containers can execute tasks that eventually terminate, but they have fundamentally different scopes and purposes.

- ## Init Container

    An **init container** is part of a specific Pod.

    It:

    * Runs before the main application containers.
    * Must complete successfully before the main containers start.
    * Is tied to the lifecycle of its Pod.
    * Cannot exist independently.
    * Is commonly used for setup and initialization.

    Typical uses:

    * Waiting for a dependency
    * Preparing configuration
    * Initializing files
    * Downloading required data
    * Performing lightweight setup tasks

    Lifecycle:

    ```text
    Init Container
          ↓
    Main Container(s)
          ↓
    Pod runs
    ```

    ---

- ## Job

    A **Job** is an independent workload resource.

    It:

    * Creates and manages Pods.
    * Runs tasks to completion.
    * Can require multiple successful completions.
    * Can run Pods in parallel.
    * Can retry failed work.
    * Exists independently of any particular application Pod.

    Lifecycle:

    ```text
    Job
     ↓
    Pod(s)
     ↓
    Task completes
     ↓
    Job Complete
    ```

---

## Comparison

| Aspect              | Init Container                  | Job                                   |
| ------------------- | ------------------------------- | ------------------------------------- |
| Purpose             | Prepare a Pod                   | Execute a standalone task             |
| Scope               | Pod-level                       | Workload-level                        |
| Runs independently  | No                              | Yes                                   |
| Creates Pods        | No                              | Yes                                   |
| Can run in parallel | No                              | Yes                                   |
| Retry behavior      | Part of Pod startup             | Job-controlled                        |
| Runs continuously   | No                              | No                                    |
| Typical use         | Setup/dependency initialization | Migrations, batch processing, reports |
| Lifecycle           | Before main containers          | Until completion criteria are met     |

### When to Use Which?

Use an **init container** when the task is required to prepare a specific Pod before its main application starts.

Use a **Job** when Kubernetes needs to manage a **standalone task that runs to completion**.

For example:

```text
Application Pod
└── Init Container
    └── Prepare environment
```

versus:

```text
Job
└── Migration Pod
    └── Run database migration
```

# Summary

* A **Job** runs Pods until the required number of successful completions is reached.
* `completions` defines the number of successful executions required.
* `parallelism` defines the maximum number of concurrent Pods.
* `backoffLimit` controls tolerated Job failures/retries.
* `activeDeadlineSeconds` limits the Job's active wall-clock time.
* `ttlSecondsAfterFinished` provides automatic cleanup after completion or failure.
* Job Pods support only `Never` and `OnFailure` restart policies.
* `RollingUpdate` and other long-running workload strategies do not apply to Jobs.
* Jobs can run tasks once, multiple times, or in parallel.
* A **Job** is an independent workload, while an **init container** is a setup mechanism inside a Pod.
