# StatefulSet

A **StatefulSet** is a Kubernetes controller used to manage **stateful applications**. Unlike Deployments, which are primarily designed for stateless workloads, StatefulSets provide:

* Stable Pod identity
* Stable network identity
* Persistent storage per Pod
* Ordered Pod creation and deletion

Stateful applications are systems where individual instances need to maintain their own identity, storage, or role. Typical examples include:

* MySQL or PostgreSQL clusters
* MongoDB
* Cassandra
* Kafka
* ZooKeeper

These systems often require predictable identities and persistent storage, which a Deployment does not provide.

---

## Why Deployments Are Not Suitable for Stateful Applications

Deployments create Pods that are generally **interchangeable**. Their identities are not stable and their names are generated by the ReplicaSet.

For example:

```text
web-7d8f6c9b7d-x2k4m
web-7d8f6c9b7d-p8j6q
web-7d8f6c9b7d-r4n2z
```

These Pods:

* Do not have stable identities.
* Can be replaced with different Pods.
* Do not provide stable per-Pod DNS identities.
* Do not provide a dedicated persistent volume for each Pod by default.
* Do not provide ordered startup and shutdown.

For stateless applications such as web servers and REST APIs, this behavior is desirable.

However, stateful applications may require:

* Stable hostnames
* Stable storage
* Predictable Pod identities
* Ordered startup and shutdown

StatefulSets provide these capabilities.

# Key Features of StatefulSet

- ## Stable Pod Names

    Each Pod in a StatefulSet receives a predictable name based on its ordinal index.

    The naming format is:

    ```text
    <statefulset-name>-<ordinal-index>
    ```

    For example, if the StatefulSet is named `mysql`:

    ```text
    mysql-0
    mysql-1
    mysql-2
    ```

    The ordinal starts at `0`.

    If `mysql-1` is deleted, the StatefulSet recreates it with the same name:

    ```text
    mysql-1
    ```

    The Pod may receive a different IP address, but its StatefulSet identity remains the same.

    This stable identity is important for distributed systems that need to distinguish individual members.

    ---

- ## Stable Network Identity

    StatefulSets can provide stable DNS identities for individual Pods through a Service, commonly a **Headless Service**.
    
    For example:
    
    ```text
    mysql-0.mysql.default.svc.cluster.local
    mysql-1.mysql.default.svc.cluster.local
    mysql-2.mysql.default.svc.cluster.local
    ```
    
    The general format is:
    
    ```text
    <pod-name>.<service-name>.<namespace>.svc.cluster.local
    ```
    
    A typical StatefulSet uses the `serviceName` field to associate the StatefulSet with the Service used for its network identity:
    
    ```yaml
    spec:
      serviceName: mysql
    ```
    
    A **Headless Service** is commonly used for this purpose because it allows DNS to return the individual Pod IP addresses instead of a Service ClusterIP.
    
    ### Important
    
    The stable Pod name alone does **not** create a DNS record.
    
    For example, creating a Pod named:
    
    ```text
    mysql-0
    ```
    
    does not automatically make:
    
    ```text
    mysql-0.mysql.default.svc.cluster.local
    ```
    
    resolvable.
    
    The per-Pod DNS records are created through Kubernetes Service/DNS mechanisms associated with the StatefulSet.
    
    > ## Headless Service
    > 
    > A **Headless Service** is a Kubernetes Service without a virtual ClusterIP. It is created by setting:
    > 
    > ```yaml
    > spec:
    >   clusterIP: None
    > ```
    > 
    > Unlike a normal ClusterIP Service, a Headless Service does not provide a single virtual IP for load balancing. Instead, Kubernetes DNS can return the IP addresses of the individual Pods selected by the Service.
    > 
    > ### Normal Service vs Headless Service
    > 
    > **ClusterIP Service:**
    >
    > ```text
    > client
    >    ↓
    > Service ClusterIP
    >    ↓
    > Pod A / Pod B / Pod C
    > ```
    > 
    > **Headless Service:**
    >
    > ```text 
    > client
    >    ↓
    > DNS
    >    ↓
    > Pod A / Pod B / Pod C IPs
    > ```
    > 
    > The client/application decides which returned Pod address to use. Kubernetes does not perform the normal Service-level load balancing through a ClusterIP.
    > 
    > ### Headless Services with StatefulSets
    > 
    > Headless Services are commonly used with StatefulSets because StatefulSets provide stable Pod identities, while the Headless Service provides DNS records that allow those Pods to be discovered individually.
    > 
    > For example:
    > 
    > ```text
    > StatefulSet: mysql
    > 
    > Pods:
    > mysql-0
    > mysql-1
    > mysql-2
    > ```
    > 
    > With a Headless Service named `mysql`, the Pods can be addressed using stable DNS names:
    > 
    > ```text
    > mysql-0.mysql.default.svc.cluster.local
    > mysql-1.mysql.default.svc.cluster.local
    > mysql-2.mysql.default.svc.cluster.local
    > ```
    > 
    > The general format is:
    > 
    > ```text
    > <pod-name>.<service-name>.<namespace>.svc.cluster.local
    > ```
    > 
    > These DNS names resolve to the current IP address of the corresponding Pod. If the Pod is recreated and receives a new IP, the DNS record continues to point to the Pod with the same StatefulSet identity.
    > 
    > ### Why Not Use a Normal ClusterIP Service?
    > 
    > A normal ClusterIP Service provides a single virtual IP and distributes traffic among its endpoints:
    > 
    > ```text
    > mysql.default.svc.cluster.local
    >           ↓
    >       ClusterIP
    >           ↓
    >   ┌───────┼───────┐
    > mysql-0 mysql-1 mysql-2
    > ```
    > 
    > This is useful when the client only needs **any available Pod**.
    > 
    > However, stateful applications may need to communicate with a **specific instance**, such as:
    > 
    > ```text
    > mysql-0 → primary
    > mysql-1 → replica
    > mysql-2 → replica
    > ```
    > 
    > A Headless Service allows applications to address those individual Pods directly.
    > 
    > ### Common Pattern
    > 
    > A StatefulSet can use both types of Services for different purposes:
    > 
    > ```text
    > Headless Service
    >     ↓
    > Stable per-Pod DNS
    >     ↓
    > Pod-to-Pod communication
    > 
    > ClusterIP Service
    >     ↓
    > Single virtual IP
    >     ↓
    > Access to any suitable Pod
    > ```
    > 
    > ### Example
    > 
    > ```yaml
    > apiVersion: v1
    > kind: Service
    > metadata:
    >   name: mysql
    > spec:
    >   clusterIP: None
    >   selector:
    >     app: mysql
    >   ports:
    >     - port: 3306
    > ```
    > 
    > Here:
    > 
    > * `clusterIP: None` makes the Service headless.
    > * `selector` selects the StatefulSet Pods labeled `app: mysql`.
    > * DNS can return the IP addresses of the selected Pods.
    > * StatefulSet Pod-specific DNS names can be used to address individual Pods.
    > 
    > **Important:** The stable DNS name such as `mysql-0.mysql.default.svc.cluster.local` exists because of the Service/DNS mechanism associated with the StatefulSet. The Pod's stable name alone does not automatically create this DNS record.
     
    > ### StatefulSet Pod DNS Name
    >
    > A StatefulSet Pod can have a stable DNS name through its associated Headless Service.
    > 
    > The general format is:
    > 
    > ```text
    > <pod-name>.<service-name>.<namespace>.svc.<cluster-domain>
    > ```
    > 
    > For example:
    > 
    > ```text
    > mysql-0.mysql.default.svc.cluster.local
    > ```
    > 
    > | Part            | Meaning                       |
    > | --------------- | ----------------------------- |
    > | `mysql-0`       | Specific StatefulSet Pod      |
    > | `mysql`         | Headless Service name         |
    > | `default`       | Kubernetes namespace          |
    > | `svc`           | Kubernetes Service DNS domain |
    > | `cluster.local` | Cluster DNS domain (default)  |
    > 
    > Therefore:
    > 
    > ```text
    > mysql-0.mysql.default.svc.cluster.local
    >    │       │       │       │
    >    │       │       │       └── Cluster DNS domain
    >    │       │       └────────── Service DNS domain
    >    │       └────────────────── Service
    >    └────────────────────────── Pod
    > ```
    > 
    > For a StatefulSet with three Pods:
    > 
    > ```text
    > mysql-0.mysql.default.svc.cluster.local
    > mysql-1.mysql.default.svc.cluster.local
    > mysql-2.mysql.default.svc.cluster.local
    > ```
    > 
    > These names provide stable DNS identities for the StatefulSet Pods. If a Pod is recreated or rescheduled and receives a new IP address, its StatefulSet identity and DNS name remain the same.
    > 
    > `cluster.local` is the default Kubernetes cluster domain, but a cluster can be configured with a different domain.

    ---

- ## Persistent Storage Per Pod

    StatefulSets can create a separate PersistentVolumeClaim (PVC) for each Pod using `volumeClaimTemplates`.

    For example:

    ```text
    mysql-0 → data-mysql-0
    mysql-1 → data-mysql-1
    mysql-2 → data-mysql-2
    ```

    Each Pod receives its own PVC instead of all Pods sharing the same PVC.

    Example:

    ```yaml
    volumeClaimTemplates:
      - metadata:
          name: mysql-storage
        spec:
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 10Gi
    ```

    The StatefulSet uses the Pod's ordinal identity to create separate PVCs.

    For example:

    ```text
    mysql-0 → mysql-storage-mysql-0
    mysql-1 → mysql-storage-mysql-1
    mysql-2 → mysql-storage-mysql-2
    ```

    The exact PVC name is based on the volume claim template name and StatefulSet Pod identity.

    If a Pod is deleted and recreated, the StatefulSet associates the recreated Pod with its existing PVC.

    Therefore:

    ```text
    mysql-0
       ↓
    same identity
       ↓
    same PVC
       ↓
    same persistent data
    ```

    This allows the Pod to reconnect to its existing storage after recreation.

    ### Important

    StatefulSets provide **stable storage mapping**, not database replication.

    For example:

    ```text
    StatefulSet
        ↓
    Stable Pod identity
        ↓
    Stable PVC mapping

    Database
        ↓
    Replication
        ↓
    Data synchronization
    ```

    Database replication or clustering is handled by the database system itself, not by the StatefulSet.

    ---

- ## Ordered Pod Creation

    By default, StatefulSets use:

    ```yaml
    podManagementPolicy: OrderedReady
    ```

    With `OrderedReady`, Pods are created sequentially according to their ordinal.

    For:

    ```yaml
    replicas: 3
    ```

    the creation order is:

    ```text
    mysql-0
        ↓
    mysql-1
        ↓
    mysql-2
    ```

    Kubernetes creates `mysql-0` first and waits for it to become **Ready** before creating `mysql-1`.

    Then it waits for `mysql-1` to become Ready before creating `mysql-2`.

    The process is:

    ```text
    1. Create mysql-0
    2. Wait for mysql-0 to become Ready
    3. Create mysql-1
    4. Wait for mysql-1 to become Ready
    5. Create mysql-2
    6. Wait for mysql-2 to become Ready
    ```

    This is useful for distributed systems that require controlled startup or bootstrapping.

    For example:

    ```text
    node-0 → leader
    node-1 → follower
    node-2 → follower
    ```

    The application may require the first node to initialize before other nodes join the cluster.

    ### Important

    The relevant condition is **Ready**, not simply Running.

    A Pod can be:

    ```text
    Running
    NotReady
    ```

    In that case, an `OrderedReady` StatefulSet does not consider that Pod ready for progressing to the next ordinal.

    ---

    ## Ordered Behavior During Failures

    Suppose a StatefulSet is being created:

    ```text
    mysql-0 → Ready
    mysql-1 → Ready
    mysql-2 → Not created
    ```

    If `mysql-0` becomes NotReady, the StatefulSet's ordered behavior can prevent progression while the required earlier Pod is not Ready.

    The general idea is:

    ```text
    mysql-0 → NotReady
          ↓
    Wait for mysql-0
          ↓
    mysql-0 → Ready
          ↓
    Continue StatefulSet progression
    ```

    StatefulSets use this ordering because earlier Pods may be important to the initialization or correctness of a stateful cluster.

    ---

- ## Ordered Pod Deletion

    With `OrderedReady`, StatefulSets terminate Pods in reverse ordinal order.

    For:

    ```text
    mysql-0
    mysql-1
    mysql-2
    ```

    the deletion order is:

    ```text
    mysql-2
    mysql-1
    mysql-0
    ```

    When scaling down, Kubernetes waits for the higher-ordinal Pod to terminate before proceeding to the next one.

    This provides predictable shutdown behavior for applications that depend on member ordering.

# StatefulSet Pod Management Policy

The **`podManagementPolicy`** field controls how StatefulSet Pods are created and deleted.

There are two possible values:

```text
OrderedReady
Parallel
```

- ## OrderedReady

    `OrderedReady` is the default.

    ```yaml
    podManagementPolicy: OrderedReady
    ```

    Pods are created sequentially and the StatefulSet waits for each required preceding Pod to become Ready before creating the next one.

    For:

    ```yaml
    replicas: 3
    ```

    the normal creation order is:

    ```text
    app-0 → Ready
               ↓
    app-1 → Ready
               ↓
    app-2 → Ready
    ```

    Deletion occurs in reverse order:

    ```text
    app-2
      ↓
    app-1
      ↓
    app-0
    ```

    This is useful for applications that require controlled startup and shutdown.

    > If you **don't** define a **readiness probe**, Kubernetes uses the container's built-in readiness behavior:
    >
    > - The container starts successfully.
    > - The container is considered Ready by default.
    > - Therefore, the Pod's Ready condition becomes True once its containers are running and there are no other conditions preventing readiness.
    > 
    > So with:
    >
    > ```yaml 
    > podManagementPolicy: OrderedReady
    > replicas: 3
    > ```
    > 
    > and no readiness probe:
    >
    > ``` 
    > Create mysql-0
    >       ↓
    > Container starts
    >       ↓
    > mysql-0 becomes Ready
    >       ↓
    > Create mysql-1
    >       ↓
    > Container starts
    >       ↓
    > mysql-1 becomes Ready
    >       ↓
    > Create mysql-2
    > ``` 
    ---

- ## Parallel

    With:
    
    ```yaml
    podManagementPolicy: Parallel
    ```
    
    StatefulSet Pods can be created and terminated in parallel without waiting for the other Pods to become Ready.
    
    For:
    
    ```yaml
    replicas: 3
    ```
    
    Kubernetes can create:
    
    ```text
    app-0
    app-1
    app-2
    ```
    
    without waiting for `app-0` to become Ready before creating `app-1`.
    
    The same applies to **deletion**. Pods do not have to be terminated sequentially.
    
    ### Important
    
    `Parallel` does **not** remove the other StatefulSet guarantees.
    
    The Pods still have:
    
    * Stable names
    * Stable identity
    * Stable storage mapping
    * StatefulSet ordinal indexes
    
    Only the creation and deletion ordering behavior changes.

# Example StatefulSet Manifest

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 3
  podManagementPolicy: OrderedReady
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8
          ports:
            - containerPort: 3306

          volumeMounts:
            - name: mysql-storage
              mountPath: /var/lib/mysql
  volumeClaimTemplates:
    - metadata:
        name: mysql-storage
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 10Gi
```

This StatefulSet creates:

```text
Pods:
mysql-0
mysql-1
mysql-2

PVCs:
mysql-storage-mysql-0
mysql-storage-mysql-1
mysql-storage-mysql-2
```

Each Pod mounts its own PVC at:

```text
/var/lib/mysql
```

The `serviceName` associates the StatefulSet with the Service used for its stable network identity.

# StatefulSet vs Deployment

| Deployment                                                  | StatefulSet                                    |
| ----------------------------------------------------------- | ---------------------------------------------- |
| Primarily used for stateless workloads                      | Used for stateful workloads                    |
| Pods are interchangeable                                    | Pods have stable identities                    |
| Pod names are generated and not stable                      | Pod names are predictable                      |
| No stable per-Pod DNS identity                              | Can provide stable per-Pod DNS identity        |
| Persistent storage is not automatically mapped per Pod      | Can create a dedicated PVC per Pod             |
| Pods are generally created/deleted without ordinal ordering | Supports ordered creation/deletion             |
| Suitable for web servers and REST APIs                      | Suitable for databases and distributed systems |

### Deployment

Typical examples:

```text
Web servers
REST APIs
Frontend applications
Stateless backend services
```

### StatefulSet

Typical examples:

```text
Databases
Message queues
Distributed databases
Distributed storage systems
Other applications requiring stable identity
```

# Summary

A StatefulSet is useful when individual Pods need a **stable identity and stable relationship with their storage and network identity**.

Its main characteristics are:

* **Stable Pod names**

  * `mysql-0`, `mysql-1`, `mysql-2`

* **Stable network identity**

  * Commonly provided through a Headless Service

* **Persistent storage per Pod**

  * `volumeClaimTemplates` creates a dedicated PVC for each Pod

* **Ordered Pod management**

  * `OrderedReady` provides sequential creation and reverse-order deletion

* **Optional parallel management**

  * `Parallel` removes the ordering requirement for creation and deletion

StatefulSets provide the Kubernetes-level identity and storage guarantees that stateful applications often require. The application itself remains responsible for things such as **data replication, clustering, leader election, and data consistency**.
